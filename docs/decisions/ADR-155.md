# ADR-155 — L'animation de M4 : format SKEL/ANIM, `ax-anim`, graphe vivant, skinning et palettes

- **Statut** : **accepté** le 2026-10-29 par Killian : Q1 à Q4 tranchées comme proposé (serveur
  autoritaire, clés `f32`, `AnimationControl` minimal, glTF générés par script). L'ADR touche :
  - un format persistant d'asset (DM-10, `COMPILER_VERSION` 15) ;
  - la frontière des palettes (IF-05, schéma de `RENDER_OUT`) ;
  - le réseau (descripteur d'états procéduraux) ;
  - une API publique (`AnimationControl`, figée en 1.x).

  Ces choix ne se décident pas sans lui (CDC §5, contrat d'implémentation l.8237). Les quatre questions
  sont en fin de document.
- **Date** : 2026-10-29
- **Portée** :
  - C-37 (fiche 5.28 : PARTIE 18, R-1430..R-1480) ;
  - C-30, sa part vivante (étape 14, `axion.scene.propagate_ns`, R-600..R-601) ;
  - C-66 (fiche 5.53 : R-790..R-792), et C-61 pour R-742 (skinning CPU du backend vanilla) ;
  - DM-10 (`BoneDesc`, `AnimationDesc`, `TrackDesc`, R-200) et IF-05 ;
  - `AnimationControl` (ADR-143) ;
  - les tests T-360..T-368 sauf T-365, T-392, T-540..T-542 et T-908 ;
  - les overlays `bones`, `nodes` et `pivots` (ADR-146 §1).
- **Ordonné par** :
  - l'ordre des chantiers de M4 décidé par Killian le 2026-10-22, où l'animation vient en dernier ;
  - [ADR-137](ADR-137.md) : graphe vivant, accesseur `animation` ;
  - [ADR-144](ADR-144.md) : T-392, palier `skinning` ;
  - [ADR-146](ADR-146.md) §1 et §7 ; [ADR-150](ADR-150.md) D6 ; [ADR-151](ADR-151.md) D8 et D9 ;
  - [ADR-154](ADR-154.md) : les palettes entrent dans `RENDER_OUT` avec l'animation.

## Contexte

- **Le format n'existe pas.**
  - Les tags `SKEL` et `ANIM` sont déclarés dans `ax-asset/src/a3d/mod.rs`. En revanche, le code ne
    définit ni `BoneDesc`, ni `AnimationDesc`, ni `TrackDesc`, et aucune section n'est écrite.
  - L'importeur glTF lit `JOINTS_0` et `WEIGHTS_0` dans les sommets et pose `SKINNED`. Il valide les skins
    et les animations, mais ne les importe pas.
  - `COMPILER_VERSION` vaut 14.
- **Le graphe de scène existe, mais ne vit pas.**
  - `ax-scene` propage et mesure `propagate_ns`, mais il n'est branché ni dans la simulation ni au rendu.
  - L'étape 14 (`Stage::SceneGraph`) est déclarée et vide.
  - Le dessin pose chaque mesh à la pose de son corps (ADR-151 D9, « forme minimale du graphe vivant »).
- **Le skinning n'existe pas.**
  - Le shader du backend natif ne déclare ni les attributs 6 (`bones`) et 7 (`weights`), ni le décalage
    de palette.
  - `palette_offset` est écrit à 0 dans le bloc d'instance.
  - `RenderCapabilities` dit le skinning non livré.
- **L'API est vide.**
  - `AnimationControl` est une interface vide. `Assembly.animation()` est déclaré, sans implémentation.
  - Le schéma de definition accepte déjà `animation` : `clip`, `layer`, `drives_joint`, `trigger`.
- **Aucun modèle animé** n'est dans le dépôt.
- **Ce que le CDC ne définit pas** :
  - la disposition des clés dans `ANIM` : format, quantification, tangentes de `CUBIC_SPLINE` ;
  - les valeurs de `channel` et d'`interp`, et la sémantique de `AnimationDesc.flags` ;
  - un `SKEL` à plusieurs skins ;
  - le format des palettes dans `RENDER_OUT` ;
  - un budget d'animation (DM-18) ;
  - les membres d'`AnimationControl` ;
  - les tests T-540..T-542 (T-541 est absent de l'ID-MAP) ;
  - l'IK et les events attachés à un clip, dont il ne dit rien.
- **Hors de ce chantier, par le CDC** :
  - la machine à états (R-1440, hors V1.0) ;
  - l'animation pilotée par la déformation et le scénario de la porte endommagée (§18.5, M6, avec C-42) ;
  - les sources procédurales de véhicule — roue, direction, suspension (M5, T-365) ;
  - le root motion ne déplace jamais une assembly physique (R-1480).

## Décision proposée

### D1. Le périmètre

- **Dans ce chantier** :
  - DM-10 et l'import glTF des skins et des animations, de node comme squelettiques ;
  - `ax-anim` :
    - l'échantillonnage par recherche binaire avec curseur, en `STEP`, `LINEAR` et `CUBIC_SPLINE` (§18.2) ;
    - quatre couches (`BASE`, `ADDITIVE_1`, `ADDITIVE_2`, `OVERRIDE`) avec masque d'os ;
    - le blending en TRS, jamais en matrices ;
    - le crossfade linéaire ;
  - l'animation qui pilote le moteur d'un joint (R-932, étape 2) ;
  - le graphe vivant, étapes 2 et 14 : côté client toujours ; côté serveur seulement quand un socket, un
    collider ou une attache en dépend (R-1430) ;
  - le skinning GPU du backend natif (C-66, TBO, repli UBO) et le skinning CPU du backend vanilla (R-742,
    plafonné) ;
  - les palettes dans `RENDER_OUT` ;
  - `AnimationControl` ;
  - les overlays `bones`, `nodes` et `pivots`.
- **Renvoyé** : ce qui figure sous « Hors de ce chantier » ci-dessus. La limite de 256 pistes actives
  (R-200) est, elle, tenue dans ce chantier.

### D2. Le format : `SKEL` et `ANIM` (DM-10), `COMPILER_VERSION` 15 (Q2)

- **`SKEL`** :
  - `u32 bone_count`, puis les `BoneDesc[]` du CDC : `name_hash u64`, `parent u16`, `u16` réservé,
    `node u32`, `inverse_bind f32[16]` ;
  - un squelette par asset : plusieurs skins glTF sont fusionnés par node ;
  - au plus 128 os (`E-3060`).
- **`ANIM`** :
  - en-tête : `u32 animation_count`, `u32 track_count`, `u32 key_bytes` ;
  - `AnimationDesc[]` : nom haché, durée `f32`, première piste, nombre de pistes, drapeaux (bit 0 :
    boucle) ;
  - `TrackDesc[]` : node visé ; `channel` (0 translation, 1 rotation, 2 échelle) ; `interp` (0 `STEP`,
    1 `LINEAR`, 2 `CUBIC_SPLINE`) ; décalage et nombre de clés ;
  - puis les clés.
- **Proposé : clés en `f32` sans quantification.**
  - Chaque clé porte un temps, puis sa valeur (3 ou 4 flottants).
  - En `CUBIC_SPLINE`, une clé porte trois valeurs, comme glTF : tangente d'entrée, valeur, tangente de
    sortie.
  - La quantification se décidera plus tard, sur mesure, avec une version de section.
- Le compilateur passe à 15 : le cache d'assets se recompile.

### D3. L'échantillonnage : natif, à la frame côté client ; serveur conditionnel

- `ax-anim` échantillonne en natif (R-1460).
- Côté client, tout se passe dans `axion_render_prepare` :
  - l'état d'animation de chaque candidat arrive avec lui ;
  - la pose échantillonnée alimente le graphe (étape 14) et les palettes ;
  - les palettes sont écrites directement dans `RENDER_OUT`, schéma 3 : une table de palettes `mat4x3` à
    la suite, et chaque retenu skinné porte son décalage.
- Côté serveur, l'échantillonnage n'a lieu que si un socket, un collider ou une attache dépend d'un node
  animé (R-1430). Sinon, la simulation ignore l'animation.

### D4. Le réseau : l'état d'animation, autoritaire du serveur (Q1)

- **Proposé** : le serveur décide, par les triggers de definition et par `AnimationControl`.
- L'état de chaque couche voyage dans le descripteur d'états procéduraux : clip, tick de départ, vitesse,
  poids, fondu. Le descripteur passe en version 3 (ADR-150 D6 ; il est en v2 depuis ADR-151 D8).
- Le client échantillonne au temps de son interpolation (ADR-150 D7) et ne renvoie rien.

### D5. `AnimationControl` (Q3)

- **Proposé** : une API minimale, appelée sur le thread autoritatif :
  - `List<String> clips()` ;
  - `void play(String clip, int layer, float weight, float fadeSeconds)` ;
  - `void stop(int layer, float fadeSeconds)` ;
  - `void setSpeed(int layer, float speed)` ;
  - `Optional<String> playing(int layer)`.
- Un clip inconnu ou une couche hors de 0..3 lève `IllegalArgumentException`.
- L'API est figée en 1.x, comme `CustomData`.

### D6. Le skinning

- **Natif** :
  - les attributs 6 et 7 au shader, sous `SKINNED` ;
  - les palettes dans un TBO (R-790), avec un repli UBO paginé ;
  - 128 os par palette, 4 os par sommet ;
  - au plus `render.max_skinned_instances` (64) instances skinnées ; au-delà, pose de repos et métrique
    (R-791) ;
  - l'ordre est le skinning, puis la déformation, puis le transform d'instance (R-792).
- **Vanilla** :
  - les sommets sont skinnés sur le CPU avant l'envoi au `VertexConsumer` ;
  - le volume est plafonné par `vanilla_max_skinned_vertices` (R-742) ; au-delà, pose de repos et
    métrique.

### D7. Les tests

Le CDC ne définit ni T-540, ni T-541, ni T-542. Cet ADR les définit, comme ADR-154 l'a fait pour les
siens.

- **T-540** : la palette d'une pose connue est celle du calcul de référence, os par os, `inverse_bind`
  compris.
- **T-541** : le chemin TBO et le repli UBO donnent la même image, au banc de rendu.
- **T-542** : au-delà de `render.max_skinned_instances`, la pose de repos s'applique et la métrique est
  émise.
- **T-360..T-364 et T-366..T-368** (§18), et **T-908**, tels que le CDC les nomme.
- **T-392** : les étapes côté client (R-662).
- **Les clips glTF de référence** sont échantillonnés aux temps des clés et entre elles, et comparés à la
  valeur attendue de chaque interpolation.

### D8. Le contenu de test (Q4)

- **Proposé** : des modèles animés écrits par script, en glTF généré par le code :
  - un bras à deux os ;
  - un pendule de node ;
  - un clip `CUBIC_SPLINE`.

  Ils sont versionnés comme les autres ressources de test : exacts, reproductibles, sans outil externe.
- Les modèles d'apparence réelle, découpés dans Blender, viendront à la phase fonctionnelle (workflow de
  contenu), Blender étant lancé par Killian.

## Mise en œuvre proposée

1. **Format et import** : DM-10, `SKEL`, `ANIM`, import glTF, `COMPILER_VERSION` 15, validation des os
   des sommets ; contenu de test.
2. **`ax-anim`** : échantillonnage, couches, blending, crossfade ; tests des interpolations.
3. **Le graphe vivant** :
   - étapes 2 et 14 : côté client dans la préparation du rendu, côté serveur de façon conditionnelle ;
   - `propagate_ns` ;
   - l'animation qui pilote un joint ;
   - T-392 et T-360..T-364.
4. **Réseau et API** : descripteur v3, `AnimationControl`, triggers de definition.
5. **Skinning natif** : shader, TBO, repli UBO, palettes dans `RENDER_OUT` (schéma 3) ; T-540, T-541,

6. **Skinning vanilla** (R-742), overlays `bones`, `nodes` et `pivots`, documentation.

## Précisions de mise en œuvre

### Tranche 1 — format et import (2026-10-29)

- **`ANIM` porte les noms des clips.** `AnimationControl.clips()` rend des noms, que l'empreinte
  seule ne rendrait pas : la section suit la table des noms de `NODE` (ADR-110). Disposition, en
  petit-boutiste :
  - en-tête de 16 octets : `animation_count`, `track_count`, `key_count` (en flottants),
    `names_size` ;
  - `AnimationDesc[]` (24 octets), `TrackDesc[]` (16), références de noms (8 : décalage, longueur) ;
  - les clés `f32`, puis les noms UTF-8.

  `key_offset` compte des flottants ; une clé occupe `1 + composantes × valeurs` flottants (4, 5,
  10 ou 13).
- **`SKEL`** : un en-tête de 8 octets (`bone_count`, un mot réservé qui aligne les os sur 8), puis
  les `BoneDesc[]` de 80 octets. Le parent d'un os est le plus proche ancêtre de son node qui soit
  un os ; il peut avoir un index plus grand que lui, l'ordre des os étant celui des skins.
- **Les skins se fusionnent par node.** Un node os de deux skins est un seul os, si les deux le
  lient par la même matrice ; sinon l'import refuse. Les indices d'os des sommets, locaux au skin
  dans glTF, sont traduits dans le squelette ; un joint de poids nul, que glTF laisse libre, prend
  l'os du premier joint. Un mesh porté par deux skins aux os différents est refusé.
- **Des `JOINTS_0` sans skin** : le mesh perd `SKINNED`, avec un avertissement, et se dessine
  rigide (R-912). C-22 refuse désormais un mesh `SKINNED` dans un asset sans squelette.
- **Les pistes de poids de morphing** sont ignorées avec un avertissement (R-912) : le moteur
  n'anime pas de morph targets en M4.
- **C-22 juge les animations** : node visé existant, canal et interpolation connus, au moins une
  clé, temps finis, positifs et strictement croissants, valeurs finies, rotations unitaires — la
  valeur seulement en `CUBIC_SPLINE`, les tangentes étant des dérivées —, durée couvrant la
  dernière clé. Plus de 128 os ou de 256 pistes dans une animation donnent `E-3060` (R-200), par
  deux violations dédiées, `TooManyBones` et `TooManyTracks`.
- **La boucle d'un clip** (`LOOP`) vient de l'annotation `extras.axion.loop` de l'animation glTF
  — décision de Killian du 2026-10-29, ni glTF ni le CDC ne le disant. Facultative (R-913) :
  sans elle, le clip joue une fois et tient sa dernière pose. Ni l'API ni le schéma de definition
  ne changent.
- **Les empreintes R-562 v15** ne changent que par l'en-tête : le corpus n'a ni skin ni
  animation.

### Tranche 2 — `ax-anim` (2026-10-29)

- **Aucune fonction transcendante.** Côté serveur, la pose d'un node animé entre dans la physique
  (R-1430), identique d'une plateforme à l'autre (ADR-116) : un `acos` ou un `sin` de la `libm` de
  la plateforme l'en ferait sortir. Le slerp développe `sin(tθ) / sin θ` en série de `cos θ - 1`
  par la récurrence d'Eberly, tronquée à **16 termes**, dont le dernier est corrigé par
  `μ = 1,9166671`. Ce `μ` a été trouvé par minimisation de l'écart maximal en `f64`, où l'écart
  tombe à 3,1e-8. À 8 termes, la série ne descend pas sous 1,9e-5. Écart mesuré en `f32` contre un
  slerp de référence en `f64` : 1,4e-7, l'arrondi. Le reste n'emploie qu'additions,
  multiplications, divisions et racines carrées, sans `mul_add`.
- **Le temps** : chaque clip qui joue garde `origine`, `ancre` et `vitesse`. Le temps de clip vaut
  `origine + (maintenant - ancre) × vitesse`, ramené par modulo si le clip boucle, borné sinon.
  Changer de vitesse ré-ancre sans saut. Ces trois valeurs, avec le poids et le fondu, sont ce que
  le descripteur v3 transportera (D4, tranche 4).
- **Couches additives** : relatives à la **pose de repos** du node. Pour la rotation, `r_repos⁻¹ · r`
  est portée à la puissance `w`, puis appliquée à droite. La translation reçoit l'écart pondéré, et
  l'échelle le rapport pondéré. `BASE` et `OVERRIDE` mélangent vers leur cible.
- **Crossfade** : du clip sortant, qui continue de jouer, à l'entrant. Un côté vide vaut la pose
  neutre : celle de dessous, ou le repos pour une couche additive. Quand on interrompt un fondu,
  celui des deux clips qui pesait le plus devient le sortant ; c'est le seul cas où la pose peut
  sauter.
- **R-200 à l'exécution** : au plus 256 pistes actives, fondus compris. Au-delà, le fondu est
  coupé ; si cela ne suffit pas, la lecture est refusée et l'instance reste inchangée.
- **Le masque** est un ensemble de nodes par couche. Sa source — definition ou API — se règle à la
  tranche 4.
- **Composition** : les modèles écrits par code sont importés par `ax-asset`, puis joués par
  `ax-anim`, et comparés à des valeurs calculées à la main. Exemple : le rebond monte d'exactement
  un bloc à mi-course.

### Tranche 3 — décisions de Killian (2026-10-29)

Quatre questions, tranchées comme proposé :

- **`RENDER_OUT` schéma 3, matrices par dessin.** Chaque retenu animé porte le décalage d'une table de
  matrices `mat4x3`, une par dessin, dans l'espace de l'asset comme `RestDraw.model` ; Java les
  substitue au repos et garde le reste (repère des corps, instancing). Un retenu non animé reste au
  repos. Les palettes de skinning (tranche 5) iront dans la même table.
- **Commandes horodatées, ABI 10.** `axion_render_animate` reçoit des commandes play, stop, vitesse,
  masque par id d'assembly, que Java pousse quand l'état change ; le contexte de rendu garde un
  `Animator` par id et l'évalue dans `axion_render_prepare`, au temps de rendu que porte `RENDER_IN`.
- **Serveur : opcodes et colliders.** Opcodes d'animation dans `SIM_IN`, `Animator` natif par assembly,
  échantillonnage aux étapes 2 et 14 seulement quand un collider dépend d'un node animé (R-1430,
  T-360) ; le collider suit alors sa pose dans son corps. Les sockets suivront leur composant.
- **Horloge : ticks du serveur.** Les instants sont des ticks de jeu (`f64`, fraction comprise ; une
  seconde vaut 20 ticks). Le serveur ancre chaque commande à son tick, le client échantillonne au
  tick interpolé d'ADR-150 D7 : animation et physique affichées restent synchrones.

### Tranche 3a — le client (2026-10-29)

- **`ANIM` se lit comme `LODM`.** Dès que `NODE` et `GEOM` sont chargés, sans bit de masque nouveau
  côté Java. Une table refusée, par sa lecture ou par la seconde passe de C-22 (R-540,
  `validate_animations`), ne refuse pas l'asset : il se rend au repos, et le refus est compté.
- **R-930 au chargement.** Le compilateur ne pose aucun état de node. Un node visé par une piste
  devient donc `ANIMATION_DRIVEN` dans le graphe vivant de l'asset, sans changer le format ni
  `COMPILER_VERSION`. Le graphe est construit une fois au chargement : une hiérarchie qu'il refuse,
  par exemple pour R-931, est refusée là, jamais à la première frame.
- **Une instance par `id` de candidat.** Le contexte de rendu garde un `Animator` et un `SceneGraph`
  (C-30) par assembly animée. `FORGET` l'oublie, et le déchargement de son asset l'emporte. Changer
  d'asset la recrée.
- **`AnimCommand`, 40 octets.** Elle porte `tick f64`, action, couche, clip, poids, fondu en secondes,
  vitesse, nombre de nodes de masque et un mot réservé ; les nodes du masque la suivent.
  Côté client, un `RenderAnimate` de 16 octets la précède : id, réservé, handle d'asset. Le serveur
  (3b) la portera dans son opcode. `axion_render_animate` valide le tampon entier avant d'appliquer
  quoi que ce soit ; une commande refusée ne change rien et est comptée.
- **`RENDER_IN` schéma 2.** Un en-tête de frame de 16 octets précède les candidats : le tick de rendu,
  puis 8 octets réservés. IF-05 garde sa signature (`float partial_tick`).
- **`RENDER_OUT` schéma 3.** L'en-tête passe à 24 octets (`matrix_total` et un mot réservé), et
  l'enregistrement à 28 octets (`matrix_first`, `u32::MAX` au repos). La table des matrices `mat4x3`
  suit celle des meshes. `palette_bytes` d'`AxionRenderResult` en porte la taille.
- **Côté Java.**
  - `LeveledDraws` substitue la matrice de chaque dessin, au mesh de son niveau. Le repère des corps
    se recalcule comme avant, depuis `draw.model()`.
  - Le tick de rendu est celui de `RenderClock` (ADR-150 D7).
  - Rien ne pousse encore de commande en jeu : le descripteur v3 les apportera à la tranche 4, et
    une assembly animée y prendra `NO_CULL`, son emprise de repos ne bornant plus ce qu'elle dessine.

### Tranche 3b — le serveur (2026-10-29)

- **L'horloge est le `tick` de `axion_sim_submit`.** Le paramètre était déjà dans la signature
  d'IF-03, et Java y passe `server.getTickCount()`. C'est le même compteur que celui des snapshots
  qui règlent l'horloge de rendu du client. Ni opcode d'horloge ni nouveau schéma du flux.
- **`CREATE_ASSEMBLY` porte les clips.** Le drapeau `ANIMATED` (bit 3) annonce, après l'état
  restauré, un `u32` de taille, un `u32` réservé, puis la section `ANIM` de l'asset ; `PHYS` reste
  alignée sur 8. Java joint `ANIM` dès que l'asset en a une : c'est le natif qui juge.
- **R-1430, jugé à la création.** Un collider dépend de l'animation si un node animé se trouve sur
  la chaîne qui va de son node porteur à la racine de son corps, racine exclue. Sans aucun collider
  dépendant, l'assembly n'a pas d'animation serveur, et ses commandes sont comptées sans effet
  (T-360).
- **R-930 et R-931.** Si une racine de corps secondaire ou l'un de ses ancêtres est animé, la physique
  l'emporte et l'animation serveur est abandonnée. Une section `ANIM` illisible ou refusée par C-22
  n'abandonne pas l'assembly.
- **`ANIMATE_ASSEMBLY`** (opcode 16) : `AnimateAssembly` (handle, `AnimCommand`, 48 octets), puis les
  nodes du masque. Il s'applique après les créations du même flux. `REMOVE_ASSEMBLY` oublie
  l'animation.
- **Étape 2.** Au début du `collect`, chaque assembly qui bouge est échantillonnée au tick du cycle.
  La pose de chacun de ses colliders dépendants est recomposée dans le repère de son corps, comme à
  la création, puis posée par `set_position_wrt_parent` ; rapier recalcule la masse au pas suivant.
  Une assembly au repos dont les colliders y sont déjà n'est pas échantillonnée.
- **Échelle.** L'échelle d'un node animé ne change pas la forme d'un collider, mise à l'échelle une
  fois à la création. Une échelle animée non uniforme laisse le collider à sa pose précédente
  (R-120).
- **Reste à faire.** L'étape 14 côté serveur — propagation pour les sockets — attend leur
  composant. L'API, les triggers et le descripteur v3 sont pour la tranche 4.

### Tranche 4 — décisions de Killian (2026-10-29)

Quatre questions, tranchées comme proposé :

- **`AnimationControl` reste interne en M4.** Il est implémenté et branché au réseau, mais seuls les
  tests, les GameTests et le banc de rendu l'appellent. Le fournisseur d'`AxionApi` vient en M9
  (ADR-137), et les interactions qui déclencheront une animation en M5 (C-53). La liste des
  commandes du §28 n'est pas touchée.
- **Le descripteur v3 porte la dernière commande de chaque couche** : clip, tick de début, temps de
  clip à ce tick, vitesse, poids, fondu. La section n'est envoyée que lorsqu'elle change, par la
  mécanique de delta du v2. Un joueur qui arrive au milieu d'un fondu le voit partir de la pose
  neutre ; tout le reste est exact.
- **`drives_joint` (R-932) suit le scénario de la porte** (M6, §18.5), avec ses déclencheurs. M4
  vérifie seulement que le joint nommé existe.
- **Pas de persistance en M4.** Le schéma NBT 3 est inchangé : après un rechargement, une assembly
  repart au repos. La question est à revoir en M5, avec les déclencheurs.

### Tranche 4 — le réseau et l'API (2026-10-29)

- **`AnimCommand` porte le temps de clip.** Le mot réservé, à l'octet 36, devient `origin` (`f32`) : le
  temps de clip à l'instant de la commande. Avec la vitesse, il permet de rejouer exactement un clip déjà
  en cours (`Animator::play_at`). La taille reste de 40 octets ; l'ABI reste la 10.
- **Descripteur v3.** Une section après les joints, sous le drapeau `ANIMATION` (64), donne un masque `u8`
  des couches non vides, puis, pour chacune : `clip + 1` (varuint, 0 pour une couche arrêtée), le tick
  (varulong), puis temps de clip, vitesse, poids et fondu (`f32`). Comme les joints, elle ne part que si
  elle a changé depuis la base du delta. Un masque au-delà de quatre couches, un clip au-delà de 127, un
  poids hors de [0, 1] ou un nombre non fini font refuser le message.
- **Une seule source de commandes.** `AnimationLayers.changesFrom` donne les commandes qui mènent d'un
  état à un autre, par tick croissant :
  - `PLAY` pour une couche qui joue autre chose ;
  - `STOP` pour une couche arrêtée, sauf depuis la couche vide ;
  - `SET_SPEED` pour une vitesse changée pendant un fondu d'entrée. La couche garde alors son tick et
    son fondu, son temps de clip y est ramené, et l'instant du changement se retrouve là où les deux
    temps de clip se rejoignent. Le fondu fini, un changement de vitesse repart du tick du changement,
    sans fondu, ce que `PLAY` rejoue exactement.

  Le serveur pousse ce diff à son natif (`ANIMATE_ASSEMBLY`), le client au sien
  (`axion_render_animate`) : les deux natifs reçoivent les mêmes commandes (R-1430). Un corps créé
  ou recréé, un client qui arrive, repartent de l'état vide et rejouent l'état entier.
- **`AnimationControl`** (`AssemblyAnimation`, côté serveur) :
  - ses clips sont ceux de la section `ANIM` de l'asset, posés à la création du corps. Un asset
    rechargé aux clips différents remet l'animation au repos ;
  - les refus sont ceux de D5, et R-1755 est vérifié par `AuthoritativeThread` ;
  - il reproduit le décompte de R-200 du natif — lecture refusée, ou fondu coupé —, ce qui lui demande
    le clip que chaque couche efface. Pour que ce décompte ne dépende que des commandes reçues,
    `Animator::play_at` clôt d'abord les fondus achevés de toutes les couches ; avant, un fondu fini
    comptait encore tant qu'aucune évaluation ne l'avait clos.
- **L'émetteur.** Une animation changée part sans attendre son échéance, même sur une assembly
  endormie à 2 Hz. Le format ne change pas. `netState()` porte toujours l'animation courante, même
  quand le natif ne rapporte plus l'état d'une assembly endormie.
- **Le client.** `AnimationSync` met en file le diff de chaque candidate, et ne le pousse au natif que
  lorsque le tick de rendu atteint le tick de chaque commande. Une assembly qu'aucune frame n'a vue
  depuis 64 frames reçoit `FORGET`. Une candidate dont une couche montre quelque chose est retenue
  `NO_CULL`.
- **Le réveil (R-1430).** rapier ne réveille pas un corps dont on repose un collider : sur une
  assembly endormie, le collider animé aurait traversé ce qu'il pousse. `set_collider_local` réveille
  désormais un corps endormi de lui-même, mais pas un corps suspendu par la gestion d'activité
  (ADR-153 D4). Le test de la tranche 3b, sur un corps cinématique qui ne dort jamais, ne pouvait pas
  le voir.
- **`ANIM` compressée.** Le compilateur compresse `ANIM` comme `GEOM` (tranche 1), et le serveur Java
  la lisait par `A3dSections`, qui refuse une section compressée. Le premier asset animé réel a fait
  lever `createBody`, et la garde du tick a avalé l'exception : tout le tick de simulation était
  sauté, sans ligne au journal. Désormais :
  - Java décompresse la section par le zstd du natif, la même fonction que celle des trames réseau
    (`axion_net_decompress`), bornée à la taille que l'entrée déclare. Aucun contrat ne change ;
  - une section illisible est tenue pour absente pour cette seule assembly, avec un avertissement
    par definition, et ne fait plus tomber le tick des autres.
- **`drives_joint`.** Le nom d'un joint est une catégorie interne (ADR-109) : un joint absent fait
  déjà refuser la definition dès sa lecture. Un test le prouve.
- **Le contenu.** `tools/assets/animation_essai.py` génère la glissière : un socle, et un coulisseau
  que le clip `glisse` pousse d'un bloc. Un GameTest la joue de bout en bout : refus hors du thread,
  collider et hitbox qui suivent, état reçu par un joueur simulé, arrêt. Le banc de rendu juge
  l'image, coulisseau poussé puis revenu.
- **Reste à faire.** Une assembly sans collider n'a pas de corps : elle n'a donc pas de snapshot, et
  son animation ne part pas. Le skinning est l'objet des tranches 5 et 6.

### Tranche 5 — décisions de Killian (2026-10-29)

Deux questions, tranchées comme proposé :

- **`RENDER_OUT` schéma 4.** L'enregistrement d'un retenu passe de 28 à 32 octets avec `palette_first` :
  le rang de la première matrice de sa palette dans la table des matrices, `u32::MAX` sans palette. Les
  palettes suivent les matrices des dessins dans la même table `mat4x3`. Java pose `palette_offset` dans
  le bloc d'instance (R-780) sans rien déduire.
- **T-908, la partie skinning dès la tranche 5.** Le test compare le skinning du shader à un skinning CPU
  de référence. La déformation, et l'ordre skinning puis déformation (R-792), s'y ajoutent en M6, avec
  C-28 et C-29.

Ce que la spécification tranche sans question :

- **L'espace de la palette** est celui de l'asset : `monde(node de l'os) × liaison inverse`. glTF ignore la
  transformation du node d'un mesh skinné ; le dessin skinné ne passe donc pas par sa matrice de dessin.
- **Le repli UBO** ne sert que si le TBO manque (H-04, R-790) : il fait partie du cœur de GL 3.1, que le
  backend natif dépasse. Aucune clé de configuration ne le force. Le banc le force par une bascule de
  développement, comme le chemin indirect, pour T-541.
- **R-791** : la description de `render.max_skinned_instances` disait « par squelette » ; le cahier des
  charges fixe un plafond global d'instances skinnées, et elle est corrigée en ce sens.

### Tranche 5 — précisions (2026-10-29)

- **5a, la palette native.** `SKEL` se lit avec `ANIM`. Un os qui désigne un node absent, ou dont la
  liaison inverse n'est pas finie et affine (dernière ligne `(0, 0, 0, 1)` à 1e-5 près), refuse la table :
  l'asset se rend au repos. `Instance::palette` lit la pose que `draw_matrices` vient d'évaluer.
- **5b, `RENDER_OUT` schéma 4.**
  - L'enregistrement fait 32 octets, `palette_first` à l'octet 28 ; la palette d'un retenu suit les
    matrices de ses dessins dans la table, un `mat4x3` par os dans l'ordre de `SKEL`.
  - Le mot réservé de l'en-tête, à l'octet 20, porte les retenus skinnés que le plafond a laissés au
    repos dans la frame. `AxionRenderResult` ne change pas.
- **R-791.** Le natif retient `render.max_skinned_instances` à l'ouverture de la session. Parmi les retenus
  skinnés — asset chargé, skinné et animé, assembly animée sur cet asset —, les plus proches reçoivent
  une palette, à égalité par `id` croissant ; les autres gardent leurs matrices de dessin animées, sans
  palette. Java publie `axion.render.skinned` (jauge, la dernière frame) et `axion.render.skinned_capped`
  (compteur).
- **5c, le skinning sur le GPU.**
  - `NativeCulling` remet la table des matrices au GPU avant de relâcher `RENDER_OUT`, depuis la vue directe
    du tampon : Java ne la copie pas (R-1460). Le TBO est en `GL_RGBA32F`, trois texels par `mat4x3`.
  - Le repli UBO (H-04) lit la palette dans une page de 16 Kio, le minimum garanti d'un bloc d'uniformes.
    Chaque dessin lie la page qui commence au plus près avant sa palette, à l'alignement du pilote ; il sert
    aussi quand la table dépasse ce que le TBO adresse. Le chemin se choisit par un uniforme : la liste des
    définitions de R-762 reste fermée.
  - `palette_offset` (R-780) porte le premier `vec4` de la palette de l'instance. Un dessin skinné ne
    s'instancie qu'avec un dessin skinné, et jamais sous le repli UBO.
  - Une variante s'applique désormais aux sommets comme aux fragments. L'émission a ses variantes : elle
    partage les sommets de la surface (`invariant gl_Position`).
  - Un mesh skinné qui reçoit une palette se pose à la racine de l'assembly, sans sa matrice de dessin, que
    glTF ignore. Sans palette — au-delà du plafond, ou tant que la variante compile —, il se dessine au
    repos.
  - Le banc de rendu natif juge le bras skinné de `tools/assets/animation_essai.py` :
    - T-908, partie skinning : la silhouette tient dans la boîte projetée des sommets skinnés sur le CPU, à
      0 pixel d'écart au passage du 2026-10-29 ;
    - T-541 : même image en TBO et en UBO ;
    - T-542 : 64 skinnés sur 65, et le compteur monte.

    Ces étapes se jouent après T-492, dont T-905 réécrit tout le cache des shaders.
  - Le backend vanilla dessine encore un mesh skinné au repos : le skinning sur le CPU est l'objet de la
    tranche 6 (R-742).

### Tranche 6 — décisions de Killian (2026-10-29)

Deux questions, tranchées comme proposé :

- **Les overlays `bones`, `nodes` et `pivots` viennent du natif.** Une fonction d'ABI 11,
  `axion_render_debug`, remplit des segments `DEBUG` (schéma existant) depuis les instances animées du
  contexte de rendu : les os (du parent à l'enfant), les nodes (leur repère), les pivots (un point). Java
  les dessine comme les autres overlays. Overlays éteints, rien ne coûte.
- **Le skinning du backend vanilla se fait en Java, à l'émission des sommets** (R-742). Pour ce backend,
  le culling lit les palettes dans `RENDER_OUT` : c'est une copie Java, bornée par
  `render.vanilla_max_skinned_vertices`. Au-delà du plafond, les instances les plus lointaines restent au
  repos, avec métrique.

### Tranche 6a — le skinning du backend vanilla (2026-10-29)

- **Les palettes.** `GeometryTransfer` lit les os et les poids d'un sommet dans le transfert reçu (octets 32
  et 36), sans tableau de plus. Sans table GPU qui les reçoive, `NativeCulling` copie la palette de chaque
  retenu skinné depuis `RENDER_OUT` : elle va de `palette_first` aux matrices du retenu animé suivant, ou à
  la fin de la table.
- **Le calcul.** `CpuSkinning` reprend celui du shader natif : la somme pondérée des matrices des quatre
  os, la position par la matrice entière, la normale par sa partie 3×3, renormalisée à l'émission. Chaque
  mesh se skinne une fois par frame et par instance : la surface et l'émission partagent ses sommets. Un
  mesh skinné se pose à la racine de l'assembly, sans sa matrice de dessin, comme au natif.
- **Le plafond (R-742).** `render.vanilla_max_skinned_vertices` se lit au choix du backend. Les retenus
  dotés d'une palette — au plus `render.max_skinned_instances` : le vanilla porte les mêmes budgets, avec
  des plafonds plus bas (fiche 5.48) — se prennent par distance croissante, celle du natif, à égalité dans
  l'ordre des candidats. Le premier qui ferait dépasser le plafond reste au repos, et tous les plus
  lointains avec lui : jamais un lointain animé quand un plus proche ne l'est pas. Un retenu compte les
  sommets de ses meshes skinnés et visibles, chacun une fois.
- **Les métriques.** `axion.render.vanilla_skinned_vertices` (jauge, la dernière frame) et
  `axion.render.vanilla_skinned_capped` (compteur). Au vanilla, `axion.render.skinned` compte les retenus
  skinnés sur le CPU.
- **La matrice des capacités (R-1493).** Elle dit désormais le skinning livré dans chaque backend, sur le
  CPU ou sur le GPU, avec son plafond ; la capacité reste « pas encore livrée » tant que la déformation
  manque (M6, C-68). Depuis la 5c, le natif l'annonçait encore entière à venir.
- **Le banc vanilla** joue le bras de la 5c, au passage du 2026-10-29 :
  - R-742 : la silhouette du bras plié skinné sur le CPU tient dans la boîte projetée de la référence, à
    0 pixel d'écart ;
  - T-493, partie skinning (ADR-128) : le plafond est abaissé à 400 sommets pour le banc. Un bras en
    skinne 32 ; sur 65 bras pliés, 12 le sont sur le CPU (384 sommets), et le compteur monte de 104 au
    relevé. La part de déformation de T-493 reste à la M6.

  Le banc natif reste vert, ses étapes du bras désormais partagées avec le vanilla. 11 mutations unitaires
  rouges (poids, translation, normale, plage du mesh, cache, compte, ordre, plafond, fin de palette, octet
  des poids) ; 3 au banc vanilla (sommets du repos émis, plafond ignoré, laissés au repos non comptés).

### Tranche 6b — décisions de Killian (2026-10-29)

Le tampon `DEBUG` vit dans le pool de la session, les instances animées dans le contexte de rendu, qui a son
pool et son verrou (ADR-154 D2). Deux questions, tranchées comme proposé :

- **Un tampon `RENDER_DEBUG`**, au pool du contexte de rendu et au schéma 2 de `DEBUG`, reçoit les segments
  des overlays `bones`, `nodes` et `pivots`. L'appel ne prend jamais le verrou de session : la frame
  n'attend pas le pas physique. Un type de tampon de plus (IF-02).
- **Le repère d'origine, sans handle.** Les segments sont relatifs à la caméra de la frame, calculés depuis
  la pose que `RENDER_IN` a donnée à chaque candidat ; chaque plage porte le handle `ABSENT`, comme une
  tuile du monde. Java n'a rien à retrouver, et les lignes tombent sur le maillage de la frame.

### Tranche 6b — les overlays de l'animation (2026-10-29)

- **ABI 11.**
  - `BufferKind::RenderDebug` = 15, au schéma 2 de `DEBUG`, routé vers le pool du contexte de rendu.
  - `axion_render_debug(ctx, overlay_mask, max_segments, out_size)` refuse `E-2002` un masque vide, ou qui
    porte un overlay que le rendu ne trace pas. Ces overlays sont `bones`, `nodes` et `pivots`, bits 10 à 12,
    leurs rangs au §31.4.
- **La pose.**
  - `prepare` retient l'`id`, la position, l'orientation et l'échelle de chaque retenu animé de la frame.
  - Les segments en sont tirés après la libération de la frame : le graphe de l'instance porte encore la
    pose qu'elle vient d'évaluer.
  - Les plages sont triées par distance, à budget de segments, comme celles de la physique
    (`select_drafts`).
- **Les overlays.**
  - `bones` relie chaque os à son os parent, celui que `SKEL` porte : le compilateur l'a relevé comme le
    plus proche ancêtre du node qui soit un os (DM-10). Un os parent hors du squelette refuse la table au
    chargement.
  - `nodes` trace trois axes de 0,25 bloc par node, échelle du node comprise.
  - `pivots` trace une croix de 0,15 bloc à l'origine de chaque node animé.
- **Java.**
  - `DebugOverlays` range ses overlays par source : physique, rendu ou Java.
  - Les overlays du rendu se demandent à chaque frame, juste après le culling et sans le verrou de session.
    Ils se dessinent à travers les maillages (`AxionRenderTypes.XRAY_LINES`).
  - `NO_DEPTH_TEST` de vanilla ne coupe rien. Pour la fonction `GL_ALWAYS`, sa mise en place n'appelle
    rien : relevé dans le bytecode de Forge 47.4.23. Il suppose le test déjà coupé entre deux types, ce qu'il
    n'est plus après les particules. Le premier passage au banc le montrait : seul le bout d'un axe dépassait
    de la peau. Un état propre coupe le test à sa mise en place, en affirmant le thread de rendu (T-019).
- **Preuves.**
  - `tests/render_debug.rs` : les trois overlays, la pose relevée après la libération de la frame,
    l'orientation du candidat, le budget, les masques refusés, les seules poses de la dernière frame.
  - `tests/palette.rs` : un node intermédiaire non-os n'interrompt pas l'os parent.
  - Bancs vanilla et natif, le 2026-10-29 : sur le bras plié, une plage par overlay, et au milieu de l'os,
    dans la colonne, 9 pixels changés sur 9.
  - Mutations rouges : 11 natives, 2 Java, et 3 au banc vanilla — lignes testées en profondeur, overlays
    jamais demandés, géométrie relue dans `DEBUG`.

## Alternatives évaluées

- **Échantillonner en Java** :
  - avantage : aucune frontière nouvelle ;
  - écarté : contraire à R-1460 (palettes en natif, sans copie Java) et coûteux à chaque frame.
- **Animation locale au client**, le serveur n'envoyant que des triggers :
  - avantage : moins de trafic ;
  - écarté : deux clients divergent dès qu'un message se perd, et R-1430 demande au serveur la même pose
    quand un collider en dépend.
- **Clés quantifiées dès maintenant** :
  - avantage : des assets plus petits ;
  - écarté : il faudrait figer un format sans mesure.
- **Modèles de test faits dans Blender** :
  - avantage : plus réalistes ;
  - écarté : ils dépendent d'un outil externe et sont moins exacts pour juger une interpolation.
