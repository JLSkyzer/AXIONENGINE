# ADR-148 — Les messages d'une compilation remontent au journal du jeu par une fonction ajoutée à IF-06

- **Statut** : **accepté** — tranché par Killian le 2026-10-17 sur les trois points (canal, journal,
  échec), chacun selon la proposition : un contrat `IF-xx` ne se modifie pas sans lui (CDC §5).
- **Date** : 2026-10-17
- **Portée** : IF-06 (`axion_asset_diagnostics`, ajoutée) ; C-20 (étape 5 : « un asset FAILED est
  journalisé une fois ») ; C-21 (R-530, R-912) ; C-32 (formes signalées, R-551) ; R-261, R-263, R-280,
  R-313, INV-07
- **Proposé par** : Claude ; **ordonné par** : [ADR-137](ADR-137.md), amendement A1 (« par un ADR de frontière ») ;
  [ADR-146](ADR-146.md), colonne 4 de C-32

## Contexte

**Ce qui se perd, relevé dans le code au 2026-10-17.**

- Les avertissements d'une compilation sont des lignes de texte (`CompiledAsset.warnings`, `Vec<String>`,
  `ax-asset/src/compile.rs`), sans code : le CDC ne définit aucun code d'avertissement. Ils viennent de
  l'importeur (R-530, R-912), des matériaux (ADR-122), des options (ADR-135), de l'optimizer et des
  colliders (C-32, R-551, R-161).
- `axion_asset_poll` dépose l'A3D dans `ASSET_OUT` puis **oublie le travail**, avertissements compris
  (`ax-ffi/src/abi.rs`, branche `AssetJob::Done`). Seule la CLI les affiche.
- Sur échec, la session ne garde que le code (`context.rs`, `AssetJob::Failed(code)`) : le message de
  `CompileError` — quelle extension est exigée, quel champ est incohérent — n'atteint pas Java non plus.
- Côté Java, `AssetRegistry` consigne ses diagnostics dans une liste que `AxionRuntime` recopie dans le
  journal **à la seule barrière de démarrage**. Après `/axion assets reload` ou un rechargement de
  ressources, un asset refusé n'est plus journalisé : il n'apparaît que dans `/axion status`. L'étape 5
  de C-20 n'est donc tenue qu'au démarrage.
- Aucun canal de journal ne va du natif vers Java ; INV-07 et R-313 interdisent tout rappel.

**Ce qu'A1 demande.** Une source qui provoque un avertissement connu le fait apparaître dans le journal
du jeu, une fois par compilation.

## Décision

### D1. Canal : une fonction ajoutée à IF-06

```c
int32_t axion_asset_diagnostics(uint64_t ctx, uint32_t job_id, uint64_t* out_size);
```

- Le sondage qui rend `COMPILED` ou `FAILED` **retient** les lignes du travail dans la session au lieu
  de les détruire avec lui. `axion_asset_diagnostics` les dépose dans `ASSET_OUT`, rend leur taille dans
  `out_size`, puis les oublie.
- **Format** : celui de la liste `NEEDS_FILES` (ADR-139) — `u32` du nombre, puis par ligne `u32` de sa
  longueur et ses octets UTF-8 (R-263), petit-boutiste. Java le lit déjà (`decodeNames`).
- **Aucune ligne** : `out_size` vaut 0 et `ASSET_OUT` n'est pas touché. `ASSET_OUT` porte ce que la
  dernière fonction y a écrit, comme pour `geometry`, `materials` et `texture` : Java lit l'A3D du
  sondage **avant** d'appeler.
- **Codes** : `AXION_OK` ; `E-2001` si `job_id` ne désigne pas un travail sondé dont les lignes attendent —
  jamais sondé, encore en cours, déjà lu ou abandonné ; `E-2002` si `ASSET_OUT` ne peut pas les contenir,
  les lignes étant alors oubliées.
- **Rétention bornée** : du sondage à la lecture. `axion_asset_cancel` (ADR-140) les libère aussi, et la
  fermeture du contexte avec le reste. Java lit juste après son sondage : la table ne tient que les
  travaux entre ces deux appels.
- L'appel ne bloque jamais (R-280), n'alloue rien côté Java et n'appelle pas Java (R-313, INV-07).
- Pont JNI : `NativeBridge.assetDiagnostics(long ctx, int jobId, long[] outSize)`, signature `(JI[J)I`.
- Métrique : `axion.asset.warnings`, le nombre d'avertissements des compilations finies (R-500).
- **`AXION_ABI_VERSION` reste 4** : une fonction ajoutée n'est pas une rupture (R-261 ; ADR-103, ADR-121,
  ADR-140).

### D2. Journal : chaque ligne une fois, au tick où la compilation finit

- `CompileStatus` porte les lignes du travail. `AssetRegistry` en fait une entrée par ligne,
  `<chemin> — avertissement : <texte>`, au sondage qui rend `COMPILED` — une fois par compilation, puisque
  ce sondage n'a lieu qu'une fois.
- Ces entrées, comme les refus déjà consignés par `fail`, vont dans un **journal vidé** sur le modèle de
  `SimulationJournal` : `dev.axion.forge` le journalise en `WARN` à la fin de chaque tick serveur, et la
  barrière de démarrage le vide par le même chemin, sans doublon. Les refus et avertissements d'un
  rechargement atteignent ainsi le journal. `diagnostics()` garde l'historique pour `/axion status`.
- Un asset repris du cache n'est pas compilé et ne dit rien : le cache ne garde que l'A3D. Le voir de
  nouveau, c'est recompiler : `/axion assets reload` recompile tout, cache compris, et
  `-Daxion.dev.asset_cache=false` recompile à chaque chargement.

### D3. Échec : le message de l'erreur voyage par le même chemin

Au sondage qui rend `FAILED`, la session retient le message de `CompileError`, une ligne, que la même
fonction rend. Le journal dit alors pourquoi l'asset est refusé, et pas seulement son code : il tient
l'étape 5 de C-20 avec son motif.

## Alternatives évaluées

- **Une quatrième case au sondage** (le nombre de lignes). Écartée : la signature de `axion_asset_poll`
  change, l'ABI passe à 5 ; or l'ABI entre dans la clé du cache d'assets, et chaque cache serait invalidé
  — une rupture pour rien qu'une fonction ajoutée ne donne pas.
- **Une section de l'A3D.** Écartée : `COMPILER_VERSION` monte, R-562 change ses empreintes, et
  l'avertissement voyage avec le cache — il serait répété à chaque reprise, et non une fois par
  compilation. ADR-108 a déjà laissé l'avertissement de `max_decomp_ms` hors de l'A3D.
- **Un canal général de journal natif → Java** (un `BufferKind` de plus, vidé à chaque tick). Écartée
  pour M3 : R-441 place le journal natif dans `<gameDir>/axion/logs/`, pas dans celui du jeu ; un tel
  contrat n'aurait ici qu'un consommateur, qui a besoin de son travail de compilation de toute façon.
- **D3 seul sans D1** : `axion_last_error` ne garde qu'un message par session, que le suivant remplace ;
  deux compilations finies au même tick se l'écraseraient.

## Preuve attendue

- Natif, `asset_diagnostics_abi` : une source glTF qui déclare dans `extensionsUsed` une extension non
  prise en charge (R-530) compile ; la fonction rend la ligne « extension ignorée » ; un second appel rend
  `E-2001` ; l'abandon libère ; un échec rend son message ; aucune ligne laisse `ASSET_OUT` intact.
- Java : `NativeBridgeTest` par la vraie JNI ; `AssetRegistryTest` — une ligne par avertissement, une
  fois par compilation, aussi après un rechargement.
- En jeu, GameTest : la même source, dans un pack de test, met sa ligne dans le journal vidé une fois par
  compilation.
- Mutations sur la rétention, l'oubli après lecture et l'unicité.

## Mise en œuvre (2026-10-17)

- **Natif.** `AssetJob` gagne l'état `Diagnostics` : le sondage qui rend `COMPILED` ou `FAILED` y laisse
  le travail avec ses lignes, au lieu de l'oublier. La table, l'abandon d'ADR-140 et la fermeture du
  contexte couvrent donc les lignes sans code de plus. Un échec garde son message (`CompileError`
  l'écrit) ; un travail annulé ou paniqué, un message qui le dit. Un A3D qui ne tient pas dans
  `ASSET_OUT` rend `FAILED` avec une ligne qui le dit, plutôt que ses avertissements.
- **ADR-140 précisé** : abandonner un travail sondé dont les lignes attendent rend `AXION_OK` et les
  libère ; `E-2001` ne vient qu'une fois les lignes lues. `asset_cancel_abi` le vérifie.
- **Java.** `CompileStatus` porte les lignes ; `NativeAssetCompiler` lit l'A3D, puis les lignes, et
  signale par une ligne des lignes non rendues ou illisibles. `AssetRegistry.drainJournal()` rend, une
  fois, ce que le registre et le cache ont consigné ; `AxionForgeEntrypoint` le journalise en `WARN`
  après la barrière et à la fin de chaque tick serveur. La barrière ne recopie plus les diagnostics dans
  les transitions.
- **Preuve en jeu.** `test/avertissement/triangle.gltf` (devcontent) déclenche R-530 ;
  `JournalDesAssetsGameTests` vérifie qu'il est consigné une fois, et l'étape « Avertissement de
  compilation au journal (ADR-148) » de `test-gametest` le compte dans `latest.log`
  (`tools/ci/gametest_journal.py`, rejouée par `local_ci.py`). `runGameTestServer` efface désormais le
  cache d'assets avant chaque passage, comme le banc de rendu : sans cela, un second passage local
  reprendrait l'asset du cache et ne compilerait rien.
- **Tests** : `asset_diagnostics_abi` (natif), `asset_cancel_abi` mis à jour, `NativeBridgeTest` (vraie
  JNI : motif d'un refus d'option, avertissement R-530), `AssetRegistryTest` (trois tests : une fois par
  compilation, motif d'un refus après rechargement, soucis du cache). 13 mutations rouges. Les deux
  appels de la couche Forge se couvrent l'un l'autre au démarrage : seul leur retrait conjoint fait
  échouer l'étape de CI ; le journal d'un rechargement repose sur `drainJournal`, que
  `AssetRegistryTest` vérifie.

## Conséquences

- La ligne C-32 de la colonne 4 d'ADR-146 se fait par cet ADR, une fois accepté.
- Un avertissement reste un texte : s'il faut un jour le filtrer ou le traduire, un code
  d'avertissement demandera son propre ADR et une entrée en ANNEXE A.1.
