## Contexte

Le backend vanilla dessine aujourd'hui chaque assembly en blanc : une texture neutre de 16×16,
aucune couleur de matériau, aucune transparence. C-26 (textures et matériaux côté client) est la
pièce qui manque pour que les modèles de l'auteur — exportés de Blender — apparaissent tels
qu'il les a faits.

### Ce que le CDC fixe

- **C-26** (5.19) : textures = `ResourceLocation` classiques chargées par le `TextureManager`
  (PNG) ; textures embarquées d'un GLB extraites à la compilation vers le cache et enregistrées
  comme `DynamicTexture` ; atlas AXION dédié pour les textures ≤ 256×256, texture individuelle
  au-delà ; slots par matériau albedo, normal, ORM, émissive, height, damage ; slot absent →
  texture neutre 1×1 ; atlas de décalques séparé. **R-570** : 4096×4096 au plus (`E-3006`),
  mipmapping activé, anisotropie selon le réglage vanilla. **R-571** : l'atlas de blocs vanilla
  n'est jamais modifié.
- **DM-05** (§3.5) : `MaterialDesc` `repr(C)` — 6 slots `u16`, facteurs, `blend_mode`
  (OPAQUE, CUTOUT, TRANSLUCENT), `cull_mode` (BACK, NONE), `shading_model`, drapeaux
  `VERTEX_COLOR`, `TINTABLE`, `FULLBRIGHT`, `WEAR_ENABLED`, `DECAL_RECEIVER`. **R-150** :
  TRANSLUCENT implique tri par distance. **DM-04** : `MeshDesc.material: u16`.
- **§7.3** : `MATL` = `MaterialDesc[]` ; `TEXR` = « table de `ResourceLocation` + textures
  extraites » ; sections du client seulement (**R-041** : le serveur les ignore). **R-880** : un
  lecteur ignore un tag inconnu ; **R-893** : toute évolution de format a son test de migration
  et un fichier de l'ancienne version dans `tests/fixtures/a3d/`.
- **C-21** : glTF strict, « aucun URI externe ni chemin remontant », « une primitive = un mesh » ;
  **R-530** : extensions admises (dont `KHR_texture_transform`, `KHR_materials_unlit`,
  `KHR_materials_emissive_strength`, clearcoat, sheen, anisotropy, ior, specular) ; **R-531** :
  aucun chemin absolu ni sortie du répertoire de l'asset (`E-3002`) ; **R-532** : images
  extraites mais **non décodées** par l'importeur, décodage par le `ResourceManager`, **PNG
  uniquement** (`E-3004` sinon). §6.5 : « un matériau par primitive », « textures PNG, puissance
  de deux, ≤ 2048×2048 recommandé ».
- **R-142** : « UV ramenés dans `[0,1]` par l'optimizer ; hors `[-8,9]` avant normalisation =
  `E-3030` ».
- **R-1513** : le backend vanilla emploie `VANILLA_COMPAT` — « albedo × lightmap, avec une
  modulation douce par la normale et l'émissive » ; pas de PBR, faute d'entrées dans les
  `RenderType` vanilla. **R-1570** : passes opaque, cutout et émissive à `AFTER_ENTITIES`,
  translucide à `AFTER_TRANSLUCENT_BLOCKS`. **R-1581** : pas de tri intra-mesh exigé.
  **R-741** : aucun appel OpenGL direct dans le backend vanilla. **R-752** : changement de
  resource pack → libération et reconstruction complètes.

Le CDC **ne fixe pas** : la disposition de `TEXR` ; le lien entre un slot et une entrée de
`TEXR` ; la correspondance glTF → DM-05 ; l'algorithme de normalisation des UV ; le filtrage
(plus proche ou linéaire) ; le rendu vanilla de l'émissive, de `UNLIT` et d'`alpha_cutoff` ;
l'espace de couleur des facteurs. Les tests T-270..T-273 ne sont décrits nulle part, et T-870
est attribué à la fois à C-26 et à C-47 (l'atlas de décalques est T-915).

### Ce que la lecture du code a établi

1. **`MATL` est provisoire et personne ne le lit** : un compte, puis par matériau une couleur et
   une chaîne de chemin (`compile.rs`, `materials_bytes`). `TEXR` n'est jamais écrite. Aucune
   image n'est lue : une image de `bufferView` est oubliée, un URI `data:` est gardé comme chaîne.
2. **DM-05 n'existe pas dans le code.** Les drapeaux de mesh `TRANSPARENT` et `DOUBLE_SIDED` ne
   sont posés par aucun importeur. Une primitive sans matériau prend l'index 0, qu'un autre
   matériau occupe peut-être ; aucun contrôle ne borne l'index.
3. **R-142 n'est pas implémentée.** Les deux importeurs écrêtent les UV dans `[0,1]`
   (`quantize_uv`) ; aucun optimizer ne les normalise. Une texture répétée — sol, chenille,
   pneu — est donc écrasée en silence, ce que l'arrivée des textures rendra visible.
4. **Un mesh glTF à plusieurs primitives n'affiche que la première.** `NodeDesc` ne porte qu'un
   `mesh` ; `bind_meshes` y met la première primitive ; les suivantes sont compilées mais jamais
   dessinées, ni comptées dans les bornes, ni dotées de LOD. Comme glTF découpe un mesh **par
   matériau**, tout modèle multi-matériau n'apparaît qu'en partie. ADR-119 l'avait nommé hors
   portée (« correctif séparé avec `COMPILER_VERSION` »).
5. **La compilation en jeu ne lit aucun fichier voisin** (`compile(&source, …, |_| None)`) :
   ni `.mtl`, ni buffer `.bin` externe, ni image. Le serveur ne découvre que
   `data/<ns>/axion/models/**` et seulement `.glb/.gltf/.obj/.stl`. La CLI, elle, résout les
   voisins.
6. **Transfert d'ADR-119** : chaque `MeshDesc` voyage avec son index de matériau, pas la table
   des matériaux. `ASSET_OUT` est au schéma 0 et Java ne le vérifie pas.
7. **Côté Java** : une seule texture blanche, `entitySolid` et `entityCutoutNoCull` ; les meshes
   `TRANSPARENT` sont sautés.

### Ce que Minecraft 1.20.1 / Forge 47.4.23 impose (bytecode, shaders et jar lus)

1. **Les `RenderType` d'entité vanilla forcent le filtrage au plus proche, sans mipmap**, à
   chaque dessin : leur `TextureStateShard(rl, false, false)` appelle `setFilter(false, false)`.
   Mipmaps (R-570) et filtrage linéaire exigent donc des `RenderType` propres — composés des
   shaders vanilla (`RENDERTYPE_ENTITY_*_SHADER`, champs `protected` atteints par une sous-classe
   de `RenderType`) avec `TextureStateShard(rl, flou, true)`. Aucun appel GL direct, aucun shader
   propre (R-741).
2. **Seuils de découpe** : les shaders `entity_cutout`, `entity_cutout_no_cull` et
   `entity_translucent` rejettent un texel d'alpha < 0,1 **avant** la couleur de sommet ;
   `entity_translucent_cull` teste l'alpha final ; `entity_solid` et `eyes` ne rejettent rien.
   La couleur de sommet multiplie la texture partout ; l'ombrage directionnel
   (`minecraft_mix_light`) s'y applique, sauf dans `eyes`, qui ignore aussi la lightmap et
   s'additionne (`ONE, ONE`).
3. **`NativeImage.read` n'est pas limité au PNG** : il décode tout ce que décode STB (PNG, JPEG,
   BMP, GIF vérifiés). La règle « PNG uniquement » de R-532 se vérifie donc à part, sur la
   signature.
4. **Mipmaps** : `TextureUtil.prepareImage(id, niveaux, l, h)` puis
   `NativeImage.upload(niveau, …)` par niveau, niveaux produits par
   `MipmapGenerator.generateMipLevels` — la recette de l'atlas vanilla. Réglage vanilla :
   `mipmapLevels` (0 à 4). **Aucune anisotropie** dans le jeu ni dans ses options.
5. **Tri des translucides** : par quad, du plus loin au plus près, clé = milieu des sommets 0 et
   2 ; pour un triangle dessiné en quad dégénéré `(a, b, c, c)`, la clé est le milieu de `a–c`.
   Le tri ne vaut qu'au sein d'un lot.
6. **`AFTER_TRANSLUCENT_BLOCKS`** est émis pendant le dessin du terrain translucide : sous
   « Fabulous », la cible translucide est liée. Ce qui y est dessiné doit être vidé dans le
   gestionnaire même pour entrer dans la composition.
7. **Fils** : décodage d'image et génération de mipmaps hors du fil de rendu ; allocation et
   téléversement sur le fil de rendu. Au rechargement de ressources, le `TextureManager`
   recharge les textures qui savent se recharger ; une texture dont `load` ne fait rien survit
   telle quelle.

## Décision proposée

### 1. `MaterialDesc` (DM-05) et section `MATL`

`MaterialDesc` est transcrit **tel quel** du CDC dans `ax-model` (`dm/material.rs`), 96 octets,
petit-boutiste, figé par un test de disposition :

```text
0  u64 name_hash          empreinte FNV-1a 64 du nom (comme les nodes)
8  u16 albedo_tex, 10 normal_tex, 12 orm_tex, 14 emissive_tex, 16 height_tex, 18 damage_tex
20 f32 albedo_factor[4]   36 f32 emissive_factor[3]
48 f32 metallic, roughness, occlusion_strength, normal_scale, alpha_cutoff, parallax_scale,
       clearcoat, clearcoat_roughness, sheen, anisotropy          (jusqu'à 88)
88 u8  blend_mode   OPAQUE = 0, CUTOUT = 1, TRANSLUCENT = 2
89 u8  cull_mode    BACK = 0, NONE = 1
90 u8  shading_model PBR = 0, PBR_CLEARCOAT = 1, PBR_SHEEN = 2, UNLIT = 3, VANILLA_COMPAT = 4
91 u8  _pad
92 u16 flags        VERTEX_COLOR = 1, TINTABLE = 2, FULLBRIGHT = 4, WEAR_ENABLED = 8,
                    DECAL_RECEIVER = 16
94 u16 wear_profile u16::MAX = aucun                              total 96
```

- **Slot absent = `u16::MAX`** pour les six slots (le CDC ne l'écrit que pour `height_tex`) ;
  sinon, index dans la table de `TEXR`.
- **Facteurs en espace linéaire**, comme glTF. La conversion pour un rendu non linéaire revient au
  backend qui dessine (§7).
- Section `MATL` : en-tête de 16 o `u32 material_count, u32 layout = 1, u32 0, u32 0`, puis
  `MaterialDesc[material_count]`, non compressée. Un `layout` inconnu — c'est le cas de l'ancien
  `MATL` provisoire, dont le second mot est le rouge d'une couleur — est **ignoré avec
  avertissement** (esprit de R-880) : l'asset reste chargeable, avec le matériau par défaut.

### 2. Section `TEXR`

```text
offset 0   u32 texture_count
       4   u32 layout = 1
       8   u32 blob_size
       12  u32 0
       16  TextureDesc[texture_count]   16 o chacun
           u8 blob[blob_size]            octets PNG embarqués et chemins relatifs (UTF-8)
```

```rust
#[repr(C)]
pub struct TextureDesc {
    pub source: u8,       // 0   EMBEDDED = 1 (PNG dans le blob) | RESOURCE = 2 (chemin relatif)
    pub format: u8,       // 1   PNG = 1, seul format admis (R-532)
    pub sampler: u8,      // 2   bits 0-1 filtrage : 0 non déclaré, 1 plus proche, 2 linéaire ;
                          //     bit 2 CLAMP_U ; bit 3 CLAMP_V (répétition sinon)
    pub _pad: u8,         // 3
    pub width: u16,       // 4   lus dans l'IHDR (EMBEDDED) ; 0 si inconnus (RESOURCE)
    pub height: u16,      // 6
    pub data_offset: u32, // 8   dans le blob
    pub data_size: u32,   // 12  total 16
}
```

- Une entrée de `TEXR` est un couple **(image, échantillonneur)** — une « texture » glTF. Deux
  entrées partageant une image partagent ses octets dans le blob.
- **EMBEDDED** : image de `bufferView` ou URI `data:` ; octets copiés **sans décodage**
  (R-532). L'importeur lit seulement la signature PNG et l'en-tête IHDR : signature absente →
  texture refusée `E-3004` ; côté > 4096 → refusée `E-3006`. Une texture refusée ne bloque pas
  l'asset : ses slots deviennent `u16::MAX` (texture neutre), avec un diagnostic de
  compilation.
- **RESOURCE** : chemin relatif d'un URI glTF ou d'un `map_*` MTL, contrôlé par R-531 (ni
  absolu, ni remontée, ni antislash, ni lettre de lecteur). Le compilateur ne connaît pas
  l'emplacement du modèle ; **Java résout** le chemin contre le répertoire de la
  `ResourceLocation` du modèle : `ns:axion/models/voiture/voiture.gltf` + `tex/caisse.png` →
  `ns:axion/models/voiture/tex/caisse.png`, chargée des resource packs (`assets/…`) — donc
  remplaçable par un resource pack.

### 3. Import → `MaterialDesc` et `TextureDesc`

**glTF** :

| Source glTF | Destination |
|---|---|
| `pbrMetallicRoughness.baseColorFactor`, `baseColorTexture` | `albedo_factor`, `albedo_tex` |
| `metallicFactor`, `roughnessFactor`, `metallicRoughnessTexture` | `metallic`, `roughness`, `orm_tex` (`occlusionTexture` retenue si c'est la même image) |
| `normalTexture` (`scale`), `occlusionTexture` (`strength`) | `normal_tex`, `normal_scale`, `occlusion_strength` |
| `emissiveFactor` × `KHR_materials_emissive_strength`, `emissiveTexture` | `emissive_factor`, `emissive_tex` |
| `alphaMode` OPAQUE / MASK / BLEND, `alphaCutoff` | `blend_mode` OPAQUE / CUTOUT / TRANSLUCENT, `alpha_cutoff` |
| `doubleSided` | `cull_mode` NONE (sinon BACK) |
| `KHR_materials_unlit` | `shading_model` UNLIT |
| `KHR_materials_clearcoat` / `_sheen` / `_anisotropy` | champs du même nom, `shading_model` PBR_CLEARCOAT / PBR_SHEEN |
| `KHR_texture_transform` du slot albedo | **cuit dans `uv0`** à l'import ; un autre slot transformé autrement → avertissement |
| `KHR_materials_ior`, `_specular` | admis (R-530), sans champ DM-05 : ignorés avec avertissement |
| attribut `COLOR_0` d'une primitive | couleurs de sommet (aujourd'hui toujours blanches) et drapeau `VERTEX_COLOR` du matériau |
| échantillonneur `magFilter`, `wrapS`, `wrapT` | `TextureDesc.sampler` ; `MIRRORED_REPEAT` → répétition, avec avertissement |

- **Matériau par défaut** : une primitive sans matériau reçoit un matériau ajouté en fin de table,
  aux valeurs par défaut de glTF (blanc, OPAQUE, BACK). Un STL, ou un OBJ sans `.mtl`, reçoit le
  matériau par défaut des options de compilation (`materials.default_roughness`,
  `default_metallic`). `MeshDesc.material` est **toujours** un index valide.
- **Drapeaux de mesh** : `TRANSPARENT` et `DOUBLE_SIDED` sont recopiés du matériau
  (`blend_mode == TRANSLUCENT`, `cull_mode == NONE`) — le culling et le tri natifs (C-64), qui ne
  chargent pas `MATL`, les lisent dans `MeshDesc`. Le validateur vérifie la concordance.
- **OBJ / MTL** : `Kd` et `d` (ou `1 − Tr`) → `albedo_factor` (TRANSLUCENT si alpha < 1) ;
  `map_Kd` → texture RESOURCE ; `Ke` → `emissive_factor` ; `map_Bump`, `bump`, `norm` →
  `normal_tex` ; `Ns` → `roughness = √(2 / (Ns + 2))` — **corrigé en T-a2 :
  `(2 / (Ns + 2))^¼`**, voir « Précisions de T-a2 ». En jeu, le `.mtl` n'est pas lu
  (constat 5) : écart préexistant, hors portée, nommé.

### 4. UV : une plage de décodage par mesh (R-142)

`MeshDesc._pad: u16` devient **`uv0_range`** : octet bas `uv_min: i8` (borne entière inférieure,
commune à U et V), octet haut `uv_span: u8` (étendue entière, 1 à 17). Encodage
`q = round((u − uv_min) / uv_span × 65535)` ; décodage `u = uv_min + q / 65535 × uv_span`. La
plage est la plus petite plage entière qui contient les UV du mesh ; **0 = `[0,1]`**, la valeur
de tout asset déjà compilé.

- Les UV stockés restent dans `[0,1]` (R-142) et la répétition est conservée jusqu'à 17 tuiles ;
  hors `[-8, 9]`, `E-3030` comme aujourd'hui.
- Un mesh entièrement dans `[0,1]` garde la précision actuelle (1/65535) ; seul un mesh répété la
  divise par son étendue.
- `uv1` reste dans `[0,1]`. La fusion des sommets et les LOD conservent la plage de leur mesh.

### 5. Plusieurs primitives par node (DM-03)

`NodeDesc._pad: [u8; 2]` devient **`mesh_count: u16`** : le node porte les meshes
`mesh .. mesh + mesh_count`, consécutifs. **0 = 1** si `mesh != u32::MAX` — la lecture de tout
asset déjà compilé. L'importeur glTF y range toutes les primitives du mesh, dans leur ordre.

- La liste de dessin au repos (ADR-119) émet **un `RestDraw` par mesh** du node — même node, même
  transformation ; sa disposition est inchangée.
- Bornes de l'asset, génération des LOD et validateur (`mesh + mesh_count ≤ mesh_count` total)
  parcourent la plage.
- Taille du node inchangée (80 o) : la disposition ne bouge pas, seul le sens de la réserve.

### 6. Frontière (IF-06) : deux fonctions ajoutées

- `axion_asset_load` accepte désormais `NODE | GEOM | MATL | TEXR` (bits 0 à 3 du masque
  d'ADR-119) ; `MATL` et `TEXR` sont décodés au chargement, contrôlés, imputés à `PERSISTENT`.

```c
/* Dépose dans AXION_BUF_ASSET_OUT la table des matériaux et des textures d'un asset chargé
   avec MATL | TEXR. out_size reçoit la taille de la charge utile. */
int32_t axion_asset_materials(uint64_t ctx, AssetHandle h, uint64_t* out_size);

/* Dépose dans AXION_BUF_ASSET_OUT les octets PNG de la texture EMBEDDED de rang `texture`. */
int32_t axion_asset_texture(uint64_t ctx, AssetHandle h, uint32_t texture, uint64_t* out_size);
```

Charge utile de `axion_asset_materials` :

```text
offset 0   u32 material_count
       4   u32 texture_count
       8   u32 path_bytes
       12  u32 0
       16  MaterialDesc[material_count]   96 o, DM-05 tel quel
           TextureDesc[texture_count]     16 o ; RESOURCE : data_offset/size dans paths ;
                                                 EMBEDDED : data_offset = 0, data_size = taille du PNG
           u8 paths[path_bytes]           chemins relatifs, UTF-8
```

- Les octets d'une texture EMBEDDED ne voyagent que par `axion_asset_texture`, **une texture
  par appel** : une table de 128 textures de 4096² ne transite pas d'un bloc.
- **Garanties natives avant dépôt** : comptes ≤ plafonds (256 matériaux, 128 textures) ; slots
  `< texture_count` ou `u16::MAX` ; énumérations valides ; facteurs finis ; `alpha_cutoff` dans
  `[0,1]` ; plages de chemins dans `paths`. `texture` hors table, ou non EMBEDDED → `E-2002`.
- `ASSET_OUT` passe au **schéma 1** (`BufferKind::schema_version`, ADR-120) ; Java le vérifie
  avant toute lecture. La charge de géométrie d'ADR-119 est inchangée.
- **ABI inchangée (2)** : deux fonctions ajoutées (règle d'ADR-103). Pont JNI :
  `assetMaterials (JII[J)I` et `assetTexture (JIII[J)I`, sorties par `long[]` (R-313).

### 7. Côté client : textures et passes du backend vanilla

**Textures** (paquet `dev.axion.render`, logique pure ; collage Forge dans `forge.client`) :

- Chargées **en arrière-plan**, sur le thread des maillages : octets (FFI pour EMBEDDED,
  `ResourceManager` client pour RESOURCE) → contrôle de signature PNG (`E-3004`) →
  `NativeImage.read` → côtés ≤ 4096 (`E-3006`) → variante de découpe (ci-dessous) → mipmaps
  (`MipmapGenerator`, `min(mipmapLevels vanilla, log2(min(l, h)))` niveaux).
  **Téléversement sur le fil de rendu** dans une sous-classe d'`AbstractTexture` dont `load` ne
  fait rien, enregistrée sous `axion:texture/<asset>/<rang>`.
- Échec ou absence → texture neutre (albedo blanc 1×1), diagnostic **une fois** par texture.
- Libération à la sortie du monde, au rechargement de ressources (**R-752** : écouteur client,
  tout est rendu puis reconstruit à la demande) et à l'arrêt du natif.
- **Filtrage** : celui de la source (échantillonneur glTF, `blur` d'un `.mcmeta` pour RESOURCE),
  sinon la valeur par défaut ratifiée (question 4). **Anisotropie : aucune**, Minecraft n'en
  offrant pas (R-570 « selon le réglage vanilla »).

**`RenderType` propres** (`AxionRenderTypes extends RenderType`, mémorisés par
(texture, mode, culling, filtrage)), format `NEW_ENTITY`, quads :

| Matériau | Shader vanilla | Mélange | Culling | Profondeur | Stage (R-1570) |
|---|---|---|---|---|---|
| OPAQUE | `entity_solid` | aucun | BACK ou NONE | écrite | `AFTER_ENTITIES` |
| CUTOUT | `entity_cutout` / `entity_cutout_no_cull` | aucun | BACK / NONE | écrite | `AFTER_ENTITIES` |
| TRANSLUCENT | `entity_translucent_cull` / `entity_translucent` | alpha, tri par quad | BACK / NONE | écrite | `AFTER_TRANSLUCENT_BLOCKS`, vidé dans le gestionnaire |
| émissive (passe 5) | `eyes` | additif | BACK / NONE | non écrite | `AFTER_ENTITIES`, après l'opaque |

- **Couleur de sommet** = `albedo_factor` × couleur du sommet si `VERTEX_COLOR`, ramenées de
  l'espace linéaire à l'espace gamma du rendu vanilla (puissance 1/2,2 sur RVB, alpha linéaire),
  calculées une fois par paire (mesh, matériau).
- **`alpha_cutoff`** : le shader vanilla coupe à 0,1 sur l'alpha du texel. La variante CUTOUT
  d'une texture binarise son alpha au seuil `alpha_cutoff / albedo_factor.a` au chargement : la
  coupe vanilla tombe alors exactement au seuil du matériau. L'alpha de sommet est sans effet en
  CUTOUT (différence déclarée).
- **Émissive** : si `emissive_factor` ≠ 0, second dessin en passe 5 avec `emissive_tex` (texture
  blanche si absente, sémantique glTF), couleur = `emissive_factor` ramené en gamma comme
  l'albedo et borné à 1 — une intensité supérieure (`KHR_materials_emissive_strength`) est
  plafonnée (déclaré).
- **`UNLIT` et `FULLBRIGHT`** : lightmap pleine (`LightTexture.FULL_BRIGHT`) ; l'ombrage
  directionnel des shaders d'entité demeure (approximation déclarée).
- Normal, ORM, height, damage : **sans effet en vanilla** (R-1513), déclarés dans la matrice de
  capacités (R-1493).

### 8. Validation (C-22) et version du compilateur

- ≤ 256 matériaux, **≤ 128 textures** (le compte est aujourd'hui toujours 0) ; slots, index de
  matériau des meshes, plages `mesh_count` et `uv0_range` contrôlés ; écart → `E-3050`.
- `COMPILER_VERSION` → **7**, des deux côtés (R-562). Tests de migration (R-893) : un fichier
  produit par le compilateur 6 (ancien `MATL`, réserves nulles) dans `tests/fixtures/a3d/` se lit
  avec le matériau par défaut, des UV `[0,1]` et un mesh par node.
- Tests de C-26 proposés pour T-270..T-273, que le CDC ne décrit pas : **T-270** disposition et
  aller-retour `MATL`/`TEXR` ; **T-271** correspondance glTF/OBJ → DM-05 ; **T-272** chargement
  des textures (PNG seul, ≤ 4096, texture neutre, mipmaps) ; **T-273** passes et `RenderType` par
  mode de mélange et de culling.

## Alternatives évaluées

- **Java lit `MATL` et `TEXR` lui-même.** Rejeté : `GEOM` est compressée et Java ne décompresse
  pas ; surtout, le format A3D appartient à Rust (ADR-118, ADR-119) — le dupliquer en Java
  ferait deux lecteurs à garder d'accord.
- **Octets PNG dans la charge de `axion_asset_materials`.** Rejeté : jusqu'à 128 textures de
  4096² d'un bloc, pour un chargement qui veut avancer texture par texture.
- **Embarquer aussi les textures RESOURCE à la compilation.** Rejeté : C-26 veut des
  `ResourceLocation` chargées par le `TextureManager`, remplaçables par un resource pack ; et la
  compilation en jeu ne lit pas les fichiers voisins (constat 5).
- **`RenderType` d'entité vanilla tels quels.** Rejeté : ils imposent le plus proche sans
  mipmap à chaque dessin, contraire à R-570.
- **Shader propre pour `alpha_cutoff` et `UNLIT` exacts.** Rejeté : contraire à l'esprit de
  R-741 et remplacé par les shaderpacks ; la binarisation de l'alpha rend la coupe exacte sans
  shader.
- **UV : plage fixe `[-8, 9]` pour tout asset.** Simple, mais divise par 17 la précision de
  tous les meshes ; la plage par mesh ne la paie que là où la répétition existe.
- **UV : rester dans `[0,1]` et refuser au-delà.** Plus de répétition : un sol carrelé
  demanderait une géométrie découpée par l'auteur.
- **UV : découper la géométrie le long des lignes entières.** Précision intacte, mais une
  géométrie modifiée (sommets, régions de déformation) pour une question d'échantillonnage.
- **Primitives : nodes enfants synthétiques.** Aucune disposition touchée, mais des nodes
  inventés (noms, rôles, parts et régions à recopier, compte vers la limite de 4096) pour
  représenter ce que la source décrit comme un seul objet.

## Précisions de T-a2 (2026-10-03)

Arrêtées à l'implémentation de l'import, dans la latitude du §3 ; aucune ne touche une
disposition ni une frontière.

- **Rugosité d'un MTL — correction du §3.** `√(2 / (Ns + 2))` est l'`α` de Beckmann de
  l'équivalence de Walter et al. (2007). DM-05 reçoit la rugosité **perceptuelle** de glTF
  (`roughnessFactor`, dont `α` est le carré) : la rugosité retenue est `(2 / (Ns + 2))^¼`. La
  formule du §3 rendait un OBJ plus brillant que le même modèle en glTF. `Pr` et `Pm`
  (extension PBR du MTL) priment sur `Ns` et le métal par défaut.
- **`v` d'un OBJ.** Le format compte `v` depuis le bas de l'image (convention OpenGL, celle des
  exports de Blender) ; glTF, Minecraft et AXION depuis le haut. L'import écrit `1 − v`, après
  la projection de `map_Kd` : sans quoi toute texture d'un OBJ apparaîtrait retournée.
- **Options des instructions de texture MTL.** `tobj` garde la fin de ligne entière comme nom
  de fichier ; les options (`-bm`, `-s`, `-o`, `-clamp`…) sont donc lues par l'import. `-s` et
  `-o` de `map_Kd` sont cuites dans `uv0` comme `KHR_texture_transform` ; `-bm` d'une carte de
  relief donne `normal_scale` ; `-clamp on` pose `CLAMP_U | CLAMP_V`. Les autres options, et
  les cartes sans slot (`map_Ka`, `map_Ks`, `map_d`…), sont averties. `norm` prime sur
  `map_Bump`/`bump` ; `map_Ke` donne `emissive_tex`. Une bibliothèque illisible est dite, ses
  matériaux remplacés par le matériau par défaut.
- **ORM sans occlusion.** Une `occlusionTexture` dans une autre image que
  `metallicRoughnessTexture` est avertie et ignorée, et `occlusion_strength` vaut alors **0** :
  le canal R de l'ORM n'est pas une occlusion, et le lire comme telle assombrirait le modèle.
- **Seuil de découpe.** Le schéma glTF ne borne `alphaCutoff` que par le bas ; DM-05 le veut
  dans `[0, 1]`. Il y est ramené, avec un avertissement en mode `MASK`.
- **Modèle d'éclairage.** `UNLIT` prime sur tout ; le vernis (`clearcoatFactor > 0`) sur le
  lustre. `sheen` reçoit la composante la plus forte de `sheenColorFactor`, DM-05 n'ayant pas de
  couleur de lustre. Les clés d'une extension sans champ DM-05 (`clearcoatTexture`,
  `sheenRoughnessFactor`, `anisotropyRotation`…) sont averties.
- **Filtrage.** `magFilter` ; à défaut, le filtrage que `minFilter` applique au sein d'un
  niveau ; à défaut, non déclaré (décision 4). `MIRRORED_REPEAT` est rendu en répétition simple,
  averti une fois par texture.
- **Refus d'image.** Une image n'est jugée que lorsqu'un slot la désigne. Un chemin `RESOURCE`
  est refusé (`E-3004`) si son type déclaré, ou à défaut son extension, n'est pas PNG ; sans
  extension, la signature tranchera côté Java. L'URI d'une image est contrôlé par R-531 que la
  texture serve ou non.
- **`COLOR_n`.** Le contrôle de forme des attributs (`gltf_refs`) couvre désormais `COLOR_n`
  (`VEC3`/`VEC4`, `F32`/`U8`/`U16`) : `read_colors` du crate `gltf` atteint un
  `unreachable!()` sur toute autre paire.
- **Diagnostics.** Refus de texture et pertes de correspondance voyagent dans
  `ImportedAsset::texture_refusals` et `material_warnings` ; la compilation les rend avec ses
  avertissements.

## Précisions de T-a3 (2026-10-03)

- **Codage de la plage.** `ax_model::dm::geometry::UvRange` porte le codage du §4 :
  `[0, 1]` toujours codée `0` (une forme non canonique, `0x0100`, se lit encore) ; plage
  invalide — étendue nulle, hors de `[-8, 9]` — refusée. Le décodage `min + q / 65535 × span`
  est épinglé au bit près, du même motif côté Rust et côté Java (`0xbefffd00` pour
  `q = 32768` sur `[-2, 1]`).
- **Où se fait la normalisation.** Dans l'optimizer (C-23, étape 4), comme le veut R-142, **avant
  la fusion** : deux sommets ne fusionnent qu'identiques une fois quantifiés dans leur plage.
  Les importeurs quantifient dans `[0, 1]`, saturé, depuis la quantification de `UvRange` ;
  l'optimizer requantifie depuis les valeurs brutes. Aucune fonction de `libm` : l'étape est
  identique entre plateformes (R-553).
- **Sommets partagés.** Deux meshes qui partagent des sommets partagent leur plage — un LOD
  copie celle de sa source. Le décodeur de `GEOM` et C-22 le vérifient
  (`uv_range_conflict`) : Java décode les UV sommet par sommet, sous la plage du mesh qui
  porte chacun.
- **`mesh_count`.** Le compilateur 8 l'écrit explicitement (un au moins pour un node qui porte
  un mesh) ; `0` se lit un. Un mesh glTF sans primitive — glTF en exige une — ou à plus de
  65 535 est refusé (`Malformed`) : son node aurait désigné les meshes d'un autre. Un objet OBJ
  découpé par `usemtl` donne un seul node, qui porte ses morceaux consécutifs ; ses deux nodes
  homonymes étaient refusés pour doublon.
- **Consommateurs de la plage.** Bornes de l'asset, LOD, liste de dessin au repos (un
  `RestDraw` par mesh, même node, même transformation), graphe de scène, et colliders d'un node :
  union des boîtes, nuage de points commun, maillage commun pour V-HACD — un collider à plusieurs
  primitives n'en couvrait que la première.
- **C-22.** Plage de meshes de chaque node dans le tableau de l'asset, comptée en `u64` ;
  `mesh_count` sur un node sans mesh ; validité de `uv0_range` ; conflit de plage — `E-3050`.
- **Migration (R-893).** `tests/fixtures/a3d/v1.1-compilateur-7.a3d` : un node à deux primitives
  et des UV écrêtées, avec `MATL` et `TEXR` ; il se relit un mesh par node, UV dans `[0, 1]`.
  Graine de fuzzing de `a3d_reader`.

## Précisions de T-a4 (2026-10-03)

Arrêtées à l'implémentation de la frontière, dans la latitude du §6 ; la disposition de la
charge et les signatures sont celles ratifiées.

- **Masque.** `MATL` et `TEXR` se demandent **ensemble** : l'un sans l'autre est refusé
  `E-2002`, comme le masque vide. Les slots des matériaux désignent la table des textures :
  aucune des deux sections ne se contrôle seule, et des textures que rien ne désigne ne servent
  à rien. `PHYS` et au-delà restent refusés.
- **Disposition inconnue (§1).** Le natif n'a pas de canal d'avertissement — `axion_last_error`
  ne porte que les erreurs, et le mot réservé de la charge vaut 0 (§6). Un `MATL` d'une
  disposition inconnue donne une table de matériaux **vide** ; l'avertissement du §1 revient au
  client, qui le constate : un mesh dont le matériau n'est pas dans la table prend le matériau
  par défaut, signalé une fois (T-b). Un `TEXR` d'une disposition inconnue donne une table de
  textures vide et **vide les slots** des matériaux : texture neutre, le reste du matériau
  demeure. Sans matériau, la table des textures n'est pas gardée — elle occuperait `PERSISTENT`
  pour rien —, mais elle reste contrôlée : corrompue, elle refuse l'asset.
- **`TEXR` absente** alors que des slots la désignent : faute du fichier, refus `E-3007`
  (`check_texture_slots`), non une disposition inconnue.
- **Chemins.** Des entrées qui partagent leurs octets dans `TEXR` partagent leur chemin dans
  `paths`, où il ne figure qu'une fois, placé par la première. Java le reçoit tel qu'écrit,
  sans décodage `%` ni normalisation ; T-b le résout contre le répertoire du modèle et le
  contrôle de nouveau (R-531).
- **Mémoire.** Le transfert des matériaux — gardé sous sa forme de transfert, comme la
  géométrie — et la table de `TEXR` (entrées et zone de données) sont imputés à `PERSISTENT`.
  Les PNG ne quittent le natif qu'à la demande, un par appel, et restent résidents : après un
  rechargement de ressources, le client les redemande sans recharger l'asset (R-752).
- **Schéma 1.** Il vaut pour toute charge d'`ASSET_OUT` — conteneur compilé et géométrie
  inchangés. Côté Java, chaque lecture compare le schéma au premier qui porte sa disposition :
  1 pour la table et les textures, 0 pour la géométrie.
- **JNI.** Un rang négatif d'`assetTexture` est refusé `E-2002` : il ne désigne aucune texture.
  Les dépôts `assetGeometry`, `assetMaterials`, `assetTexture` et `debugFill` partagent une
  forme : sortie `long[]` d'au moins un élément, taille dans `out[0]`.
- **Client.** `NativeAssetLoader.RENDER_SECTIONS` comprend `MATL | TEXR` : un asset chargé pour
  le rendu est dès maintenant contrôlé et imputé avec ses matériaux. Lecture par
  `MaterialTransfer`, `NativeAssetLoader.materials` et `texture` ; l'interface `AssetLoader`
  est inchangée — T-b dira ce que le cache de maillages en attend.
- **Tests (T-270).** Disposition de la charge figée octet par octet (Rust) et lue depuis des
  octets écrits à la main (Java) ; chargement des fichiers des compilateurs 6 et 7 ; ABI
  (`asset_materials_abi`) et vraie JNI (`NativeBridgeTest`) : un glTF à PNG embarqué et à
  ressource, dont le PNG revient à l'identique.

## Précisions de T-b1 (2026-10-03)

Arrêtées à l'implémentation du chargement des textures, dans la latitude du §7 ; aucune ne
touche une disposition ni une frontière.

- **Fil et moment.** Les textures se chargent avec l'asset, sur le thread des maillages : sous
  le verrou natif, la table des matériaux et les octets embarqués, tant que le handle vit ; hors
  du verrou, lecture des ressources, contrôles, découpe et mipmaps ; puis téléversement sur le
  fil de rendu, qui installe l'asset. Un asset n'est servi qu'avec ses textures : la boîte de
  repli reste affichée d'ici là, plutôt qu'un modèle blanc qui changerait de couleur.
- **Ce qui se charge.** L'albedo et l'émissive seuls ; normal, ORM, height et damage sont sans
  effet en vanilla (R-1513), et les charger coûterait de la mémoire pour rien. Un matériau
  CUTOUT a sa variante binarisée, par seuil ; les octets embarqués d'une image ne se lisent
  qu'une fois, quel que soit le nombre de ses variantes.
- **Noms.** `axion:texture/<asset>/<chargement>/<rang>`, suivi de `/cutout/<seuil>` pour une
  variante. Le numéro de chargement est nécessaire : `TextureManager.register` ferme la texture
  déjà enregistrée sous le même nom (`safeClose`, relevé dans le bytecode). Sans lui, la texture
  d'un chargement précédent, pas encore libérée, serait fermée par la nouvelle, puis la
  libération de l'ancienne fermerait la nouvelle.
- **Ressources.** Résolues contre le répertoire du modèle, sous `assets/<ns>/axion/models/…` ;
  le chemin, pris tel qu'écrit, est contrôlé de nouveau (R-531) et doit former une
  `ResourceLocation` : majuscules et espaces sont refusés, et rapportés. Le `.mcmeta` donne
  `blur` et `clamp` quand l'échantillonneur ne déclare rien.
- **Écrêtage.** Le téléversement vanilla écrête les deux axes à la fois : un échantillonneur qui
  n'en écrête qu'un est rendu en répétition, signalé une fois.
- **Échecs.** Table des matériaux illisible : matériau par défaut, signalé. Texture refusée —
  introuvable, `E-3004`, `E-3006`, illisible : texture neutre, signalée une fois par rang.
  L'asset s'affiche dans tous les cas.
- **Libérations.** Sur le fil de rendu (R-751) : à la sortie d'un monde ; au rechargement des
  ressources, par un écouteur client (R-752), ce qui couvre aussi un changement du réglage des
  mipmaps ; au remplacement d'un asset ; à l'arrêt du natif, la libération est confiée au fil de
  rendu. Une texture préparée qu'aucun téléversement n'attend plus est abandonnée, sa mémoire
  rendue.
- **Vérification.** Logique et cycle de vie testés sans Minecraft, avec un pipeline simulé ;
  cinq mutations du cache attrapées. Le collage — décodage, mipmaps, téléversement — n'est
  exercé qu'en jeu, avec T-b2 et le contenu de T-b4.

## Précisions de T-b2 (2026-10-03)

Arrêtées à l'implémentation des types de rendu et des couleurs, dans la latitude du §7 ; aucune
ne touche une disposition ni une frontière.

- **Types de rendu.** Ceux d'`entity_solid`, `entity_cutout` et `entity_cutout_no_cull`,
  recomposés tels que le bytecode les montre — shader d'entité, `NO_TRANSPARENCY`, `LIGHTMAP`,
  `OVERLAY`, `NO_CULL` pour le dernier, `create(…, NEW_ENTITY, QUADS, 256, true, false, …)` —,
  la texture liée par `TextureStateShard(rl, flou, mipmap)` au filtrage de son téléversement :
  mipmap seulement s'il y a des niveaux (`prepareImage` borne `GL_TEXTURE_MAX_LEVEL`). Une
  sous-classe de `RenderType`, jamais instanciée, atteint ses états `protected`. Mémorisés par
  (texture liée, shader, faces) ; oubliés à la libération de leur texture.
- **Sans contour.** `createCompositeState(false)` : à contour, un type mémoriserait pour sa
  texture un type de contour dans `RenderType.OUTLINE`, un `Util.memoize` jamais vidé (relevé dans
  le bytecode) — une entrée de plus à chaque chargement, les noms changeant. La passe ne dessinait
  déjà pas dans le tampon de contour.
- **Passes.** Passe 1 puis passe 2 (§19.10), un lot par type dans chacune. Opaque :
  `entity_solid`, faces selon l'état de culling ; découpe : `entity_cutout`, ou
  `entity_cutout_no_cull` à deux faces (T-273). Translucide et émissive : T-b3.
- **Couleurs.** Une fois par (mesh, matériau), sur le thread de fond : facteur × couleur de
  sommet si `VERTEX_COLOR`, facteur seul sinon ; produit borné à `[0, 1]` — un facteur supérieur
  à 1 multiplie donc avant la borne —, puis puissance 1/2,2 (`StrictMath` : le même octet sur
  toute machine), alpha linéaire ; ARGB sur 8 bits.
- **Matériau par défaut.** Un index hors de la table — table vide, ou défaut de la frontière —
  prend le matériau de glTF (blanc, sans texture, PBR, couleur de sommet), au mode et aux faces
  que disent les drapeaux du mesh (§3). Signalé une fois par chargement, sauf si la table,
  illisible, l'a déjà été.
- **Découpe qui rejette tout.** Seuil sur l'alpha du texel supérieur à 1
  (`albedo.a < alpha_cutoff`) : le mesh n'est pas dessiné — la texture neutre, d'alpha 1,
  passerait le test du shader.
- **Pleine lumière.** `UNLIT` ou `FULLBRIGHT` : lightmap `FULL_BRIGHT`.
- **Frontière.** `MaterialTransfer` refuse un mode de mélange, de faces ou d'éclairage inconnu,
  que le natif garantit pourtant : la table tombe entière au matériau par défaut, signalée, plutôt
  qu'un rendu au hasard. Un mesh qui désigne hors de ses sommets rend son handle : boîte de
  repli, signalée.
- **Libération différée au remplacement.** Un nouveau contenu se découvre pendant la collecte des
  assemblies, au milieu d'une frame : une autre assembly a pu recevoir l'ancien asset juste
  avant. Ses textures se libèrent donc au passage suivant du fil de rendu, la frame finie. Sans
  quoi le type de rendu, en liant un nom libéré, appellerait `TextureManager.getTexture`, qui
  enregistre à ce nom une `SimpleTexture` sans fichier : avertissement « Failed to load
  texture », puis la texture manquante, rangée à ce nom et jamais libérée (relevé dans le
  bytecode).
- **Vérification.** Logique et cycle de vie testés sans Minecraft : T-273 (passes et shaders),
  couleurs contre un calcul indépendant, matériau par défaut, liaisons des textures, libération
  différée ; dix-sept mutations attrapées. Le collage — types de rendu, émission des sommets,
  filtrage réappliqué à chaque dessin — n'est exercé qu'en jeu, avec le contenu de T-b4.

## Précisions de T-b3 (2026-10-03)

Arrêtées à l'implémentation des passes translucide et émissive, dans la latitude du §7 ; aucune
ne touche une disposition ni une frontière.

- **Lecture par un flux.** `NativeImage.read(byte[])` copie le PNG sur la pile de LWJGL
  (`MemoryStack.malloc`), de 64 Kio par défaut — ni Minecraft, ni la configuration de
  développement de Forge, ni le projet ne la règlent —, et une texture plus grosse la fait
  déborder : `OutOfMemoryError("Out of stack space.")`, une `Error` que T-b1 ne rattrapait pas.
  D'après le code, la tâche de fond s'arrêtait là, l'asset restait en chargement, sa boîte de
  repli affichée. Écart de T-b1 corrigé : toute image se lit par `read(Format.RGBA, flux)`, que
  Minecraft copie hors de la pile (`MemoryUtil`), en RGBA — le format qu'exige `getPixelRGBA`,
  dont dépendent la découpe, le masque et `MipmapGenerator`. Relevé dans le bytecode, pas observé
  en jeu.
- **Émissive d'un matériau découpé.** `eyes` additionne `texel × couleur` sans rejeter aucun
  texel (shader lu) : l'émission brillerait dans les trous. Elle passe par une variante
  masquée — la couleur de l'émissive, ou du blanc sans texture d'émissive, là où l'albedo binarisé
  au seuil du matériau est gardé ; du noir ailleurs, qui n'ajoute rien. Le masque se lit au plus
  proche, sous le centre de chaque texel de l'émissive ; une requête porte les deux images, lues
  une fois chacune.
- **Émission manquante.** Sans texture d'émissive, le facteur sur du blanc (sémantique glTF).
  Texture d'émissive refusée ou perdue, masquée comprise : la neutre est noire (fiche C-26), donc
  pas d'émission, plutôt qu'un rayonnement sur toute la surface ou dans ses trous.
- **Passe 5.** À `AFTER_ENTITIES`, après les passes 1 et 2 : `eyes` recomposé tel que le bytecode
  le montre (additif, `COLOR_WRITE`, sans lightmap ni overlay, quads triés), faces selon le
  matériau ; couleur = facteur émissif en gamma, borné à 1. L'émission d'une surface translucide,
  dessinée avant elle (R-1570), en est atténuée d'un facteur `1 − α` : approximation déclarée.
- **Passe 4.** À `AFTER_TRANSLUCENT_BLOCKS` : `entity_translucent_cull` ou `entity_translucent`
  recomposés (mélange alpha, profondeur écrite, lightmap, overlay, quads triés au téléversement,
  `DISTANCE_TO_ORIGIN` pendant le rendu du niveau). Meshes du plus loin au plus près, à la distance
  au carré du centre de leur boîte posée (R-1580), égalités dans l'ordre donné ; lots consécutifs
  de même type, chaque changement de type vidant le lot précédent, le dernier vidé avant de rendre
  la main. `MAIN_TARGET`, cible par défaut de ces types, ne lie rien (relevé) : sous « Fabulous »,
  la cible translucide déjà liée reçoit le dessin.
- **Matrice de capacités.** Cartes normal, ORM, hauteur et dommage : indisponibles en vanilla, et
  pas chargées (R-1513). L'éclairage disponible dit `VANILLA_COMPAT`, la pleine lumière des
  matériaux sans éclairage et l'émissive additive.
- **Vérification.** Logique testée sans Minecraft : variantes masquées (règle, noms, requêtes à
  deux images lues une fois chacune), émission (couleur, texture manquante, masque perdu), ordre
  de profondeur, centres, shaders (T-273), matrice ; onze mutations attrapées. Le collage —
  lecture par flux, variante masquée, passes 4 et 5, vidage sous « Fabulous » — n'est exercé
  qu'en jeu, avec le contenu de T-b4.

## Précisions de T-b4 (2026-10-03)

- **Où.** Le contenu d'essai vit dans `java/axion-mod/src/devcontent` : un jeu de sources que
  les seuls lancements de développement chargent (`runClient`, `runServer`…), jamais empaqueté —
  le mod livré n'embarque que ses definitions de démonstration (R-1790). Modèles sous
  `data/axion/axion/models/test/materiaux/`, texture ressource sous
  `assets/axion/axion/models/test/materiaux/tex/`, definitions `axion:test/materiaux/*`. Source
  Blender, images empaquetées : `src/devcontent/blender/materiaux_t-b4.blend`.
- **Ce que chaque modèle exerce.** `cube_texture` : PNG embarqué de 286 Ko, au-delà de la pile de
  LWJGL. `vitre` : cadre opaque et verre `BLEND` à deux faces, cinq meshes. `grille` : `MASK` à
  deux faces. `panneau_emissif` : émissive texturée, et grille `MASK` émissive sans texture —
  l'émission masquée. `sol_repete` : PNG RGB sans alpha, UV répétées six fois, filtrage au plus
  proche. `multi_materiaux` : un mesh, trois matériaux, couleurs de sommet sur l'un d'eux.
  `ressource` : image externe `tex/bois.png`, tampon intégré au `.gltf` — la compilation en jeu
  ne lit aucun fichier voisin.
- **Collideurs.** Une boîte `auto_box` par modèle ; celle d'une surface plane a une épaisseur de
  5 cm, le validateur refusant une dimension nulle.
- **Vérification.** Les sept modèles compilent par `axion-cli`, le pipeline du jeu (R-830).
  Observés en jeu le 2026-10-03 par Killian, client de développement : conformes de jour ; de
  nuit, émission sans lueur dans les trous ; vitre transparente sous « Fabuleux » ; F3 + T sans
  perte.

## Précisions de T-c (2026-10-03)

Arrêtées à l'implémentation de l'atlas, dans la latitude de la fiche C-26 (« atlas AXION dédié
pour les textures ≤ 256×256 ; au-delà, texture individuelle »), qui n'en fixe ni l'étendue, ni
la disposition, ni les marges. Aucune ne touche une disposition, une frontière ni un format.

- **Étendue : un atlas par chargement d'asset.** Les petites textures d'un asset s'y rangent ;
  la page est une texture de l'asset comme les autres — même nom propre au chargement
  (`…/<chargement>/atlas/<page>`), même téléversement, même libération. Un atlas commun à tous
  les assets aurait demandé un allocateur de tuiles vivant, des téléversements partiels entre
  deux frames et des coordonnées de texture qui changent sous un asset déjà servi, pour un gain
  limité au regroupement d'assets différents : les instances d'un même asset partagent déjà
  leurs types de rendu. Écarté, nommé hors portée.
- **Ce qui entre.** Une texture préparée — variante découpée et émissive masquée comprises — de
  côtés ≤ 256, que **chaque** mesh qui la lit, en albedo ou en émission, lit dans `[0, 1]`
  (plage d'UV `[0, 1]`, ADR-122 §4) : une tuile ne se répète pas. Un seul mesh qui la répète la
  garde individuelle. Une page par filtrage — au plus proche, linéaire —, le filtrage se liant
  par page ; un filtrage qui ne réunit qu'une texture n'en fait pas.
- **Marges.** `2^L` texels de chaque côté, `L` étant le réglage des mipmaps du jeu, remplis de
  ce qu'échantillonnerait la texture seule au-delà de son bord : texels enroulés en répétition,
  bord recopié en écrêtage. Un sommet à `u = 1`, le filtrage linéaire et chaque niveau de
  mipmap lisent donc ce que la texture seule aurait donné, jamais la tuile voisine. Coût
  déclaré : une texture de 16² occupe une tuile de 48² à `L = 4`, une de 256², 288².
- **Mipmaps.** Tuiles alignées et de côtés multiples de `2^L` : chacune reçoit les siens de
  `MipmapGenerator`, comme la texture seule, et ils se recopient niveau par niveau à leur place.
  Le bytecode lu montre que Forge ne remplit pas un niveau au-delà de `log2(min(l, h))`
  (`ForgeHooksClient.getMaxMipmapLevel`) : la marge garantit des tuiles d'au moins `2^(L+1)`. En
  répétition, chaque niveau d'une tuile, marge comprise, est exactement celui de la texture
  seule (vérifié sur tableaux, avec un filtre local quelconque) ; en écrêtage, la base l'est,
  les niveaux réduits le sont à la moyenne du bord près.
- **Disposition.** Rangées, des tuiles les plus hautes aux plus basses ; largeur puissance de
  deux, doublée tant que la page est plus haute que large ; hauteur multiple de `2^L` ; côtés
  ≤ 4096 (R-570), le reste passant à une page suivante. Zones libres transparentes ; la page
  s'écrête, les tuiles portant leur répétition dans leur marge.
- **Coordonnées de texture.** L'asset sert à chaque mesh une région — la texture liée et la
  place de son image — ; `u' = décalage + u × étendue` s'applique à l'émission des sommets.
  Une page lie un seul type de rendu par shader et par faces : ses meshes tombent dans le même
  lot.
- **Échecs.** Une page qui ne se compose pas laisse ses textures se préparer une à une,
  signalé une fois ; une page perdue au téléversement laisse la texture neutre à toutes ses
  tuiles, signalé. Toute image décodée est prise ou rendue exactement une fois, sur tous les
  chemins.
- **Hors portée, nommé.** Atlas commun à plusieurs assets ; option `max_texture_size`, réglage
  de compilation que Java ne reçoit pas (il faudrait le porter par le format).
- **Vérification.** Disposition (aléatoire, débordement, déterminisme), marges et mipmaps sur
  tableaux, éligibilité, cycle de vie dans le cache (pages, filtrages, échec, perte,
  supplantation, images rendues) ; douze mutations attrapées. En jeu le 2026-10-03, contenu
  `axion:test/materiaux/atlas` (source `src/devcontent/blender/atlas_t-c.blend`) : six petites
  textures aux bords contrastés, une bande qui en répète une ; journal : page de 256×96 (trois
  textures au plus proche), page de 256×160 (deux linéaires), la texture répétée restée seule ;
  panneau émissif en page de 1024×288. Observé par Killian : bords intacts de près comme de
  loin, répétition nette, panneau inchangé.
