# ADR-103 — IF-01 gagne le côté de démarrage et l'export des métriques

- **Statut** : accepté
- **Date** : 2026-09-10
- **Portée** : IF-01, `AXION_ABI_VERSION`, C-12, C-15
- **Décidé par** : Killian, sur deux options recommandées

## Contexte

Deux composants de M1 ont buté sur la même limite du contrat de frontière.

**C-12** dimensionne son pool de workers avec R-471 : `clamp(cores - 2, 1, N)`,
où `N` vaut 4 sur un client et 8 sur un serveur dédié. Or `axion_init` ne
recevait qu'une configuration, où rien ne dit d'où elle vient.

**C-15** doit exporter ses métriques en JSON (R-502, `/axion metrics export`).
Ni IF-01 ni la liste des tampons d'IF-02 ne prévoyaient par où.

Les deux relèvent du contrat de frontière, que le cahier des charges range parmi
ce qu'un agent ne décide pas seul.

## Options écartées

**Déduire le côté des clés reçues.** Le chargeur Java n'envoie que la portée de
son côté : la présence d'une clé de portée `CLIENT` trahit le client. Ne touche
à aucun contrat, mais crée un couplage implicite entre le chargeur et la
frontière, qui casserait silencieusement le jour où une option changerait de
portée. Un pool mal dimensionné ne se voit pas : il ralentit.

**Faire du côté une option de configuration.** `general.side` dans la map CBOR.
N'ajoute rien de visible dans les fichiers `.toml`, mais fait passer pour un
réglage ce qui n'en est pas un — personne ne « configure » le côté sur lequel il
joue — et l'ANNEXE A.3 est la liste normative des options.

**Un tampon partagé pour les métriques.** `AXION_BUF_TELEMETRY`, dans la liste
d'IF-02. Cohérent avec les transferts volumineux et périodiques, mais
surdimensionné pour un export à la demande, et la liste des types de tampons est
donnée comme fermée.

## Décision

**Le côté devient un paramètre d'`axion_init`.**

```c
int32_t axion_init(const uint8_t* config_cbor, size_t len, uint32_t side,
                   uint64_t* out_ctx);
```

`side` vaut `AXION_SIDE_CLIENT` (0) ou `AXION_SIDE_SERVER` (1). Toute autre
valeur est refusée : en supposer une donnerait un pool mal dimensionné sans que
rien ne le signale.

**L'export des métriques devient une fonction**, calquée sur `axion_last_error`,
qui existait déjà :

```c
int32_t axion_metrics_export(uint64_t ctx, uint8_t* out_utf8, size_t cap,
                             size_t* out_len);
```

Une différence assumée avec `axion_last_error` : **rien n'est écrit quand la
capacité ne suffit pas**, et `out_len` reçoit toujours la longueur complète.
Un message de diagnostic tronqué reste lisible ; un document JSON tronqué ne
l'est pas — il ne se distinguerait même pas d'un document complet décrivant
autre chose. L'appelant rappelle avec un tampon plus grand.

**`AXION_ABI_VERSION` passe de 1 à 2.** R-261 l'impose : la signature
d'`axion_init` change, c'est une rupture. Rien n'est publié, la rupture ne coûte
donc rien — et le handshake d'ABI, vérifié en acceptance de M0 avec un natif
réellement construit sur une autre version, protège de toute façon le cas d'un
JAR partiellement remplacé.

## Conséquences

- `NativeBridge.init` devient `([BI)J`, et une méthode native `metricsExport`
  s'ajoute — toujours dans la classe unique qu'impose R-492.
- La séquence de démarrage transmet son côté depuis la portée de configuration
  qu'elle charge déjà. La portée `COMMON` n'en est pas une : la rencontrer lève,
  plutôt que de supposer un côté.
- Le jeton `0` désigne désormais, pour `axion_last_error`, un refus survenu
  **avant** l'ouverture d'une session. Sans lui, une configuration refusée ne
  rendait qu'un code au moment où le message compte le plus.
- L'ANNEXE A.1 n'est pas touchée : un côté inconnu est refusé avec le code déjà
  retenu pour une configuration refusée ([ADR-102](ADR-102.md)).

## Ce que cette décision ne fait pas

Elle ne crée pas de canal de télémétrie périodique. L'export est **à la
demande** : c'est ce que R-502 décrit. Le jour où des métriques devront remonter
à chaque tick, ce sera un tampon partagé, et une autre décision.
