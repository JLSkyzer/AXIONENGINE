# ADR-117 — Opcodes de tuiles de collision du monde sur `SimIn` (IF-03)

- **Statut** : **accepté** — ratifié par Killian le 2026-09-30. Le protocole ci-dessous fait
  foi pour C-38 T2 (transcription des structs de payload + décodage), à écrire à effort maximal.
- **Date** : 2026-09-30
- **Portée** : C-38, IF-03 (§4.5), DM (`dm/commands.rs`), ADR-114, ADR-115, R-640, R-641,
  R-642, R-643, R-970, R-1020, R-901, interdiction 3.13, ABI
- **Proposé par** : Claude, en préparant C-38 T2 ; **ratifié par** : Killian le 2026-09-30

## Contexte

C-38 T1 a construit, **et testé**, le magasin natif de tuiles de collision du monde,
côté `ax-physics` :

| Fonction native (`SimDriver`) | Effet | Tranche |
|---|---|---|
| `set_world_tile(dim, section, boxes, material)` | Tuile de collision solide : N boîtes `Cuboid`, corps STATIC (R-640) | T1 |
| `set_world_tile_heightfield(dim, section, rows, cols, heights, scale, material)` | Repli champ de hauteurs quand la section dépasse le seuil de boîtes (R-641) | T1b |
| `set_world_fluid_tile(dim, section, boxes, density)` | Volumes de flottabilité, « capteurs » (R-642) | T1d |
| `remove_world_tile(dim, section)` | Retire la tuile de collision d'une section | T1 |
| `remove_world_fluid_tile(dim, section)` | Retire les volumes de fluide d'une section | T1d |

Ces opérations sont **prouvées** (un corps repose sur une dalle, flotte dans l'eau, le
matériau change la friction…). Ce qui manque, c'est leur **transport sur la frontière** :
Java (T3) construit les tuiles depuis `Level.getBlockCollisions`, les quantifie en 1/16 de
bloc et les **envoie par lot** (fiche 5.30, étapes 2-3), à `world.tiles_per_tick` par tick.

Le §4.5 (IF-03) et ADR-114 fixent le **cadre** de `SimIn` — un `CommandStreamHeader`, puis
`command_count` commandes, chacune un `SimCommandHeader { opcode, payload_len }` suivie de son
payload `repr(C)` lu en place — mais **ne définissent pas les opcodes des tuiles du monde**.
C'est une décision d'**ABI** : comme la disposition de `PhysicsEvent` (ADR-113) ou le
protocole de commande lui-même (ADR-114), « un octet mal placé se paie en silence et pour
toujours ». D'où cet ADR, à effort maximal, **avant** toute ligne de T2.

Le format doit, comme l'exige ADR-114 :

- se lire **en place**, sans copie ni allocation superflue par tick ;
- porter des **données de taille variable** (liste de boîtes, matrice de hauteurs) — le
  précédent existe : `CREATE_ASSEMBLY` porte un en-tête fixe `CreateAssembly` **suivi, dans
  le même payload, des octets `PHYS`** (ADR-115) ;
- rester **extensible** et **compatible avant** (un lecteur qui ignore l'opcode saute son
  payload) ;
- s'appliquer de façon **déterministe**, dans l'ordre du flux (R-1020) ;
- traiter l'entrée comme une **donnée hostile** : bornée avant toute allocation (R-901),
  validée, jamais indexée telle quelle (interdiction 3.13).

Distinction structurante : le monde tient **deux registres indépendants** par section — la
**collision** (`tiles` : soit des boîtes, soit un champ de hauteurs, l'un remplaçant
l'autre) et le **fluide** (`fluid_volumes`). Une section peut porter les deux à la fois. Le
protocole doit donc adresser chaque registre séparément, retrait compris.

## Décision proposée

### 1. Cadre — inchangé (ADR-114)

Aucun nouveau cadre. Les tuiles sont des **commandes ordinaires** du flux `SimIn` : le « lot »
de la fiche 5.30 est simplement une suite de commandes `SET_WORLD_*` dans un même `submit`,
comptées par `command_count`. `CommandStreamHeader::CURRENT_SCHEMA` **reste à 1** : ajouter des
opcodes ne change le payload d'aucun opcode existant (la règle de bump d'ADR-114 ne s'applique
qu'à un changement de payload existant). Un lecteur antérieur ignore ces opcodes (compatibilité
avant) ; après T2, ils passent d'« ignoré » à « appliqué ».

### 2. Opcodes ajoutés (append-only, en fin de table)

| Opcode | Valeur | En-tête fixe (`repr(C)`) | Corps variable | Registre | Fonction native |
|---|---|---|---|---|---|
| `SET_WORLD_COLLISION`  | 6  | `SetWorldCollision` (32 o) | `box_count × [f32;6]` | collision | `set_world_tile` |
| `SET_WORLD_HEIGHTFIELD`| 7  | `SetWorldHeightfield` (48 o) | `rows × cols × f32` | collision | `set_world_tile_heightfield` |
| `SET_WORLD_FLUID`      | 8  | `SetWorldFluid` (32 o) | `box_count × [f32;6]` | fluide | `set_world_fluid_tile` |
| `REMOVE_WORLD_COLLISION`| 9 | `RemoveWorldTile` (24 o) | — | collision | `remove_world_tile` |
| `REMOVE_WORLD_FLUID`   | 10 | `RemoveWorldTile` (24 o) | — | fluide | `remove_world_fluid_tile` |

Chaque opcode correspond **un pour un** à une fonction native déjà écrite et testée : le
protocole n'ajoute aucune logique physique, seulement son transport.

### 3. Dispositions figées (petit-boutiste, testées comme les autres DM)

Toutes les boîtes sont **relatives à l'origine de la section** (`section × 16`), en blocs,
quantifiées en 1/16 (fiche 5.30, étape 2) — exactement ce que les setters natifs attendent.
`[minx, miny, minz, maxx, maxy, maxz]`.

```rust
// Opcode 6 — collision solide.
#[repr(C)]
pub struct SetWorldCollision {
    pub dimension: u64,     // 0
    pub section: [i32; 3],  // 8   (index de section 16³ = coord_bloc >> 4)
    pub box_count: u32,     // 20
    pub friction: f32,      // 24  matériau dominant (R-643)
    pub restitution: f32,   // 28
}                           // BYTES = 32 ; corps : box_count × 24 o

// Opcode 7 — champ de hauteurs (repli R-641).
#[repr(C)]
pub struct SetWorldHeightfield {
    pub dimension: u64,     // 0
    pub section: [i32; 3],  // 8
    pub rows: u32,          // 20
    pub cols: u32,          // 24
    pub friction: f32,      // 28  matériau dominant (R-643)
    pub restitution: f32,   // 32
    pub scale: [f32; 3],    // 36  étendue x/z, facteur de hauteur y
}                           // BYTES = 48 ; corps : rows × cols × 4 o (hauteurs, ligne-major)

// Opcode 8 — volumes de fluide.
#[repr(C)]
pub struct SetWorldFluid {
    pub dimension: u64,     // 0
    pub section: [i32; 3],  // 8
    pub box_count: u32,     // 20
    pub density: f32,       // 24  masse volumique (eau douce ≈ 1000)
    pub _pad: u32,          // 28  réservé, à zéro
}                           // BYTES = 32 ; corps : box_count × 24 o

// Opcodes 9 et 10 — retrait (payload partagé, comme APPLY_FORCE/APPLY_IMPULSE).
#[repr(C)]
pub struct RemoveWorldTile {
    pub dimension: u64,     // 0
    pub section: [i32; 3],  // 8
    pub _pad: u32,          // 20  réservé, à zéro
}                           // BYTES = 24
```

Tous alignés sur 8 (le `u64` initial), tailles multiples de 8 : un test de disposition
(`size_of`, `align_of`, `offset_of`) les verrouille, comme `dm/commands.rs` le fait déjà.

### 4. Validation (donnée hostile, R-901 / interdiction 3.13)

Pour un opcode connu à corps variable, le lecteur vérifie **avant toute allocation** :

- `payload.len() >= <En-tête>::BYTES` (sinon `BadPayloadLength`) ;
- le compte déclaré est borné : `box_count <= MAX_WORLD_TILE_BOXES` (**4096**, le seuil de
  R-641 : au-delà, Java doit envoyer un champ de hauteurs, jamais des boîtes) ; pour le champ,
  `2 <= rows, cols <= MAX_WORLD_HEIGHTFIELD_DIM` (**64**), donc au plus 4096 hauteurs ;
- la longueur du corps correspond **exactement** au compte : `payload.len() == BYTES +
  box_count·24` (resp. `+ rows·cols·4`), sinon `BadPayloadLength` ;
- les valeurs (boîtes, hauteurs, matériau, densité) restent des données : le natif les
  **assainit** déjà (`ContactMaterial::sanitized`, boîtes dégénérées ignorées, densité ≤ 0 →
  retrait). L'ABI transporte des `f32` bruts ; la frontière ne fait que borner les **comptes**.

Ces plafonds sont des **limites de validation, pas des champs de disposition** : ils peuvent
évoluer sans casser l'ABI figée. Une commande fautive est refusée et journalisée (`E-2002`,
lecture de tampon `SimIn` invalide, R-491), jamais appliquée à moitié.

### 5. Où les opcodes sont décodés

Contrairement à `CREATE_ASSEMBLY` — qui dépend d'`ax-asset` pour décoder la section `PHYS`
et reste donc **différé à la frontière** (`ax-ffi`) — les tuiles du monde ne portent que des
tableaux de `f32` : **aucune dépendance `ax-asset`**. Elles sont donc décodées et appliquées
**directement dans `ax_physics::apply_command_stream`**, comme `REMOVE_ASSEMBLY` ou
`SET_KINEMATIC`, et comptées `applied` dans `CommandOutcome`. La frontière n'a rien de spécial
à faire pour elles.

### 6. Suppression

Deux chemins, tous deux **définis** :

- **explicite** — `REMOVE_WORLD_COLLISION` / `REMOVE_WORLD_FLUID` : le chemin **recommandé**
  pour l'invalidation (fiche 5.30, étape 4) et la libération des tuiles lointaines (étape 5).
  Payload minimal `{dimension, section}`, sans corps ;
- **implicite** — un `SET_WORLD_COLLISION` / `SET_WORLD_FLUID` à `box_count == 0` (ou une
  densité ≤ 0 pour le fluide) **retire** le registre visé : c'est déjà le contrat des setters
  natifs (une section sans collision n'a pas de corps). Défini, pas indéfini ; mais le retrait
  explicite dit mieux l'intention.

### 7. Déterminisme (R-1020)

Les commandes de tuiles s'appliquent **dans l'ordre du flux**, mêlées aux autres. Un
`SET_WORLD_COLLISION` puis un `REMOVE_WORLD_COLLISION` sur la même section dans un même lot
respectent cet ordre. `set_world_tile_heightfield` et `set_world_tile` écrivent le **même**
registre de collision : le dernier reçu pour une section gagne, de façon déterministe.

### 8. Sortie

Aucune. Les tuiles sont **entrée seule** (Java → Rust). Les corps STATIC ne sont pas collectés
dans `SimOut` (`body_states` filtre le non-dynamique). `AxionCollectResult` est inchangé.

## Alternatives évaluées

- **Un opcode `SET_WORLD_TILE` unique, discriminé par un champ `kind` (boîtes / champ /
  fluide).** Rejeté : c'est le patron « union `repr(C)` » qu'ADR-114 a déjà écarté — l'en-tête
  fige sa taille sur le plus gros cas et gaspille la bande passante du cas courant (les boîtes
  n'ont que faire de `rows/cols/scale`), tuile après tuile. Il **mélange en plus les deux
  registres** (collision / fluide) sous un opcode, ce qui rend le retrait ambigu. Des opcodes
  étroits, un par opération, sont l'esprit d'ADR-114.

- **Un seul `REMOVE_WORLD_TILE { dimension, section, target: u32 }`** (0 = collision, 1 =
  fluide) au lieu de deux opcodes de retrait. Uniforme en taille (pas une union), donc
  acceptable ; écarté par cohérence — ADR-114 distingue les opérations distinctes par opcode
  (retirer une collision et retirer un fluide agissent sur deux registres distincts), et deux
  opcodes se documentent seuls sans discriminant à valider. Compromis mineur, réversible avant
  ratification si tu préfères l'économie d'opcode.

- **Suppression implicite seule (pas d'opcode `REMOVE`).** Rejeté comme unique mécanisme : le
  chemin d'invalidation/déchargement est fréquent (étapes 4-5) et mérite un opcode étroit
  `{dim, section}` plutôt qu'un en-tête `SET` vide. Conservé comme **alias** défini.

- **Boîtes en coordonnées monde (`f64`).** Rejeté : double la taille du corps, et l'API native
  comme la quantification Java sont **relatives à la section** (1/16 de bloc) ; un index de
  section (`i32`) plus des offsets `f32` collent exactement au natif livré et à la fiche 5.30.

- **Un tampon `SimIn` dédié aux tuiles.** Rejeté (même raison qu'ADR-114) : multiplie les
  acquisitions par tick et brise le flux unique ordonné qui garantit l'ordre déterministe
  entre les tuiles et les autres commandes.

## Conséquences

- Cinq opcodes (6–10) réservés **en fin de table, jamais réattribués** ; leurs quatre structs
  de payload sont figées avec un **test de disposition**, transcrites **avec leur consommateur**
  (T2) — la règle d'ADR-114 / `dm/mod.rs`.
- Les tuiles du monde se décodent **dans `ax-physics`** (aucune dépendance `ax-asset`),
  appliquées en ligne : `CREATE_ASSEMBLY` reste le seul opcode différé à la frontière.
- `CommandStreamHeader::CURRENT_SCHEMA` **inchangé** (1) : ajout additif, compatible avant.
- Les plafonds de comptes (`MAX_WORLD_TILE_BOXES = 4096`, `MAX_WORLD_HEIGHTFIELD_DIM = 64`)
  bornent la donnée hostile **avant** allocation (R-901) et peuvent évoluer sans casser l'ABI.
- Aucune incidence sur `SimOut` / `collect` : les tuiles sont entrée seule.
- Une fois ratifié, T2 (`[EFFORT MAX]`) transcrit ces structs dans `dm/commands.rs` (avec
  leurs tests), les décode dans `apply_command_stream`, et ouvre la voie à T3 (Java/Forge) qui
  poussera enfin les tuiles à travers la frontière.

## Décisions ratifiées (Killian, 2026-09-30)

Les trois points ouverts ont été tranchés en faveur des recommandations ; le corps de l'ADR
ci-dessus les reflète déjà :

1. **Retrait** : **deux opcodes** `REMOVE_WORLD_COLLISION` (9) et `REMOVE_WORLD_FLUID` (10),
   chacun `{dimension, section}` — un opcode par opération, sans discriminant à valider.
2. **Plafonds** : `MAX_WORLD_TILE_BOXES = 4096` (seuil R-641) et `MAX_WORLD_HEIGHTFIELD_DIM = 64`
   (au plus 4096 hauteurs par tuile), bornes de validation ajustables sans casser l'ABI.
3. **Alias de suppression implicite** : **conservé et défini** — un `SET_WORLD_*` à `box_count`
   nul (ou densité ≤ 0) retire le registre visé, conformément au contrat des setters natifs ;
   les opcodes `REMOVE` restent le chemin recommandé pour l'intention.
