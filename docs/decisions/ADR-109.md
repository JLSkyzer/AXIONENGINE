# ADR-109 — Lecture du schéma de definition 1

- **Statut** : accepté
- **Date** : 2026-09-13
- **Portée** : C-27, R-580, R-581, R-1780..R-1783, PARTIE 23.4, PARTIE 24.1
- **Décidé par** : Claude, en ouvrant C-27 ; périmètre M2 décidé par Killian

## Contexte

R-1780 fait de `"schema": 1` une version : une definition qui la porte promet
une forme, et un validateur doit pouvoir la vérifier. Le §23.4 donne cette
forme sous la forme d'un **exemple**. Relu champ par champ, il laisse ouvert ce
qu'un validateur doit trancher :

- R-1781 annonce des « défauts documentés » ; **aucune table de défauts**
  n'existe dans le cahier des charges.
- Les énumérations sont écrites en **MAJUSCULES** dans les DM (`REVOLUTE`,
  `WELD`, `LOAD_BEARING`, `DETACHABLE`) et en **minuscules** dans l'exemple JSON
  (`revolute`, `hinge`, `load_bearing`, `detachable`). Aucune règle ne les
  relie.
- `kind` n'a que `vehicle` en exemple ; `AssemblyKind` compte neuf valeurs
  (`Static`, `RigidObject`, `Vehicle`, `Articulated`, `Character`, `Visual`,
  `Structure`, `Machine`, `SoftObject`) sans graphie JSON.
- `"asset": "mymod:models/pickup.glb"` omet le segment `axion/` des chemins de
  modèles (`assets/<ns>/axion/models/**`).
- Beaucoup de champs n'ont ni plage ni liste fermée écrites ; plusieurs clés
  citées ailleurs (`gravity_scale`, `anti_roll`, seuils d'étapes) n'ont pas de
  nom JSON.
- L'exemple lui-même référence un joint (`door_l_hinge`) et une part (`body`)
  qu'il ne déclare pas.

Un validateur qui comblerait ces trous en silence publierait un format que
personne n'a décidé. Ce fichier dit comment le schéma 1 est lu.

## Décisions

1. **Casse.** Toute valeur d'énumération s'écrit en JSON en `snake_case`
   minuscule du nom du DM : `REVOLUTE` → `revolute`, `LOAD_BEARING` →
   `load_bearing`, `RigidObject` → `rigid_object`. C'est la forme de chaque
   exemple du cahier des charges ; la forme en majuscules est refusée.
   Exception : les étapes de dommage restent en majuscules comme clés
   (`"HEAVY"`), parce que c'est ainsi que §13.4 et `collider_variants` les
   écrivent.

2. **`kind`** : `static`, `rigid_object`, `vehicle`, `articulated`,
   `character`, `visual`, `structure`, `machine`, `soft_object`.

3. **`asset`** : `<ns>:<chemin>` désigne le modèle `<ns>:axion/<chemin>`, soit
   `assets|data/<ns>/axion/<chemin>`. Un chemin qui commence déjà par `axion/`
   est refusé : il désignerait `axion/axion/…`, et l'auteur ne l'a pas voulu.

4. **Clés inconnues refusées**, sauf sous `custom`, qui est précisément la
   place des données de l'auteur. Une clé que le cahier des charges cite sans
   lui donner de nom JSON n'appartient pas au schéma 1 ; elle y entrera par une
   version de schéma, pas par tolérance. Accepter l'inconnu ferait d'une faute
   de frappe (`"mas": 1650`) un champ silencieusement ignoré.

5. **Ce qui est vérifié, et rien de plus.** Chaque champ l'est par le type que
   l'exemple implique. S'y ajoutent **uniquement** les contraintes écrites :
   listes fermées (types de joint C-34, drapeaux de part DM-11, types et
   drapeaux de liaison DM-14, rôles de siège et actions d'interaction C-53,
   étapes et actions de `on_part_stage` §13.4/R-1170, genres et autorités de
   particules DM-16, sources procédurales ANNEXE A.4, niveaux de qualité),
   plages écrites (masse `[0.001, 1e6]`, proportions `[0, 1]`, capacités
   `> 0`) et plafonds par assembly (R-190, C-22). Aucune plage n'est inventée
   pour un champ qui n'en a pas.

6. **Absence d'un champ optionnel = non déclaré.** Faute de table de défauts,
   la definition compilée ne remplit rien : elle garde l'absence, et c'est le
   système consommateur qui applique son défaut documenté (masse calculée
   R-622, liaisons générées C-28, colliders automatiques C-32). Un défaut
   inventé ici se figerait dans les données avant que le système qui le définit
   n'existe.

7. **Noms internes** (bodies, joints, parts, zones, sièges, animations) : non
   vides, ASCII imprimable, 64 octets au plus, uniques dans leur catégorie —
   la règle de C-22 pour les noms d'un asset, étendue aux noms que la definition
   déclare. Toute référence interne désigne un nom déclaré dans la même
   definition ; les incohérences de l'exemple du §23.4 ne font pas règle.

8. **Refus.** `schema` absent ou d'un autre type qu'entier : `E-7001`. Valeur
   entière autre que `1` : `E-7003` (R-1780). Toute autre faute : `E-7001`, une
   definition à la fois (R-580), avec le chemin JSON de la faute. `kind:
   vehicle` alors que le module `vehicles` est désactivé : refus avec message
   (§24.1).

9. **Aucune exécution** (R-581, ADR-009) : aucune valeur n'est interprétée
   comme expression, script ou nom de classe. Les chaînes à grammaire — sources
   procédurales, `driven_by`, `trigger` — sont confrontées à leurs listes
   fermées, jamais évaluées.

## Conséquences

- Le schéma publié (`docs/schema/definition-1.json`, R-1783) transcrit ces
  décisions ; il est la version lisible par machine de ce fichier.
- Un champ dont le cahier des charges fixera un jour la plage ou le défaut
  entrera par une nouvelle version de schéma. Une definition `schema: 1` reste
  lue comme ici.
- Les points laissés ouverts par le cahier des charges et tranchés ici sont à
  signaler lors d'une prochaine révision du CDC : table des défauts, casse,
  graphie de `kind`, chemin de `asset`.

## Précisions de la vérification structurelle

Posées en écrivant la vérification de toute la structure (`SchemaOne`) ; elles
appliquent les décisions ci-dessus aux cas que le relevé champ par champ a
laissés ouverts.

10. **Champs obligatoires sous la racine.** R-1781 rend tout optionnel hors de
    `schema`, `asset` et `kind`. Trois exceptions, parce que l'élément n'existe
    pas sans elles : le nom de tout élément que d'autres désignent (`name` des
    bodies, joints, parts, liaisons, zones, sièges et ensembles de particules ;
    `node` d'une roue), `action` d'une interaction, `source` d'une animation
    procédurale.

11. **Objets renvoyés ailleurs.** Là où le §23.4 écrit `{ }` ou `[ ]`, les clés
    sont celles de l'exemple de la section qui les définit : §12.3 (qui ajoute
    `anti_roll` à la suspension), §12.5 à §12.7, §14.8, §17.5, §18.3.
    `on_part_disabled` (R-1083) donne sa forme sans son emplacement : il
    n'appartient pas au schéma 1.

12. **Listes reprises d'une clé homonyme.** `render.shadow` (`map`, `contact`,
    `none`) et `render.lod_bias` (`-2..3`) reprennent la liste et la plage de
    leur clé de configuration (ANNEXE A.3). `animations.*.layer` est un entier
    de 0 à 3 : quatre couches, figées par R-1440.

13. **Actions.** `on_detach` emploie la liste fermée de R-1170, comme
    `on_part_stage` : ce sont les mêmes effets fonctionnels. Un argument dont le
    cahier des charges donne un exemple a sa forme ; les autres
    (`show_node`, `break_joint`, `detach_part`, `disable_seat`,
    `play_animation`, `set_material_param`) ne sont pas typés.

14. **Plafonds.** Le dépassement d'un plafond d'assembly — 64 bodies, 128
    joints, 64 parts, 16 sièges, 8 ensembles de particules (R-190), 256
    liaisons et 128 animations (C-22) — porte `E-3050`, le code de R-190. Le
    nombre de roues (1 à 32, R-1052) n'est pas un plafond d'assembly : `E-7001`.

15. **Mêmes règles que l'asset.** Masse de part dans `[0.001, 1e6]`, fractions
    dans `[0, 1]`, quatre capacités d'une liaison strictement positives, liaison
    entre deux parts distinctes : exactement ce que vérifie le validateur d'asset
    (C-22), pour qu'une même donnée ne soit pas jugée deux fois différemment.

16. **Sources procédurales.** Famille, nom éventuel et champ sont confrontés à
    l'ANNEXE A.4 ; le nom se résout contre la definition pour les roues, parts,
    liaisons, joints, sockets, sièges et ensembles de particules. `region.<n>`
    se résout contre l'asset ; `attach.<n>` et `var.<n>` désignent des éléments
    du runtime et ne se résolvent pas à la lecture.

17. **Forme publiée.** `docs/schema/definition-1.json` (JSON Schema 2020-12)
    est **rendu** depuis l'arbre du validateur, jamais écrit à la main ; un test
    échoue dès qu'il en diffère. Ce que JSON Schema n'exprime pas — unicité des
    noms, résolution des références, liaison entre parts distinctes, cycles de
    zones, module `vehicles` — y figure en annotations `x-axion-declares`,
    `x-axion-refers` et `x-axion-code`, ignorées par les validateurs tiers et
    vérifiées par AXION. La CI juge chaque definition du dépôt avec le
    validateur, qui est le schéma exécutable ; aucun validateur JSON Schema tiers
    n'est ajouté à l'outillage, que le §32.4 ne prévoit pas.
