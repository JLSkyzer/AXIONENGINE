# ADR-133 — Métriques de rendu, mémoire native et textures : ce qui reste à compter

- **Statut** : **accepté** — D1, D2 et D3 tranchés par Killian le 2026-10-13 : l'option A, recommandée, pour les trois
- **Date** : 2026-10-13
- **Portée** : R-500, R-502, R-1850, INV-08, INV-19, R-480, R-482, R-750, R-2260, §31.1 ; C-13,
  C-15, C-60, C-62 ; budgets `render_prep_ns`, `gpu_mem_bytes`, `max_visible_instances`,
  `max_triangles_frame`, `max_decals_frame`, `max_shadow_instances`, `idle_hook_ns`,
  `native_mem_bytes`
- **Proposé par** : Claude, à la tranche E1 de la clôture de M3

## Contexte

L'inventaire du 2026-10-13 (vérification de la Definition of Done de M3) a établi :

1. **Budgets.** Le registre déclare la consommation et le dépassement des vingt budgets
   (`axion.budget.<nom>.consumed` / `.overruns`) et les exporte tous. Le natif alimente depuis
   `cfb33e0` ceux qu'il mesure : `sim_ns_per_tick`, `submit_ns`, `max_active_bodies`,
   `native_mem_bytes` (partiel, voir 3) et les budgets de durée de ses jobs. Les budgets de
   **rendu** et `idle_hook_ns` se mesurent **côté Java**, et rien ne les porte à l'export :
   `/axion metrics export` écrit tel quel le JSON du natif, et aucune fonction ne permet à Java
   d'y ajouter une métrique.
2. **Rendu.** Les statistiques existent en Java sans sortir du client : `FrameStats`, temps des
   variantes de shaders, `ShaderStats`, backend actif, objets GL vivants, octets des arènes GPU
   (`NativeMeshes.gpuBytes`), `GpuBudget.chargedBytes`. Un dépassement du budget GPU n'est
   qu'un avertissement émis une fois. Il n'y a ni temps GPU par passe (requêtes de minuterie),
   ni compte de draw calls ou de triangles.
3. **Mémoire native (INV-08).** `ax-mem` compte à la main : l'arène persistante ne voit que les
   assets chargés. Les mondes `rapier` — corps, colliders, structures de la phase large — ne
   sont comptés nulle part, ni les tampons de transfert dans une arène. T-016 ne vérifie donc
   l'équilibre que de ce qui est compté.
4. **Textures (R-750).** Les textures qu'AXION décode et téléverse (`AxionTexture`,
   `VanillaTexturePipeline`) ne sont pas imputées à `GpuBudget`, qui ne compte que sommets et
   indices. L'ADR-127 dit les textures « référencées, jamais possédées » mais aussi « toute
   allocation est comptée » ; les deux phrases ne visent pas les mêmes textures.

Un seul `AxionRuntime` existe par JVM : en solo, le client et le serveur intégré partagent le
même runtime et le même contexte natif. Sur un client relié à un serveur distant,
`/axion metrics export` s'exécute sur le serveur et ne voit pas le rendu du client.

## Décisions demandées

### D1 — Comment les métriques Java entrent dans l'export

- **A (recommandée) : un registre Java fusionné par `AxionRuntime.metricsJson()`.** Les
  composants Java déclarent leurs métriques (mêmes noms `axion.budget.*`, mêmes types) dans un
  registre du runtime ; l'export ajoute ses entrées à la liste du JSON natif, au même schéma.
  Ni ABI ni format ne changent. Le rendu d'un client distant s'exporte par une commande
  cliente (`/axion diag dump`, R-442, ou une variante client de `metrics export`).
- B : une fonction FFI `axion_metrics_set` qui pousse les valeurs Java dans le registre
  natif. Un export unique, mais une **ABI 4** et une traversée de plus par métrique et par
  frame (INV-04 compte les traversées par tick).

### D2 — Comment compter la mémoire native (INV-08)

- **A (recommandée) : un allocateur compteur global dans `ax-ffi`** (`#[global_allocator]` sur
  l'allocateur système), qui impute chaque allocation à une arène — persistante par défaut,
  `SCRATCH` dans les jobs, celle du monde physique pendant un pas — par une étiquette de thread
  posée en portée. Rien n'échappe au comptage, comme le veut R-480. Coût : une addition
  atomique par allocation et par libération, **à mesurer** (B-08 ou un banc dédié) avant
  d'être accepté ; aucun chiffre n'est avancé ici.
- B : une estimation par structure (corps × taille, colliders × taille de forme). Moins chère,
  mais une estimation n'est pas un comptage : INV-08 ne serait pas tenu, seulement approché.

### D3 — Quelles textures comptent dans `budgets.gpu_mem_bytes`

- **A (recommandée) : celles qu'AXION décode et téléverse**, chaîne de mips comprise, imputées
  à `GpuBudget` à l'envoi et rendues à leur libération ; l'éviction LRU de R-750 les décharge
  avec leurs assets. Les textures de Minecraft qu'AXION ne fait que référencer (atlas, packs de
  ressources) restent hors budget — c'est le sens de « référencées, jamais possédées ». Le
  backend vanilla, qui téléverse les mêmes textures, porte alors le même budget.
- B : ne rien compter des textures, et le dire : R-750 n'est alors pas tenu.

## Ce qui ne dépend pas de ces décisions

Une fois D1 tranchée, chaque budget de rendu reçoit la mesure qui existe déjà (préparation de
frame, instances visibles, octets GPU) ; le temps GPU par passe demande des requêtes de minuterie
OpenGL, mesurées et désactivables (R-2262), et se traite à part.

## Mise en œuvre

- **D3** (2026-10-13) : `TexturePipeline.Prepared.gpuBytes()` (niveaux de mipmaps compris, RGBA8) ;
  `MeshCache` tient le budget pour les deux backends (`GpuBudget<String>` par chemin d'asset, frame
  vue à chaque `get`) et, une fois par frame avant la passe opaque (`AxionRenderPass`), décharge en
  entier — maillage du backend, textures, handle natif — l'asset non vu le moins récent tant que
  textures et maillages dépassent `budgets.gpu_mem_bytes`. `NativeMeshes` n'a plus de budget propre.
  Tests : `MeshCacheTest` (textures comptées, éviction et rechargement, asset vu jamais déchargé,
  asset sans texture déchargé pour ses maillages).
- **D1** (2026-10-13) : `dev.axion.diag.JavaMetrics`, registre du processus fusionné par
  `AxionRuntime.metricsJson()` — une métrique Java de même nom qu'une entrée native en donne la
  valeur, sous le type et l'unité natifs ; les autres s'ajoutent, `metric_count` suit, le schéma
  reste 1. Alimentés : `render_prep_ns` (temps CPU des passes d'AXION par frame), `gpu_mem_bytes`
  (octets tenus, dépassement par frame qui a dû décharger), `max_visible_instances`,
  `max_triangles_frame`, `idle_hook_ns` (hook de tick sans corps ni événement), et les jauges
  `axion.render.*` (backend, octets de textures et de maillages, évictions, objets GL, shaders).
  `max_decals_frame` et `max_shadow_instances` restent à zéro : ni décalques ni ombres n'existent.
  Tests : `JavaMetricsTest`. **Reste** : la commande cliente qui exporte le rendu d'un client relié
  à un serveur distant (`/axion metrics export` y tourne sur le serveur), à vérifier en jeu.
