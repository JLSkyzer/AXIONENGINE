# ADR-162 — L'API d'enregistrement du contenu : un mod Java déclare ce qu'AXION connaît

- **Statut** : **accepté** le 2026-11-10 par Killian, tel que proposé, Q1 à Q3 comme proposé : builder généré
  depuis le schéma, API découpée en paquets dans la tranche 1, configuration `axion-server-overrides.toml`. Les
  choix de fond sont les siens (ADR-160 D9 et D10).
- **Date** : 2026-11-10
- **Portée** : C-27 (registres de contenu), C-70 (`axion-api`), C-51 (handshake, envoi du registre), C-52 (identifiants
  au NBT), R-1750 à R-1790, EX-01, EX-04, EX-05 ; ADR-137 et ADR-143 (amendés) ; capacités CAP-11, CAP-33 (en
  partie), CAP-40, CAP-44 à CAP-52.

## Contexte

Killian, le 2026-11-10 : tout passe par un mod Java et l'API ; le JSON reste optionnel mais c'est le mod qui le
charge ; le chargement par datapack est supprimé (ADR-160 D9). Ses onze réponses à l'audit 4 fixent le reste
(ADR-160 D10) : API activée dès M5, registre propre à AXION, dossier lu dans le JAR du mod, resource packs pour
l'apparence seule, espace de noms imposé, client sans l'addon refusé, configuration serveur bornée pour les
administrateurs, exemples par l'API publique, étage Java au tick, publication Maven dès M5, `@Experimental` jusqu'au
prononcé de M5.

Ce qui existe : six écouteurs de rechargement de datapack (`AxionForgeEntrypoint`) pour les modèles, matériaux
physiques, groupes de collision, blocs vers matériaux, pneus et definitions ; un identifiant tiré du chemin de fichier
(`DefinitionRegistry`) ; une empreinte calculée sur le fichier (`Definition`) ; le registre envoyé au client sous forme
de textes JSON (`RegistryContent`, `ServerHandshake`) ; `axion-api` en 60 types, dont 34 vides, sans fournisseur
(`AxionApi.get()` lève). L'inventaire complet de ce que la suppression touche est dans ADR-160 D9.

## Décision

### D1 — Le fournisseur, et la règle d'ADR-137 et d'ADR-143 amendée

`axion-mod` fournit `AxionApi` par `ServiceLoader` (`META-INF/services/dev.axion.api.AxionApi`), dès cette
tranche. La règle « pas de fournisseur tant qu'un accesseur n'est pas réel » devient : **la surface publique ne
contient que ce qui est réel**. Un service d'un jalon futur (déformation M6, structure M7, surface M9) n'y figure pas
encore : il y entre à son jalon, en méthode `default` qui ne casse aucun addon. Rien ne lève « pas encore
disponible » : ce serait un stub, interdit par R-001. Les 34 types vides d'ADR-143 restent tant qu'une signature en
a besoin, et ne gagnent un membre qu'avec son implémentation.

### D2 — Une phase d'enregistrement séquentielle

AXION ouvre l'enregistrement dans `FMLCommonSetupEvent.enqueueWork`, donc sur le thread principal, une fois les mods
construits, et le parcourt **mod par mod, l'un après l'autre** : il poste `AxionRegisterEvent` sur le bus de chaque
mod qui dépend d'AXION. Deux passes :

1. **les extensions** : sources procédurales, contrôleurs, étages de véhicule, types d'interaction, de son et de
   lumière (ADR-160 D5) ;
2. **le contenu** : matériaux physiques, groupes de collision, blocs vers matériaux, pneus, definitions, modèles.

AXION résout ensuite tout en une passe, dans un ordre écrit (matériaux, groupes, pneus, puis definitions), au lieu de
l'ordre implicite des écouteurs d'aujourd'hui. La partie propre au client (hooks de rendu, évaluation des sources
procédurales) s'enregistre de même dans `FMLClientSetupEvent.enqueueWork`, par `AxionRegisterClientEvent`. Hors de
ces phases, enregistrer lève une erreur nommée.

Une definition qui veut son item ou son bloc de Minecraft (CAP-27, CAP-28) le déclare à Forge elle-même, avant le gel
des registres. L'aide qu'AXION apportera à ce sujet est l'affaire de M10.

### D3 — Ce que voit le moddeur

```java
@SubscribeEvent
static void enregistrer(AxionRegisterEvent event) {
    // Tout ce que contient axion/ dans le JAR de ce mod : JSON et GLB.
    event.registerFolder("axion/");
    // Ou en Java : la même definition, construite par le builder.
    event.definitions().register("patrouille", Definition.vehicle()
            .asset("patrouille.glb")
            .mass(1900.0)
            .wheel("roue_av_g", w -> w.radius(0.53).steering(true))
            .build());
}
```

- **L'espace de noms est le modId** : `register("patrouille", …)` enregistre `policemod:patrouille`. Un mod ne
  déclare que dans le sien.
- **`registerFolder`** lit le dossier du JAR de **ce** mod, et rien d'autre : `axion/definitions/`,
  `axion/models/`, `axion/physics_materials/`, `axion/collision_groups/`, `axion/block_materials/`, `axion/tires/`.
- **Remplacer l'entrée d'un autre mod** passe par `event.replace(id, …)`, explicite. La trace nomme les deux mods.
  Un doublon sans `replace` est refusé, et l'erreur nomme les deux mods.
- **Chaque entrée garde son propriétaire** (le modId), sa source (le fichier du JAR, ou l'appel du builder) et son
  empreinte. Les erreurs (R-580, R-1761) les citent toutes les trois.

### D4 — Une forme canonique unique

Le builder Java et le JSON produisent **le même document**, validé par le même `SchemaOne`. Il est sérialisé de
façon canonique : clés triées, nombres normalisés, aucun espace. L'empreinte (sha256) se calcule sur cette forme et
non sur le fichier, si bien qu'un même contenu a la même empreinte, qu'il vienne du JSON ou du Java (CAP-47). Un
builder n'accepte aucune lambda dans ce qu'il produit : la definition doit pouvoir partir chez le client (R-581). Les
extensions s'y désignent par leur identifiant.

### D5 — Modèles et resource packs

Les GLB viennent du JAR du mod qui les enregistre, au serveur comme au client : les colliders se compilent au serveur
à partir du JAR, jamais d'un pack. Au client, un resource pack peut remplacer **l'apparence** d'un modèle ou d'une
texture (`assets/<modid>/axion/models/…`) : forme visible, textures, livrées. Jamais sa physique ni sa definition
(ADR-160 D10.4). Le remplacement sert au rendu seulement ; les colliders restent ceux du serveur.

### D6 — Identifiants et mondes existants

Les identifiants des exemples (`axion:example/*`) et du contenu de test (`axion:test/*`) ne changent pas : le NBT
garde l'empreinte de l'identifiant (`axion:def`), et les mondes de M1 à M5 restent lisibles. Le contenu de test et
celui des films s'enregistrent dans l'espace `axion`, par le contenu de développement.

### D7 — Client et serveur

Le serveur reste l'autorité : il envoie toujours le registre résolu (documents canoniques), puisque la configuration
d'un administrateur (D8) peut y changer des valeurs. Le handshake ajoute la **liste des mods propriétaires de
contenu, avec leur version**. Un client à qui il manque un addon, ou qui l'a dans une autre version, est refusé avec
un message qui nomme l'addon et la version attendue (ADR-160 D10.6). Le code Java d'une extension ne voyage jamais :
il doit être installé des deux côtés, ce que le refus garantit.

### D8 — Ce qu'un administrateur règle sans code

`config/axion-server-overrides.toml` contient des surcharges bornées, lues avant la résolution :

- des multiplicateurs, dans des bornes, sur les grandeurs d'un matériau physique ou d'une definition (masse, couple,
  adhérence) ;
- des correspondances bloc vers matériau, pour les blocs d'un mod tiers.

Il ne permet aucun nouveau contenu. Chaque surcharge entre dans l'empreinte et se nomme dans les erreurs (CAP-51).

### D9 — Recharger en développement

`/axion dev reload` (opérateur, et seulement si `content.dev_reload` est vrai, faux par défaut) relance
l'enregistrement de chaque mod, relit les dossiers depuis le disque quand le mod tourne depuis ses sources, résout et
renvoie le registre aux clients (CAP-50). Les assemblies déjà posées gardent leur definition jusqu'à CAP-33.

### D10 — Ce qui disparaît, ce qui reste

- **Disparaissent** : les six écouteurs de rechargement de datapack, la lecture des definitions et registres sous
  `data/<ns>/axion/` par le gestionnaire de ressources, `/reload` comme moyen de recharger AXION.
- **Reste un datapack** : `data/axion/damage_type/collision.json`, registre dynamique de Minecraft lui-même,
  par exception écrite.
- **Les exemples d'AXION** s'enregistrent par `AxionRegisterEvent` et l'API publique, comme un addon, sous
  `content.examples` (ADR-160 D10.8). Ils prouvent EX-01 en CI.
- **Les textes du CDC** qui décrivent le chargement par datapack (C-27, 23.3, R-171, R-1030, R-1640, 28.1, R-1783,
  R-1790, conflits 19 et 21 de la PARTIE 38), ainsi que le premier paragraphe d'ADR-160 D5, sont réécrits par la
  tranche 1. Le registre 38.9 reçoit l'amendement A8.

### D11 — Distribution et stabilité

- **L'artefact** `dev.axion:axion-api:<version de l'API>` est publié sur GitHub Packages à chaque version
  (ADR-160 D10.10). Un addon le déclare en `compileOnly` et ne l'embarque jamais : le paquet `dev.axion.api` serait
  sinon présent dans deux modules.
- **La dépendance** : un addon la déclare dans son `mods.toml` (modId `axion`). Il annonce aussi, à
  l'enregistrement, la version d'API qu'il exige ; AXION refuse clairement une version trop ancienne.
- **La nouvelle surface** est `@Experimental` jusqu'au prononcé de M5, puis `@Stable`. Une garde de compatibilité
  binaire entre alors en CI (CAP-52). Toute interface qu'un addon implémente ne gagne plus que des méthodes
  `default`.

### D12 — L'étage Java d'un véhicule

L'enregistrement d'un étage (`VehicleStage`) est réservé par la passe des extensions de D2. Son contrat est celui
d'ADR-160 D10.9 : appelé au tick, il rend des paramètres que le cœur natif applique à chaque sous-pas. Il se conçoit
avec la tranche 5 de C-33, en même temps que les paramètres d'instance.

## Questions à Killian — tranchées le 2026-11-10, comme proposé

- **Q1 — Le builder Java.** Proposé : le **générer** depuis le schéma de definition par `tools/codegen`, pour qu'il
  ne diverge jamais du JSON. Autre voie : l'écrire à la main, plus lisible mais à tenir en phase à chaque champ ajouté.
- **Q2 — Découper l'API en paquets** (ADR-161 D5) tant qu'elle est `@Experimental` : `dev.axion.api.content`,
  `….vehicle`, `….event`, `….physics`, `….render`… Proposé : oui, dans la tranche 1. Autre voie : garder un seul
  paquet de 60 types et plus.
- **Q3 — Le nom de la configuration des administrateurs.** Proposé : `axion-server-overrides.toml`, à côté des
  fichiers de configuration existants.

## Précisions de mise en œuvre

### Tranche 1 (2026-11-11)

- **1a — Paquets.** `dev.axion.api` garde la façade ; `assembly`, `content`, `event`, `damage`, `physics`,
  `attachment`, `vehicle` reçoivent leurs types.
- **1b — Les messages entre mods plutôt qu'un événement Forge.** D2 prévoyait un `AxionRegisterEvent` posté sur le
  bus de chaque mod. Un événement Forge ne peut pas vivre dans l'API : R-401 interdit `net.minecraftforge.*` hors de
  `dev.axion.forge`. Un mod envoie donc un `ContentProvider` (type de l'API, pur Java) par `InterModComms`, pendant
  `InterModEnqueueEvent` ; AXION les appelle dans `InterModProcessEvent.enqueueWork`, sur le thread principal, l'un
  après l'autre, triés par modId. Forge certifie le mod expéditeur : un mod ne peut pas enregistrer au nom d'un
  autre (CAP-46). Une seule passe pour l'instant : aucune extension ne s'enregistre encore, la passe des extensions
  viendra avec la première (sources procédurales, tranche 4 de C-33) ; de même l'enregistrement propre au client.
- **1c — Le branchement.** Le registre (`ContentRegistry`) rend chaque famille avec les clés que les registres
  lisaient déjà, `<modId>:axion/<famille>/<chemin>` : aucun registre n'a changé. Les écouteurs de rechargement du
  serveur restent, pour le cycle de vie (démarrage, `/reload`), mais remettent le contenu enregistré au lieu de lire
  les datapacks ; `/reload` ne relit donc plus rien (le rechargement en développement est la tranche 4). Le client
  lit les resource packs en préparation et les modèles enregistrés en application : son premier rechargement se
  prépare pendant le chargement des mods, avant l'enregistrement ; l'application suit la barrière qui l'attend.
- **Le contenu du dépôt** quitte `src/*/resources/data/axion/axion/` : les exemples pour `content/examples/axion/`,
  le contenu de test pour `content/test/axion/`, la Charger pour `local/contenu/axion/` ; Gradle en fait des dossiers
  de ressources, et AXION enregistre un seul dossier, `axion/`, à la racine de son JAR. Restent en datapack ce qui
  est à Minecraft : le type de dégâts `collision`, les structures et scénarios des GameTests.
- **T-713f** (un modèle que le serveur a et que le client n'a pas, R-1640) ne passe plus par un datapack de monde :
  le banc remet au seul serveur le contenu enregistré plus une definition et un modèle ; le client garde les siens.
- **1d — Le fournisseur, sur une surface ramenée au réel.** `ForgeAxionApi` est déclaré à `ServiceLoader`
  (`META-INF/services/dev.axion.api.AxionApi`). `AxionApi` ne porte plus que `version()` et `assemblies()` ;
  `AssemblyService` (`spawn`, `byEntity`, `inRange`) passe par le chemin de `/axion spawn` ; `Assembly` ne porte plus
  que `id`, `definition`, `entity`, `transform`, `animation`, `customData`, `isValid`, `remove`. Les quarante-deux
  types qu'aucune signature réelle n'exigeait plus quittent la surface : les dix-huit événements, `EventBus` et
  `Subscription` ; les services physique, dommage, déformation, attaches, assets, definitions, registres,
  diagnostics et qualité, avec `RuntimeState` ; les vues de pièces, de structure, de déformation, de surface et de
  particules ; `Socket`, `VehicleControl`, `PartStage`, `RepairLevel`, `QualityLevel`. Chacun revient, réel, avec son
  composant (CAP-11). `ImpactSource`, vide mais exigé par `ImpactSpec`, reste, et `ApiDeclaredTypesTest` le garde
  seul dans sa liste. Un GameTest (`ApiPubliqueGameTests`) joue le service comme un mod tiers.
- **Vérifié** : neuf tests du registre (mutation des doublons rouge) ; GameTests sur serveur dédié ; banc de rendu
  vanilla, natif et sous Oculus, T-713f compris ; T-284 parcourt `content/` et exige d'y trouver les cinq exemples ;
  T-006 recense aussi `content/` pour INV-01.

### Tranche 2 (2026-11-11)

- **2a — La forme canonique** suit la canonicalisation JSON du RFC 8785 : aucun espace, clés triées par unités
  UTF-16, tableaux dans leur ordre ; une chaîne n'échappe que les guillemets, la barre oblique inverse et les
  caractères de contrôle. Un nombre est la valeur `double` qu'il désigne, écrite par le plus court décimal qui la
  redonne, à la façon de JavaScript (`1`, `1.0` et `1e0` s'écrivent `1`). Ce plus court décimal se calcule par
  `BigDecimal` à partir de la valeur exacte : `Double.toString` a changé de sortie avec le JDK 19, et un serveur et
  un client sur deux JDK doivent calculer la même empreinte. Aucun champ du schéma n'admet d'entier au-delà de
  2^53, où un `double` cesserait d'être exact. L'empreinte d'une definition (`Definition.sha256`) porte désormais
  sur cette forme et non sur les octets du fichier ; elle n'entrait encore dans aucun échange réseau, qui viendra
  avec la tranche 3.
- **2b — Une definition construite en Java** est un `DefinitionDocument` de l'API : un arbre des seules valeurs de
  JSON (chaînes, booléens, nombres finis rangés en `Long` ou `Double`, listes, tables à clés textuelles), copié et
  figé à la construction ; tout autre objet, `null` ou une lambda sont refusés en nommant leur chemin (R-581).
  `ContentRegistrar.register(name, document)` déclare `<modId>:<name>` ; `replace(target, document)` remplace la
  definition d'un autre mod. Le registre la range comme un fichier virtuel, `<modId>:axion/definitions/<name>.json`,
  dont les octets sont la forme canonique : validation par `SchemaOne`, doublons, remplacements, empreinte et envoi
  aux clients sont ceux d'un fichier, et un fichier et une definition Java de même nom sont un doublon. La source
  nommée dans les messages est `<modId> — builder, register("<name>")`.

## Tranches

1. **Le fournisseur et le registre.** `AxionApi` fourni (D1). Phase d'enregistrement (D2). Événements,
   `registerFolder`, espace de noms, propriété, doublons et `replace` (D3). Exemples, contenu de test et des films
   migrés (D6, D10). Écouteurs de datapack retirés. Textes du CDC réécrits. Tests et GameTests sur la nouvelle voie.
   Le dossier `content/` d'ADR-161 D3 naît ici.
2. **Le builder et la forme canonique** (D4), avec l'empreinte calculée sur le document.
3. **Handshake des addons, configuration des administrateurs** (D7, D8).
4. **Rechargement en développement** (D9).
5. **Publication et addon témoin.** Artefact Maven, guide d'addon, un addon témoin compilé contre `axion-api` seul,
   en CI (D11, CAP-48, CAP-49).
6. **Garde de compatibilité binaire**, au prononcé de M5 (CAP-52).

Chaque tranche se ferme à la grille transversale d'ADR-160 D7. La tranche 4 de C-33 reprend après la tranche 1,
écrite directement sur cette API.
