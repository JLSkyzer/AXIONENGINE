# ADR-142 — `bench-quick` en CI : non bloquant le temps de mesurer le bruit, puis bloquant (R-2250, R-2251)

- **Statut** : **accepté** — le principe (non bloquant, puis bloquant) est tranché par Killian le
  2026-10-15 ; le critère de bascule (§3) est proposé par Claude et se confirme au moment de basculer.
- **Date** : 2026-10-16
- **Portée** : R-2250, R-2251, R-2252, R-2231 ; C-72 ; job `bench-quick` de 34.3 ; ADR-131
- **Constat d'origine** : audit de la DoD de M2 (2026-10-15) — aucun job de benchmark en CI

## Contexte

R-2250 veut que la CI exécute un sous-ensemble rapide de benchmarks et le compare au dernier résultat
archivé de la même plateforme ; R-2251, qu'une hausse de plus de 20 % du p95 bloque la fusion. Le dépôt
avait le coureur (`bench-ci`, C-72) et l'outil de comparaison (`tools/bench/bench.py`), mais aucun job.

Deux obstacles :

1. **La machine change.** Un runner GitHub partagé n'a pas toujours le même processeur ; comparer deux
   mesures de processeurs différents ferait d'une différence de matériel une régression.
2. **Le bruit est inconnu.** Deux exécutions consécutives du même code, sur la même machine locale, ont
   déjà différé de l'ordre de 10 % sur B-09 (diagnostic local du 2026-10-16, non publiable, R-2252). Sur
   des runners partagés, l'écart peut être plus grand ; bloquer à 20 % sans le connaître produirait de
   faux rouges, et une CI qui crie au loup cesse d'être lue.

## Décision

### 1. Le job

`bench-quick` (`.github/workflows/ci.yml`) mesure les benchmarks de R-2250 dont le composant existe —
**B-02 et B-09** ; B-01, B-07, B-11, B-18, B-19, B-21 et B-23 entrent avec le leur, ou avec un banc en
jeu pour B-07 — en configuration rapide, et compare chaque p95 au dernier résultat **de la même
machine** :

- la machine est le **modèle de processeur** du runner (`lscpu`) ; la référence vit dans le cache
  d'Actions sous une clé qui le nomme, et n'est restaurée que pour lui ;
- un résultat ne devient référence qu'après un run **sans régression** sur `master` : une régression
  ne masque pas la suivante ;
- chaque série garde ses cinq derniers résultats ; ils sont aussi téléversés en artefact.

Ces chiffres détectent des régressions grossières ; ils ne se publient pas (R-2252, ADR-131).

### 2. Non bloquant d'abord

Le job porte `continue-on-error: true` : une régression le marque en échec et se voit dans la CI, sans
bloquer la fusion. **C'est un écart temporaire à R-2251**, consigné ici.

### 3. Critère de bascule

Le job devient bloquant (retrait de `continue-on-error`) quand, pour le modèle de processeur le plus
fréquent des runners, **vingt runs consécutifs sur `master`** ont été comparés à leur référence et que
**l'écart relatif du p95 de chaque série est resté sous 10 %** hors changement du code mesuré. Si le
bruit ne descend pas sous ce seuil, la décision revient à Killian : allonger la mesure, ou changer de
machine de mesure — pas relever le seuil de R-2251.

### 4. R-2231

Un résultat archivé porte désormais sa configuration de mesure (`MeasureConfig::describe` : mode,
échauffement, exécutions, durée, plafond d'échantillons, profil de compilation), dans `bench-ci` comme
dans le coureur de B-08. `/axion bench` écrit le commit que le build a compilé — ressource
`axion-build.properties` générée par Gradle, suffixe `-dirty` si l'arbre suivi était modifié — au lieu
du marqueur `ingame-dev`.

## Conséquences

- R-2250 est tenue pour les benchmarks qui existent ; R-2251 l'est en signalement, jusqu'à la bascule.
- La DoD de M2 compte `bench-quick` comme fait (ADR-137) ; la bascule est suivie dans `tasks/todo.md`.
- Les benchmarks à venir s'ajoutent à `bench-ci` avec leur composant, et entrent dans ce job sans le
  changer.
