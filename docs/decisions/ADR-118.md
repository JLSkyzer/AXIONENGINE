# ADR-118 — Couture de rendu : abstraction de backend, passe `RenderLevelStageEvent`, acheminement du maillage (GEOM) au client

- **Statut** : **accepté** — les deux bifurcations structurantes (backend **vanilla d'abord**,
  **décodage GEOM en natif via FFI**) ont été ratifiées par Killian le 2026-10-01. Le reste de
  la couture ci-dessous découle de la PARTIE 19 et de l'état constaté du code ; soumis pour
  confirmation avant la tranche 1.
- **Date** : 2026-10-01
- **Portée** : C-60, C-61, C-62 (indirect), C-50, C-40 (position interpolée), IF-03 / ABI
  (nouvelle fonction FFI de décodage GEOM), R-1490, R-1491, R-1492, R-1570, R-740..R-744,
  R-1493, R-401 / T-020, §19.1, §19.2, §19.10, §19.4 ; R-1500..R-1505 et format d'upload GPU
  **différés** à l'ADR de C-60 natif.
- **Proposé par** : Claude, en ouvrant la chaîne de rendu ; **ratifié par** : Killian le
  2026-10-01 (choix de backend et de lieu de décodage).

## Contexte

La moitié physique de M3 (C-31→C-40) est faite et observée en jeu ; une `AxionEntity` tombe,
repose, se recharge. Mais elle n'a **aucune géométrie rendue** : le seul rendu client est
`AxionEntityRenderer`, un `EntityRenderer` de debug qui dessine le libellé de la definition
quand les hitbox vanilla sont affichées. On ouvre la chaîne de rendu pour afficher le **vrai
maillage**.

**Ce que PARTIE 19 impose.** AXION rend ses objets **en plus** du monde vanilla, dans le même
framebuffer, via `RenderLevelStageEvent` (§19.1). Il existe **deux backends** (§19.2, R-1490..
R-1492) :

- **NATIVE_GL (C-60)** — pipeline OpenGL dédié (VAO/VBO/UBO/TBO, shaders GLSL, PBR, instancing,
  skinning + déformation GPU, ombres, occlusion). Chemin par défaut, le plus lourd ; s'appuie
  sur C-62 (GPU Resource Manager), C-63 (shaders) et C-81 (sonde d'environnement).
- **VANILLA_CONSUMER (C-61)** — rend à travers Minecraft (`RenderType` / `VertexConsumer` /
  `PoseStack`), **sans appel GL direct ni shader propre** (R-741), skinning/déformation **CPU**
  plafonnés (R-742). Repli universel, **obligatoire** sous shaderpack (Iris/Oculus). Les deux
  backends partagent des **invariants géométriques** stricts (§19.2bis, R-1492) ; leurs
  capacités visuelles diffèrent selon une matrice déclarée (R-1493).

**État constaté (enquête 2026-10-01).**

- **Assets côté client.** La compilation A3D est pilotée **côté serveur** (dédié ou intégré) :
  découverte sur `AddReloadListenerEvent`, pompage dans `onServerTick`. En **solo**, client et
  serveur intégré partagent le **même `AxionRuntime`** (singleton `@Mod`) — les octets A3D
  compilés sont donc en mémoire (`runtime.assets()`), mais **non exposés** au paquet
  `dev.axion.forge.client` (seules les definitions le sont, et en package-private). En
  **multi**, rien n'est compilé ni transmis au client (le contexte natif y tourne pourtant :
  une compilation client sera possible plus tard).
- **Format GEOM.** Le maillage est la section `GEOM`, écrite **compressée (zstd)**.
  `A3dSections` (seul lecteur Java) localise les sections mais **refuse le compressé** : côté
  Java on ne décode jamais le *contenu* d'un A3D — c'est Rust qui le fait (précédent : `PHYS`
  est passé tel quel au natif, qui le décode via `decode_colliders`). Disposition GEOM
  (décompressée) : en-tête 16 o + table de meshes (48 o) + sommets (48 o, = le sommet GPU du
  §19.4) + indices `u32`. Le bloc d'instance (88 o) est construit **au runtime**, hors A3D.

## Décision

### 1. Abstraction de backend + sélection (R-1490)

Une interface `RenderBackend` (paquet `dev.axion.forge.client`) que les deux backends
implémentent. `VanillaConsumerBackend` est livré maintenant ; `NativeGlBackend` viendra avec
C-60. La sélection (`render.backend = auto|native|vanilla`, R-1490) choisit à l'init et
re-évalue au chargement du monde / changement de resource pack / changement de shaderpack.
Tant que le natif n'existe pas — ou sous shaderpack, ou si l'init natif échoue — `auto`
retombe sur **vanilla**, ce qui est déjà le comportement correct de repli (R-1491 : vanilla
n'est jamais un chemin mort).

### 2. Passe de rendu : `RenderLevelStageEvent`

Une **passe centrale** s'abonne à `RenderLevelStageEvent`, collecte les `AxionEntity` visibles
et les confie au backend actif — et non un rendu par entité : la spec veut un passage unique
(instancing/batching C-65, culling C-64 à venir). Premier périmètre : **passe OPAQUE au stage
`AFTER_ENTITIES`** (R-1570). L'`EntityRenderer` existant est **conservé pour le seul libellé de
debug** (lignée C-67) ; la géométrie passe par la passe centrale.

La discipline d'état GL (`GlStateGuard`, R-1500..R-1505, INV-12) ne concerne que le backend
**natif** : le backend vanilla ne touche pas l'état GL (il passe par `RenderType`, qui le gère)
— elle est donc **différée** à l'ADR de C-60.

### 3. Acheminement du maillage — décodage GEOM en **natif via FFI** (ratifié) `[EFFORT MAX]`

Conforme au partage déjà en place (Rust possède le format A3D ; Java localise les sections et
passe les octets) : Java fournit au natif les octets A3D (comme pour `PHYS`), le natif
**décompresse et décode GEOM**, et renvoie **sommets + indices** par le **protocole de tampons**
existant (IF-03). Java construit alors, **une fois par asset**, un *renderable* client (maillage
mis en cache) réutilisé à chaque frame.

- C'est une **nouvelle surface FFI/ABI** (une fonction de décodage, pas un opcode `SimIn`) →
  **effort maximal**, transcription + test de disposition comme les autres DM, **après** le feu
  vert « effort max ». `CommandStreamHeader::CURRENT_SCHEMA` **inchangé** (ce n'est pas une
  commande de tick).
- **Périmètre : solo d'abord.** Les octets sont en mémoire via un accesseur client (point 4).
  Le **multi** (compilation client, ou transport réseau de GEOM) est une **tranche ultérieure**
  explicitement différée.
- Rien ne duplique le format A3D côté Java, et aucune dépendance zstd Java n'est ajoutée.

### 4. Accesseur assets côté client

Exposer les assets compilés à `dev.axion.forge.client` (miroir de l'accès aux definitions),
pour suivre `AxionEntity.definitionId() → Definition.asset() → AssetEntry.compiled()` — le même
chemin que `AssemblyRuntime.physOf` côté serveur. **Contrainte de threading** : l'`AssetRegistry`
est muté par le thread autoritatif ; le renderable client est construit **paresseusement et mis
en cache** depuis des octets `compiled()` **immuables** (entrée terminée), la lecture de la
registry étant protégée. En multi, l'accesseur rend « indisponible » proprement (pas d'asset),
sans erreur.

### 5. Backend vanilla (C-61), premier rendu

`VanillaConsumerBackend` dessine le maillage mis en cache via un `RenderType` (opaque/cutout) +
`VertexConsumer` + `PoseStack`, positionné à la **position interpolée** de l'entité (la couture
d'interpolation posée plus tôt aujourd'hui). Les attributs GEOM quantifiés sont dé-quantifiés
pour `VertexConsumer` (normal/tangent `i8÷127`, uv `UNORM16`, couleur `UNORM8`). Skinning/
déformation CPU (R-742), décalques (R-743) et matrice de capacités (R-1493) : **tranches
suivantes**.

### 6. Tranches

- **T1 — couture + preuve de passe** (effort élevé) : `RenderBackend` + sélection (R-1490),
  passe `RenderLevelStageEvent` @ `AFTER_ENTITIES`, accesseur assets client. Le backend vanilla
  dessine une **boîte placeholder** à la position interpolée. Valide la passe de bout en bout
  **sans** GEOM ni FFI.
- **T2 — vrai maillage** `[EFFORT MAX]` : fonction FFI de décodage GEOM (natif) + cache de
  renderable client + rendu du maillage réel par le backend vanilla (T-474 : assembly visible,
  orientée, éclairée).
- **T3+** : plafonds CPU skinning/déformation (R-742), décalques (R-743), bascule Iris→vanilla
  (R-740 / T-490), matrice de capacités (R-1493) ; puis le **backend natif C-60** (sa propre
  pile C-62→C-63→pipeline→PBR, son propre ADR).

*Précision (2026-10-02, décision de Killian)* : T3 se limite à ce que l'existant permet —
stages de passes conformes à R-1570 et matrice de capacités de R-1493 (entrée de journal
au démarrage du backend, section « rendu » de `/axion status`). R-742, R-743, R-744 et
T-490..T-492 sont rattachés aux composants qui les rendent possibles (C-66, M6, C-69,
C-60) ; l'indicateur d'overlay à C-73 ; l'exposition API de R-1495 attend un ADR, `render()`
étant absent de l'API du §23.2. C-26 (textures et matériaux) vient ensuite.

## Ce qui est explicitement différé (ADR de C-60 natif)

Format d'upload GPU sommet (48 o) / instance (88 o) et son transfert ; discipline d'état GL
(R-1500..R-1505, INV-12) ; shaders et cache binaire (C-63) ; GPU Resource Manager (C-62) ;
PBR + sonde d'environnement (C-81) ; instancing (C-65) ; skinning GPU (C-66) ; ombres,
occlusion ; **disponibilité du maillage en multi**.

## Alternatives évaluées

- **Rendu géométrique par `EntityRenderer` (un par entité).** Rejeté : plus simple à court
  terme, mais à contre-courant de l'architecture (§19 veut une passe centrale instanciée que les
  deux backends partagent) ; l'`EntityRenderer` reste pour le seul libellé de debug.
- **Décodage GEOM côté Java** (zstd LWJGL/zstd-jni + parseur gardé par `compiler_version`).
  Rejeté (bifurcation ratifiée en faveur du natif) : duplique le format A3D côté Java et ajoute
  une dépendance, alors que Rust possède déjà le décodage et qu'il faudra de toute façon la
  couture de données de rendu natif→Java pour C-60.
- **Backend natif d'abord (C-60).** Rejeté pour le premier rendu : le plus dur, au sommet d'une
  pile (C-62/C-63/C-81) ; aucun pixel avant toute la pile. Vanilla donne un rendu visible vite
  et sert de repli universel (R-1491).
- **Placeholder seul, sans vrai maillage.** Conservé uniquement comme **étape T1** de validation
  de la passe, pas comme rendu final.

## Conséquences

- Une couture de rendu neuve sous `dev.axion.forge.client` (R-401 / T-020 : seul `dev.axion.
  forge` touche Forge/Minecraft) : interface `RenderBackend`, sélection R-1490, passe
  `RenderLevelStageEvent` @ `AFTER_ENTITIES`.
- Une **nouvelle fonction FFI** de décodage GEOM (T2, `[EFFORT MAX]`), avec test de disposition,
  transcrite avec son consommateur ; `CURRENT_SCHEMA` inchangé.
- Un accesseur assets client et un cache de renderable par asset ; lecture cross-thread bornée
  aux octets `compiled()` immuables.
- Rendu **solo d'abord** ; le multi (compilation client ou transport réseau du maillage) est une
  tranche ultérieure.
- Les décisions du backend natif (upload GPU, état GL, shaders, PBR…) restent **ouvertes** pour
  l'ADR de C-60.
