# ADR-166 — La version d'API qu'un addon exige, le kit de GameTest et le validateur hors jeu

- **Statut** : **proposé** le 2026-11-12, en attente de Killian. Il ajoute à l'API publique une surface nouvelle (un
  service de lecture du contenu, un paquet d'aide aux GameTests) et une convention dans le `mods.toml` des addons :
  des choix de contrat qui ne se décident pas sans lui (CDC, contrat d'implémentation, section 5).
- **Date** : 2026-11-12
- **Portée** : C-70 (API), C-27 (registre du contenu), C-71 (commandes) ; ADR-162 D11 (le principe de la version
  exigée, déjà accepté) et sa tranche 5. Capacités tenues : **CAP-49** (kit de test et validateur hors jeu ; l'addon
  témoin est fait) ; **CAP-48** pour sa dernière part, « version de l'API déclarable comme dépendance d'un addon » ;
  **CAP-42** en partie (voir Q4).
- **Ordonné par** : ADR-162, tranche 5 ; ADR-160 D10.10 et la vision V3 (développeur d'addon Java).

## Contexte

Ce qui existe (tranche 5, 2026-11-12) :

- **La publication** : `dev.axion:axion-api`, le JAR complet d'AXION et le modèle d'addon sont sur
  `maven.eriniumlab.com`. Un débutant télécharge le modèle, le lance, et voit ses caisses en jeu.
- **La version de l'API** : `ApiVersion.CURRENT` (1.0.0) et `satisfies(...)` existent, indépendants de la version du
  mod (R-1751). Rien ne permet à un addon de **déclarer** la version qu'il exige : il compile contre l'API 1.2, un
  joueur l'installe avec AXION 1.0, et le jeu plante sur la première méthode absente — un `NoSuchMethodError` qui ne
  nomme ni l'addon ni la version à installer. ADR-162 D11 a décidé le principe : « AXION refuse clairement une
  version trop ancienne ».
- **Tester un addon** : un addon peut écrire des GameTests Forge, et l'API sait déjà faire apparaître une assembly
  (`AxionApi.get().assemblies().spawn(...)`). Mais rien ne lui dit si sa definition a été chargée ou pourquoi elle a
  été refusée : il doit lire le journal. Chaque addon réécrirait les mêmes aides (attendre le repos d'un objet,
  vérifier qu'il bouge).
- **Valider sans lancer le jeu** : les règles qu'AXION applique au chargement — schéma, références entre contenus,
  présence des modèles, et compilation d'un modèle et de sa definition par le natif — sont du Java pur ou passent par
  la bibliothèque native, qui se charge hors du jeu (les tests JUnit d'AXION le font). Rien ne les offre à un addon :
  il découvre ses fautes en lançant Minecraft.

## Décision

### D1 — La version d'API exigée se déclare dans le `mods.toml` de l'addon

Un addon déclare la version minimale de l'API qu'il exige dans les propriétés de son mod, que Forge lit sans code :

```toml
[modproperties.example_addon]
    axion_api = "1.0"
```

- **Format** : `MAJEUR.MINEUR` ou `MAJEUR.MINEUR.CORRECTIF`. La comparaison est celle de `ApiVersion.satisfies` :
  même majeure, mineure et correctif au moins égaux.
- **Contrôle** : AXION lit cette propriété pour chaque mod chargé, à sa construction. Une version exigée que l'API
  présente ne satisfait pas — ou une valeur mal écrite — produit un **avertissement de chargement Forge** : l'écran
  jaune que Forge affiche à la fin du chargement, qui nomme l'addon, la version exigée et la version présente
  (« example_addon exige l'API AXION 1.2, AXION fournit 1.0 : mettez AXION à jour »). Le même message va au journal.
- **Conséquence** : le contenu de cet addon n'est pas enregistré (son fournisseur n'est pas appelé), et le jeu
  démarre. Un addon sans la propriété est accepté, comme aujourd'hui.
- **Le modèle d'addon** porte la propriété, à la version de l'API qu'il compile.
- **Les mécanismes de Forge** existent dans Forge 47.4.23 : `IModInfo.getModProperties()` rend la table
  `[modproperties.<modId>]`, et `ModLoader.addWarning(ModLoadingWarning)` ajoute un avertissement à l'écran de fin de
  chargement (lu dans les JAR `forgespi` et `fmlcore` de cette version, par `javap`, le 2026-11-12).

Pourquoi le `mods.toml` et pas un appel Java : le contrôle a lieu avant tout code de l'addon, donc avant la première
méthode absente ; un débutant n'a rien à programmer ; et le message apparaît à l'écran du joueur, pas seulement au
journal.

### D2 — Un service de lecture du contenu : `AxionApi.content()`

L'API gagne un service en lecture seule, `ContentQuery` :

| Méthode | Ce qu'elle rend |
|---|---|
| `boolean isLoaded(String definitionId)` | vrai si la definition est chargée et utilisable |
| `Optional<String> refusal(String definitionId)` | la cause de son refus, telle que le journal l'écrit, si elle a été refusée |
| `Set<String> definitions()` | les definitions chargées |

Thread : quelconque (un instantané du registre). Coût : une lecture. Échec : aucun ; une definition inconnue n'est ni
chargée ni refusée. `@Experimental` jusqu'au prononcé de M5 (ADR-162 D11).

### D3 — Le kit de GameTest : `dev.axion.api.testing`

Un paquet de l'API, livré avec AXION, aide un addon à tester son contenu dans un vrai serveur de GameTests :

| Méthode statique de `AxionGameTests` | Ce qu'elle fait |
|---|---|
| `assertLoaded(GameTestHelper, String definitionId)` | échoue, avec la cause du refus, si la definition n'est pas chargée |
| `spawn(GameTestHelper, String definitionId, Vec3 relative)` | fait apparaître une assembly, position relative au gabarit du test |
| `succeedWhenAtRest(GameTestHelper, Assembly)` | réussit quand l'assembly ne bouge plus (position stable sur dix ticks) |
| `succeedWhenMoved(GameTestHelper, Assembly, double distance)` | réussit quand elle s'est déplacée d'au moins cette distance |

- Il s'appuie sur l'API publique seule (`assemblies()`, `content()`) : un addon n'y voit rien de l'implémentation.
- Un gabarit de test minimal (une dalle) est fourni sous `axion:testing/dalle`, pour qu'un addon n'ait pas à créer
  sa propre structure.
- L'addon témoin reçoit un GameTest écrit avec ce kit ; la CI d'AXION le joue, et le modèle d'addon le porte, avec un
  lancement `runGameTestServer`.

### D4 — Le validateur hors jeu : `./gradlew checkAxionContent`

Le JAR d'AXION porte un point d'entrée, `dev.axion.tools.ContentCheck`, que le modèle d'addon branche sur une tâche
Gradle, elle-même appelée par `./gradlew build` :

- **Ce qu'il lit** : le dossier `src/main/resources/axion/` de l'addon, comme `registerFolder("axion/")`, plus le
  contenu d'AXION lui-même (ses matériaux, que les definitions de l'addon nomment).
- **Ce qu'il vérifie** : exactement les règles du chargement en jeu — doublons, schéma, références entre contenus
  (matériaux, pneus, groupes de collision), présence des modèles, puis la compilation de chaque modèle et de chaque
  definition contre son modèle par la bibliothèque native (les nœuds nommés existent, les roues ont leur nœud…).
- **Ce qu'il dit** : chaque faute, avec le fichier et le chemin JSON, dans les mêmes mots que le journal du jeu ; la
  tâche échoue s'il y en a une.
- **Ce qu'il ne voit pas** : une definition construite en Java par le builder, qui n'existe qu'à l'exécution de
  l'addon. Le kit de GameTest (D3) la couvre : `assertLoaded` dit pourquoi elle serait refusée.

### D5 — Le CDC et la documentation

- **23.2** (surface de l'API) reçoit `ContentQuery` et le paquet `testing` ; **C-70** la convention `axion_api` ;
  l'ANNEXE A.7 note CAP-48 et CAP-49 tenues ; le registre des amendements (38.9) reçoit **A14**.
- **Le guide d'addon** reçoit deux pages, en français et en anglais : « Tester ton addon » (GameTests et validateur)
  et « Versions » (déclarer l'API exigée, ce que voit le joueur).

## Grille d'ADR-160 D7

| Axe | Réponse |
|---|---|
| JSON | le validateur lit les fichiers de l'addon avec les règles du jeu (D4) |
| API | `AxionApi.content()` (D2), `dev.axion.api.testing` (D3) ; `@Experimental` jusqu'à M5 |
| Instance | sans objet |
| Sauvegarde | sans objet : rien ne s'écrit dans le monde |
| Réseau | sans objet ; la version d'API exigée se vérifie de chaque côté, sur ses propres mods |
| Bornes | format de version contrôlé ; une valeur mal écrite avertit au lieu d'être ignorée |
| Coût | à la construction des mods, une lecture de propriété par mod ; le validateur tourne au build de l'addon, pas en jeu |
| Multijoueur | un serveur dont l'AXION est trop ancien n'enregistre pas le contenu de l'addon, donc ne l'exige pas de ses clients (ADR-165) |
| Créateur | le modèle d'addon porte la version exigée, un GameTest et le validateur ; deux pages de guide |
| Preuve | à écrire avec le code : test de la lecture de `axion_api` et de l'avertissement ; GameTest du témoin par le kit ; le validateur sur le témoin (vert) et sur un contenu fautif (chaque faute nommée) |
| Composition | sans objet |
| Côtés | le kit et `content()` côté serveur ; la version exigée des deux côtés |
| Évolution | une nouvelle aide de test est un ajout ; le validateur suit les règles du jeu, puisqu'il les appelle |
| Ensemble | sans objet |
| Diagnostic | l'écran d'avertissement de Forge et le journal (D1) ; la cause du refus (D2, D3) ; la sortie du validateur (D4) |
| Présentation | messages traduits (anglais, français) pour l'avertissement de version |
| Propriété | sans objet |

## Questions à Killian

- **Q1 — La version exigée non satisfaite.** Proposé : avertissement Forge à l'écran, contenu de l'addon non chargé,
  le jeu démarre. Autre voie : arrêter le chargement (écran d'erreur de Forge), comme une dépendance absente — plus
  net, mais un monde qui contient déjà des objets de cet addon ne s'ouvre plus du tout.
- **Q2 — Où vit le kit de GameTest.** Proposé : dans `axion-api` (paquet `dev.axion.api.testing`), donc livré avec
  AXION, sans dépendance de plus pour l'addon. Autre voie : un artefact séparé, `axion-testkit`, que seul un addon qui
  teste déclare.
- **Q3 — Le validateur dans le build.** Proposé : `./gradlew build` l'appelle, donc un contenu fautif fait échouer le
  build de l'addon. Autre voie : une tâche à lancer à la main, qui n'échoue jamais un build.
- **Q4 — CAP-42.** CAP-42 demande de « valider une definition contre son modèle sans lancer le jeu (`ax-cli`) ». Le
  validateur de D4 le fait, en Java, avec les règles exactes du jeu. Proposé : CAP-42 se tient par lui pour cette
  part (amendement), `ax-cli` gardant la validation des seuls fichiers de modèle ; la seconde part de CAP-42, voir en
  jeu les definitions refusées (`/axion defs list | info`), reste à faire. Autre voie : garder CAP-42 telle quelle, et
  écrire aussi la validation de definition dans `ax-cli`.

## Alternatives évaluées

- **Déclarer la version exigée par un appel Java** (`registrar.requireApi(...)`) : écarté au profit de D1. Le
  contrôle viendrait après le chargement des classes de l'addon, un débutant devrait le programmer, et le joueur ne
  verrait rien à l'écran.
- **S'appuyer sur la plage de version du `mods.toml` (`versionRange` de la dépendance `axion`)** : elle porte sur la
  version du mod, que R-1751 rend indépendante de celle de l'API. Elle reste utile, mais ne dit rien de l'API.
- **Un validateur qui réécrit les règles** (un schéma JSON pour un éditeur, par exemple) : il divergerait des règles
  du jeu. Le validateur appelle le code du chargement lui-même.

## Conséquences

- L'API gagne deux surfaces `@Experimental` ; la garde binaire (CAP-52, tranche 6) les couvrira au prononcé de M5.
- Le modèle d'addon devient le parcours complet d'un moddeur : déclarer, valider au build, tester en jeu, publier.
- La tranche 5 d'ADR-162 se ferme avec cet ADR, une fois son code fait et prouvé.
