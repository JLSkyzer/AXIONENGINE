# ADR-110 — Section `NODE` : nodes sur 80 octets et table des noms

- **Statut** : accepté
- **Date** : 2026-09-13
- **Portée** : C-21, C-24, DM-03, PARTIE 7.3, R-881, R-893, R-901, R-903, C-27
- **Décidé par** : Claude ; résolution des noms d'asset en M3 décidée par Killian

## Contexte

La table 7.3 définit `NODE` comme « `NodeDesc[]` + table des noms », sans en
donner la disposition. L'écrivain livré en M1 s'en écartait de trois façons :

- **aucune table des noms** : un nom de node — celui qu'une definition écrit,
  `"root_node": "body"` — ne pouvait pas se retrouver depuis l'asset compilé ;
- **76 octets par node** au lieu des 80 de `NodeDesc` : le remplissage de fin,
  qu'impose l'alignement sur le `u64` de tête, n'était pas écrit. La section ne
  se lisait donc pas en place, contrairement à R-881 et au commentaire du code ;
- **empreintes nulles** pour les nodes OBJ et STL : seul l'importeur glTF
  calculait `name_hash`.

En corrigeant l'importeur glTF, un défaut voisin est apparu : un node sans nom
entrait dans la règle d'unicité de C-22 sous le nom `"node"`, si bien que deux
nodes sans nom faisaient refuser un glTF valide pour doublon.

C-27 a besoin de ces noms. Killian a décidé que la résolution des noms d'asset
désignés par une definition se fera **côté natif, en M3**, quand la definition
sera transmise au natif : le lecteur A3D Rust existe, il est fuzzé (R-903), et
régions, clips, os et colliders n'existent dans l'asset qu'à partir de M3. M2
corrige le format pour que M3 trouve les noms à leur place.

## Décision

1. **Disposition**, en petit-boutiste :

   ```text
   u32 node_count
   u32 names_size                    octets de la table des noms
   NodeDesc[node_count]              80 octets, disposition repr(C)
   NameRef[node_count]               u32 offset, u32 length
   u8[names_size]                    noms UTF-8, sans terminateur
   ```

   Les nodes commencent à l'octet 8, multiple de leur alignement, et se lisent
   en place. Les références de noms donnent un accès direct au nom d'un node
   sans parcourir la table.

2. **Nom et empreinte sont liés.** Le nom d'un node est celui dont `name_hash`
   est l'empreinte FNV-1a 64 bits ; un node sans nom a un nom vide.
   L'encodeur refuse d'écrire une empreinte qui ne correspond pas à son nom, le
   décodeur refuse de la lire. Une incohérence ferait résoudre un nom vers un
   autre node sans erreur.

3. **`name_hash` vit dans `ax-model`**, avec les descripteurs qui la portent, et
   tous les importeurs l'emploient.

4. **Un node sans nom n'entre pas dans la règle d'unicité** de C-22 : il n'a
   rien à rendre unique.

5. **Le décodeur traite des données hostiles** : dénombrement plafonné par
   C-22 avant toute allocation (R-901), taille exacte, nom dans la table,
   UTF-8, 64 octets au plus. Toute faute rend `E-3007`. La cible de fuzzing
   `a3d_reader` décode la table dès qu'une section `NODE` est présente.

## Migration

Aucun lecteur ne décodait le contenu de `NODE` avant cette décision : le seul
consommateur de l'ancienne disposition était le cache d'assets, que
l'incrément de `COMPILER_VERSION` (5) invalide (R-892). Le conteneur, lui, ne
change pas : T-590 et T-591 relisent et reproduisent toujours le fichier de
référence v1.1. La nouvelle disposition est figée par un test qui compare
l'encodage à des octets écrits champ par champ, et les positions des champs de
`NodeDesc` par un test de `ax-model`.

## Conséquences

- Une definition ne peut toujours pas se voir refuser un nom de node inexistant
  en M2 : elle n'en vérifie que la forme (ADR-109). La résolution vient en M3,
  avec les autres catégories de noms d'asset.
- Tout importeur ou toute étape qui ajoute des nodes — y compris des nodes
  synthétiques — doit tenir `node_names` à jour, sans quoi la compilation échoue
  à l'écriture de `NODE`.
