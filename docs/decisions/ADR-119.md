# ADR-119 — Chargement d'asset natif (IF-06) et transfert de géométrie au client

- **Statut** : **accepté** — ratifié par Killian le 2026-10-01. Le contrat ci-dessous fait foi
  pour T2 (`[EFFORT MAX]`, frontière FFI).
- **Date** : 2026-10-01
- **Portée** : IF-06 (§4.8), IF-02 (§4.4), R-250, R-262, R-264, R-270, R-271, R-313, R-320..R-322,
  R-110, R-111, R-143, R-880, R-882, R-890, R-900..R-902, R-480, INV-08, DM-03, DM-04, §6.3,
  §7.2, §7.3, §19.4, ADR-103, ADR-118 ; C-24, C-13, C-14, C-30, C-61.
- **Proposé par** : Claude, en ouvrant ADR-118 T2 ; **ratifié par** : Killian le 2026-10-01.

## Contexte

ADR-118 a ratifié le principe : le maillage d'une assembly est **décodé par le natif** et remis
à Java, qui le dessine (backend vanilla d'abord). Il n'a pas fixé **les octets** de ce passage.
C'est l'objet de cet ADR — « un octet mal placé se paie en silence et pour toujours ».

Le CDC donne déjà le cadre, qu'il faut suivre et non contourner :

- **§4.10** : *Rust possède les assets compilés* ; Java n'en détient que des vues.
- **IF-06** (§4.8) déclare `axion_asset_load(ctx, asset_id, sections_mask, AssetHandle* out)` et
  `axion_asset_unload(ctx, AssetHandle h)` — **spécifiées, jamais implémentées**.
- **§6.3** : le lecteur A3D charge par masque de sections ; GEOM va au natif *(serveur + client)*
  et au GPU *(client)*.
- **IF-02** : la donnée de masse passe par des tampons typés (`AXION_BUF_ASSET_IN/OUT`) ; **R-313**
  interdit à une fonction FFI d'allouer côté Java — donc aucun `byte[]` rendu par JNI.
- **§4.1** : scene graph, LOD, construction du contenu des tampons de rendu = **Rust** ; appels GL
  et draw calls = Java.

Ce que la lecture du code a établi, et qui façonne le contrat :

1. **GEOM est en espace local des nodes.** L'importeur range les positions telles que la source
   les donne ; c'est la hiérarchie DM-03 (`NodeDesc.parent`, `local`, `mesh`) qui place chaque
   pièce. Dessiner GEOM à l'identité serait juste pour un cube à un seul node, **faux pour un
   vrai modèle** (les pièces s'empileraient à l'origine). Le natif a tout pour calculer la pose de
   repos : `decode_nodes` (C-24) et `SceneGraph` (C-30, livré).
2. **Les indices sont locaux au mesh** : `sommet = vertices[mesh.vertex_offset + indice]`, chaque
   indice `< mesh.vertex_count` (validateur C-22, `rules.rs`) — le style *base vertex* de §5.52.
3. **`ASSET_IN`/`ASSET_OUT` sont uniques par session**, déjà employés par la compilation (thread
   serveur). En solo, client et serveur intégré partagent la session : sans sérialisation côté
   Java, une acquisition concurrente peut **réallouer** le tampon (R-270) sous la vue de l'autre
   thread, qui écrirait alors dans de la mémoire native libérée.
4. **Un seul verrou de session natif** sérialise tous les appels : décoder un gros asset sous ce
   verrou bloquerait le cycle de simulation du serveur intégré.
5. Le bilan d'arrêt (R-322) ne compte aujourd'hui que les tampons ; `ax-mem` fournit
   `ArenaCounter` (C-13) que la session n'emploie pas encore.

## Décision proposée

### 1. Fonctions

```c
/* IF-06 — signature du CDC, inchangée. */
int32_t axion_asset_load(uint64_t ctx, uint64_t asset_id, uint32_t sections_mask,
                         AssetHandle* out);

/* IF-06 — signature du CDC, inchangée. */
int32_t axion_asset_unload(uint64_t ctx, AssetHandle h);

/* Ajout à IF-06 (cet ADR) : dépose dans AXION_BUF_ASSET_OUT la géométrie d'un asset chargé
   et sa liste de dessin au repos ; out_size reçoit la taille de la charge utile. */
int32_t axion_asset_geometry(uint64_t ctx, AssetHandle h, uint64_t* out_size);
```

`AssetHandle = Handle { u32 index; u32 generation; }` (DM-01) ; génération 0 = invalide (R-111),
incrémentée à la libération (R-110) ; un handle périmé rend `E-2001` sans effet de bord.

**`AXION_ABI_VERSION` reste 2.** ADR-103 l'a portée à 2 pour une **rupture** (signature
d'`axion_init` modifiée) ; les ajouts faits depuis (`axion_asset_compile/poll`, `axion_sim_*`)
ne l'ont pas incrémentée. Trois fonctions ajoutées ne rompent rien, et le JAR embarque toujours
son propre binaire natif (`validateJar`).

### 2. `axion_asset_load` — entrée et validation

- **Octets** : Java écrit le conteneur A3D compilé, tel quel, dans la charge utile d'`ASSET_IN`.
  Le conteneur est **auto-délimité** par le `total_size` de son en-tête (§7.2) : la signature du
  CDC n'a pas de paramètre de longueur, et n'en a pas besoin. Sous le verrou de session, le natif
  lit `total_size` (borné par la charge utile disponible et `assets.max_compiled_bytes`, R-900,
  R-901) et **copie** ces octets hors du tampon partagé ; **décodage hors verrou** ; insertion du
  résultat sous verrou. Un gros asset ne fige donc pas le cycle de simulation.
- **Conteneur** : `A3dFile::open` — magic, CRC d'en-tête, version majeure (R-890), bornes des
  sections, plafonds (R-900, R-901) ; CRC de section avant décompression (R-882), décompression
  bornée (R-902).
- **Identité** : `header.asset_id` doit valoir `asset_id`, sinon refus `E-2002` — les octets ne
  sont pas ceux de l'asset annoncé, faute d'appelant.
- **Masque** : bit *i* = rang du tag dans la table normative de la PARTIE 7 (`SectionMask`,
  déjà documenté comme forme de passage IF-06) : `NODE` = bit 0, `GEOM` = bit 1, `MATL` = bit 2,
  … `EXTR` = bit 16 ; **ajout en fin uniquement**. Cet ADR prend en charge `NODE | GEOM` ; tout
  autre bit, ou un masque vide, est refusé `E-2002` — un masque qui « réussit » sans rien charger
  ferait croire à un chargement qui n'a pas eu lieu. Une section demandée mais **absente** du
  fichier n'est pas une faute (esprit de R-880) : elle est notée absente.
- **Décodage** : `NODE` par `decode_nodes` (existant) ; `GEOM` par un nouveau `decode_geometry`
  (§4). Échec → code d'`A3dError` (`E-3007` pour une section malformée).
- **Pose de repos** : si `NODE` et `GEOM` sont présents, la liste de dessin (§3) est calculée au
  chargement par le scene graph (C-30). Une transformation non finie refuse l'asset (`E-3007`).
- **Mémoire** : la taille des données décodées résidentes est imputée à l'arène `PERSISTENT`
  (`ArenaCounter`, C-13, R-480), plafonnée par `budgets.native_mem_bytes` ; dépassement →
  `E-2004`, rien n'est conservé.
- **Propriété** : chaque appel crée un handle **indépendant** ; Java le possède et doit le rendre
  par `axion_asset_unload` (R-321).

### 3. `axion_asset_geometry` — charge utile de `ASSET_OUT`

Le handle doit être vivant (`E-2001` sinon) et chargé avec `NODE | GEOM` (`E-2002` sinon). La
charge utile est reconstruite depuis les données résidentes à **chaque appel** : Java peut la
redemander sans recharger l'asset (reconstruction des ressources GPU sur changement de resource
pack, R-752). Un fichier sans `GEOM` ni `NODE` rend des comptes nuls — un transfert vide valide.

Disposition, petit-boutiste, alignée sur 4 :

```text
offset 0   u32 mesh_count
       4   u32 vertex_count
       8   u32 index_count
       12  u32 draw_count
       16  MeshDesc[mesh_count]        48 o chacun, DM-04 tel quel
           Vertex[vertex_count]        48 o chacun, DM-04 (R-140) = sommet GPU de §19.4
           u32 indices[index_count]    locaux au mesh (base vertex)
           RestDraw[draw_count]        64 o chacun
```

```rust
#[repr(C)]
pub struct RestDraw {
    pub mesh: u32,        // 0   index dans MeshDesc[] (LOD 0)
    pub node: u32,        // 4   node porteur (état par node à venir : parts, dommages)
    pub node_flags: u32,  // 8   NodeFlags du node (DM-03) : NO_CULL, EMISSIVE, SHADOW_CASTER…
    pub _pad: u32,        // 12  réservé, à zéro
    pub model: [f32; 12], // 16  mat4x3 colonne-major (convention GLSL de §19.4) : transformation
}                         //     de repos du node, en espace asset ; total 64 o
```

**Garanties vérifiées par le natif avant tout dépôt** (Java peut indexer sans contrôle de
cohérence, les bornes de tableau Java restant la dernière défense) : comptes `<=` plafonds R-143
(2 000 000 sommets, 6 000 000 indices) ; chaque plage de mesh tient dans ses tableaux ;
`index_count` de chaque mesh multiple de 3 ; chaque indice `< mesh.vertex_count` ; chaque
`RestDraw.mesh < mesh_count` ; `model` fini.

**Liste de dessin au repos (LOD 0)** : un `RestDraw` par node portant `VISIBLE`, un mesh
(`mesh != u32::MAX`), le bit 0 de `lod_mask`, et **pas** `REVEALED_ON_DAMAGE` (masqué tant qu'aucun
dommage ne l'a révélé) ; ordre des nodes (déterministe). Le routage par passe reste à Java, d'après
`MeshDesc.flags` (`TRANSPARENT` → passe translucide, `DOUBLE_SIDED` → sans culling).

C'est la version **statique, calculée une fois**, de ce qu'`axion_render_prepare` (IF-05) produira
à chaque frame — transformations animées, LOD, culling. Les sommets restent locaux aux nodes, donc
téléversables une fois par le backend natif et animables par matrices (§19.4).

### 4. `decode_geometry` (C-24) — section `GEOM`

Disposition (celle qu'écrit le compilateur, DM-04) : `u32 mesh_count, vertex_count, index_count,
u32 0`, puis `MeshDesc[]`, `Vertex[]`, `u32[]`. Décodage **calqué sur `decode_colliders`** :
comptes plafonnés **avant** allocation (R-901), longueur exacte (arithmétique vérifiée), plages,
multiples de 3 et indices locaux contrôlés ; le premier écart rend `MalformedSection` (`E-3007`),
jamais une panique. Un test fige la disposition octet par octet.

### 5. `axion_asset_unload`

Handle vivant → libéré, génération incrémentée, octets rendus à `PERSISTENT`. Périmé → `E-2001`.

### 6. Bilan d'arrêt (R-321, R-322, INV-08)

Le bilan d'`axion_shutdown` inclut les assets encore chargés et l'équilibre de `PERSISTENT` :
un handle non rendu fait renvoyer `E-2003`, comme un tampon non relâché.

### 7. Pont JNI (C-14)

| Méthode Java | Signature | Sortie |
|---|---|---|
| `assetLoad(long ctx, long assetId, int mask, long[] out)` | `(JJI[J)I` | `out[0]` index, `out[1]` génération |
| `assetGeometry(long ctx, int index, int generation, long[] out)` | `(JII[J)I` | `out[0]` taille |
| `assetUnload(long ctx, int index, int generation)` | `(JII)I` | — |

Sorties par tableau `long[]` alloué par Java, comme `assetPoll` et `simCollect` (R-313).

### 8. Obligations côté Java

- **Un verrou unique** sérialise toute séquence *acquérir → écrire → appeler → lire → relâcher*
  sur `ASSET_IN`/`ASSET_OUT` ; `NativeAssetCompiler` l'adopte aussi (constat 3).
- Les A3D compilés sont **publiés** pour lecture inter-threads par une table concurrente
  (`AssetRegistry`) ; la référence de definitions que remplace un rechargement devient `volatile`.
- Le client possède ses handles et les rend au déchargement du monde, avant l'arrêt du natif.

### 9. Placement

`decode_geometry` → `ax-asset` (à côté de `decode_colliders`, `decode_nodes`) ; liste de dessin
au repos → `ax-scene` (scene graph) ; `RestDraw`, en-tête de transfert, encodeur et tests de
disposition → `ax-model` (à côté de `dm/commands.rs`) ; `ax-ffi` ne fait que valider, appeler,
convertir (règle de `abi.rs`) et gagne les dépendances **internes** `ax-scene` et `ax-mem` —
aucune dépendance externe.

## Alternatives évaluées

- **Fondre le dépôt de géométrie dans `axion_asset_load`** (côté client seulement). Rejeté :
  comportement implicite selon le côté, et redemander la géométrie (R-752) exigerait de recharger.
- **Ne transférer que GEOM, Java calculant les transformations des nodes.** Rejeté : dupliquerait
  le scene graph en Java, contre §4.1.
- **Cuire les transformations dans les sommets.** Rejeté : le backend natif veut des sommets
  locaux téléversés une fois et animés par matrices (§19.4) ; la pose de repos est une donnée de
  plus, pas une réécriture de la géométrie.
- **Ajouter un paramètre de longueur à `axion_asset_load`.** Rejeté : la signature d'IF-06 est
  celle du CDC figé, et le conteneur se délimite et se valide lui-même (R-900).
- **Rendre un `byte[]` par JNI.** Interdit (R-313).

## Conséquences

- Trois fonctions exportées (`axion_asset_load`, `axion_asset_geometry`, `axion_asset_unload`),
  ABI inchangée (2) ; `RestDraw` et l'en-tête de transfert figés par tests de disposition.
- Première imputation d'une arène C-13 dans la session (`PERSISTENT`) ; bilan d'arrêt étendu.
- Côté Java : verrou des tampons d'asset, publication thread-safe des A3D, cache de maillages
  client propriétaire de ses handles.
- **Hors portée, nommé** : orientation de l'assembly côté client (rotation du corps, tranche
  suivante) ; meshes glTF multi-primitives — un node ne désigne que la première (comportement
  préexistant de C-21, correctif séparé avec `COMPILER_VERSION`) ; transformations dynamiques,
  LOD et culling (IF-05) ; maillage en multijoueur.

## Décisions ratifiées (Killian, 2026-10-01)

1. **Contrat** : ratifié tel quel — trois fonctions, disposition du transfert (`RestDraw` de
   64 o), ABI inchangée (2), masque `NODE | GEOM`.
2. **Chargement côté client** : **en arrière-plan**. Le décodage se fait sur un thread de fond ;
   la boîte de T1 s'affiche le temps du chargement, puis le vrai maillage — aucun à-coup, même
   pour un gros modèle.
3. **Cube de test** : **recentré bas-centre**, `[-0.5, 0.5] × [0, 1] × [-0.5, 0.5]` (§6.5 ;
   convention des véhicules, Y = 0 au contact) — maillage, collider et hitbox s'alignent.

Découpage : **T2a** — natif, pont JNI, tests de disposition et d'ABI (aucun rendu) ; **T2b** —
cache de maillages client et rendu du vrai maillage par le backend vanilla, vérifié en jeu.
