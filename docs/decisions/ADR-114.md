# ADR-114 — Protocole de commande de `SimIn` (IF-03)

- **Statut** : **accepté** — ratifié par Killian le 2026-09-20. Le protocole ci-dessous fait foi pour l'implémentation de `submit`/`collect` (tranche 4b, à faire en session neuve).
- **Date** : 2026-09-20
- **Portée** : C-31 tranche 4, IF-03 (§4.5), DM-02, DM-06, DM-08, DM-09, ABI, R-1020, interdiction 3.13
- **Proposé par** : Claude, en préparant la tranche 4b ; **ratifié par** : Killian

## Contexte

`axion_sim_submit(ctx, tick, command_count, impact_count)` lit, dans le tampon
`SimIn`, les **commandes** que Java adresse au moteur pour le tick, et les
**impacts** destinés à la chaîne de dommage. Le §4.5 donne les comptes mais **ne
spécifie ni le format des commandes ni celui des impacts**. C'est donc une
décision d'**ABI** — au même titre que la disposition de `PhysicsEvent` (ADR-113)
ou de `BodyState` : un octet mal placé se paie en silence et pour toujours.

Le format doit :

- être **extensible** — M4 (joints), M5 (attaches), M6 (déformation) ajouteront
  des opérations, sans casser les lecteurs anciens ;
- se lire **en place**, sans copie ni allocation par tick (IF-03 vise le
  zéro-copie borné) ;
- s'**aligner sur les structures DM** existantes (`repr(C)`), pas réinventer
  leur forme ;
- appliquer les commandes de façon **déterministe** (R-1020) ;
- traiter l'entrée comme une **donnée externe** : validée, jamais indexée telle
  quelle (interdiction 3.13).

## Décision proposée

### 1. Cadre (framing)

La charge utile de `SimIn` est :

```text
[ CommandStreamHeader ]
[ command_count commandes ]
[ impact_count impacts ]
```

```rust
#[repr(C)]
pub struct CommandStreamHeader {
    pub schema_version: u32,   // version du protocole ; incrémentée à tout
                               // changement de payload d'un opcode existant
    pub _pad: u32,
}
```

Chaque **commande** est un en-tête suivi d'un payload propre à l'opcode :

```rust
#[repr(C)]
pub struct SimCommandHeader {
    pub opcode: u32,
    pub payload_len: u32,      // octets de payload qui suivent
}
```

Le lecteur avance de `8 + align_up(payload_len, 8)`. Un **opcode inconnu est
ignoré** (le lecteur saute son payload) — compatibilité avant, comme les genres
d'événements (ADR-113). Un `payload_len` qui ne correspond pas à la taille
attendue de l'opcode **connu** est un refus (`E-3050`/`E-7001` selon le cas),
jamais une interprétation de travers.

Les **impacts** forment un tableau homogène d'`ImpactSpec` (structure DM à
définir avec C-41, M6), séparé des commandes parce qu'homogène et destiné à une
autre chaîne. Tant que M6 n'existe pas, `impact_count` vaut 0.

### 2. Opcodes initiaux (M3)

Chaque payload est une structure `repr(C)` figée, avec son test de disposition,
alignée sur les DM :

| Opcode | Valeur | Payload | Effet |
|---|---|---|---|
| `CREATE_ASSEMBLY` | 0 | `AssemblyDesc` (DM-09) | Bâtit corps + colliders depuis l'asset compilé (C-32), assigne l'identité (`handle`, `node`) et la place à `spawn` dans `dimension`. |
| `REMOVE_ASSEMBLY` | 1 | `{ handle: Handle }` | Retire l'assembly et ses corps. |
| `SET_KINEMATIC` | 2 | `{ handle: Handle, transform: WorldTransform }` (DM-02) | Impose la pose d'un corps cinématique pour le prochain pas. |
| `APPLY_FORCE` | 3 | `{ handle: Handle, vector: [f32;3], point: [f32;3], at_point: u32 }` | Force centrale ou au point. |
| `APPLY_IMPULSE` | 4 | idem | Impulsion centrale ou au point. |
| `SET_DIMENSION_ENV` | 5 | `{ dimension: u64, gravity: [f32;3], wind: [f32;3], fluid_surface: f32, fluid_density: f32, flags: u32 }` | Gravité, vent et fluide d'une dimension (§10.6). |

Les opcodes des joints (M4), attaches (M5) et déformation (M6) **se réservent en
fin de table** à mesure de leurs composants ; une valeur d'opcode n'est **jamais
réattribuée**.

### 3. Déterminisme

Les commandes s'appliquent **dans l'ordre du flux**, qui est celui que Java —
autorité — écrit (R-1020). Aucune réorganisation, aucune `HashMap` dans ce
chemin.

### 4. Validation

`opcode` et `payload_len` viennent d'une donnée externe : chaque payload est lu
via un accès borné et vérifié (longueur exacte pour un opcode connu, valeurs
bornées à la construction — R-1762 pour les impacts, R-990 pour la config).
Une commande invalide est refusée et journalisée, jamais appliquée à moitié.

## Alternatives évaluées

- **Records de taille fixe (union `repr(C)`).** Plus simple à parcourir, mais
  fige la taille sur le plus gros payload et gaspille la bande passante des
  petites commandes (la plupart). L'en-tête `opcode` + `payload_len` est
  extensible sans réserver cet espace.
- **Commandes en CBOR.** Souple, mais coûteux à décoder chaque tick et non
  lisible en place — l'inverse de ce que veut IF-03. Le CBOR reste réservé à la
  configuration au démarrage (IF-01), pas au chemin chaud par tick.
- **Un tampon `SimIn` par type de commande.** Multiplie les acquisitions de
  tampon par tick ; un flux unique ordonné préserve l'ordre déterministe entre
  types (créer *puis* imposer une transform sur le même corps, dans l'ordre).

## Conséquences

- Chaque payload d'opcode devient une structure DM figée (test de disposition),
  **ratifiée avec son opcode** — donc au fil des composants qui l'emploient.
- `CREATE_ASSEMBLY` dépend de C-32 (colliders depuis l'asset compilé), M3 ; les
  opcodes M4/M5/M6 attendent leurs composants.
- Ce protocole est **ratifié** (Killian, 2026-09-20) : `axion_sim_submit`/
  `collect` s'écrivent contre lui, en session neuve à effort maximal.
- `AxionCollectResult` (sortie de `collect`) et le format des tampons `SimOut`
  (`BodyState[]`) / `Events` (`PhysicsEvent[]`) sont déjà cadrés par IF-03 et
  ADR-113 / DM-08 ; seul l'**entrée** (ce protocole) restait à concevoir.
