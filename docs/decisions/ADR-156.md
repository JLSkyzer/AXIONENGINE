# ADR-156 — Étapes 4 et 5 de C-27 : `CompiledDefinition` compilée par le natif, registre de session, ABI 12

- **Statut** : **accepté** le 2026-10-30 par Killian : Q1 à Q4 tranchées comme proposé (compilation
  native sur `DEFN`, `CREATE_ASSEMBLY` par empreinte en ABI 12, asset par handle d'IF-06, étape 14 côté
  serveur renvoyée en M5). L'ADR touche :
  - l'ABI (version 12 : trois fonctions, le masque de `axion_asset_load`) ;
  - le format de `CREATE_ASSEMBLY` (IF-03) ;
  - un format d'échange nouveau, `DEFN` ;
  - la DoD de M4 (renvoi de l'étape 14 côté serveur).

  Ces choix ne se décident pas sans Killian (CDC §5, contrat d'implémentation l.8237). Les quatre
  questions sont en fin de document.
- **Date** : 2026-10-30
- **Portée** :
  - C-27 (fiche 5.20) : étapes 3 (la part qui désigne l'asset), 4 et 5 ; R-580, R-581 ;
  - R-190 (`E-3050` « à la compilation »), R-930 et R-931 (`E-7002`), R-704, R-1640 ;
  - DM-09 (`AssemblyDesc.definition: u64`) ; IF-03 (`CREATE_ASSEMBLY`) ; IF-06 (`axion_asset_load`) ;
  - le renvoi de C-30 (étape 14 côté serveur) ;
  - l'avertissement d'une table `LODM` ou `ANIM` refusée, que Java ne peut pas nommer.
- **Ordonné par** :
  - [ADR-137](ADR-137.md), ligne C-27 : noms d'asset résolus côté natif, étape 4, étape 5 avec C-51 ;
  - [ADR-146](ADR-146.md) §5 et §7 ; [ADR-150](ADR-150.md) D5 ; [ADR-155](ADR-155.md), tranche 3b.

## Contexte

- **Ce que le CDC demande** (fiche 5.20) :
  - « 3. résolution des références (asset, matériaux, nodes, sockets, parts, régions) » ;
  - « 4. compilation en CompiledDefinition, transfert au natif » ;
  - « 5. enregistrement dans la registry, synchronisée serveur -> client au login ».
  - Une assembly native désigne sa definition par une empreinte (DM-09, `definition: u64`).
  - Les refus de R-190 (`E-3050`) se jugent « à la compilation » ; R-931 refuse une definition dont un
    node physique a un parent animé (`E-7002`) ; R-930 fait d'un conflit déclaré un avertissement de
    compilation.
- **Ce qui existe** :
  - Étapes 1 à 3 en Java (`DefinitionRegistry`, `DefinitionChecker`). Les références internes se
    résolvent à la lecture. Celles qui désignent l'asset (node, mesh, région, clip, os, collider) ne sont
    vérifiées que dans leur forme (`NameCategory`, catégories non internes).
  - Étape 5, pour la registry Java : `S2C_Registry` porte les textes JSON, que le client relit par le
    même lecteur strict (ADR-150 D5). La synchronisation au login est donc faite.
  - Aucune `CompiledDefinition`, aucun registre natif. À chaque apparition, `AssemblyRuntime.createBody`
    relit le conteneur de l'asset en Java et en tire `NODE`, `PHYS` et `ANIM`. Il résout ensuite les noms
    (`AssemblyBodies.of`) et marque `PHYS` : `REFITTABLE` (R-623), l'index de matériau (ADR-149 D2) et
    les groupes de collision (R-980). `CREATE_ASSEMBLY` emporte le tout : corps, joints, points de
    grippage, `NODE`, `ANIM` et `PHYS` marqué.
  - Le client relit `NODE` en Java pour trouver le node racine de son rendu (`AxionRenderPass.rigOf`).
  - Le serveur ne charge aucun asset dans le natif : `axion_asset_load` ne sert qu'au rendu, et
    n'accepte que `NODE`, `GEOM`, `MATL` et `TEXR`.
- **Ce qui ne va pas** :
  - Une definition dont un nom ne se résout pas n'est pas refusée (R-580). L'assembly reste inerte à
    son apparition, avec un avertissement, et la faute ne se voit qu'en jeu.
  - Java lit trois formats binaires de l'asset (`NODE`, `PHYS`, `ANIM`), que le natif lit aussi. Une
    évolution de DM-03 ou de DM-06 se fait donc en deux langages.
  - R-931 n'est pas appliquée comme un refus. Si une racine de corps secondaire ou l'un de ses ancêtres
    est animé, l'animation serveur est abandonnée à la création (ADR-155, tranche 3b).
  - Une table `LODM` ou `ANIM` refusée garde son motif dans le natif (`LoadedAsset.lod_refused`,
    `anim_refused`). `axion_asset_load` ne rend que le handle : Java ne peut pas nommer l'asset fautif.

## Décision proposée

### D1. Le périmètre

- **Dans ce chantier** :
  - la résolution de toutes les références d'une definition qui désignent l'asset : nodes, meshes,
    clips, os, colliders ; les nodes que désignent ses sockets, ses parts, ses corps, ses joints et ses
    roues ;
  - la compilation (étape 4) et le registre natif (étape 5) ;
  - les refus de R-190 et de R-931, et l'avertissement de R-930, à la compilation ;
  - `CREATE_ASSEMBLY` par empreinte de definition ;
  - le canal des avertissements d'asset.
- **Hors de ce chantier** :
  - les régions de déformation. Une région peut être générée par C-28, qui n'existe qu'en M6 : la
    résoudre avant refuserait une definition valide. Leur forme reste seule vérifiée jusque-là ;
  - ce que les sockets, les parts et les sièges produisent à l'exécution (C-48, C-53 en M5 ; C-41, C-42
    en M6). Leurs nodes sont résolus et vérifiés ; la `CompiledDefinition` n'en garde que ce qu'un
    système consomme (R-001) ;
  - l'étape 14 côté serveur (D6).

### D2. La compilation : natif, sur un encodage `DEFN` écrit par Java (Q1)

- **Le partage** : Java connaît le JSON et les registres de données ; le natif connaît l'asset.
  - Java ne lit plus le format d'asset côté serveur.
  - Le natif ne lit pas de JSON : aucune dépendance nouvelle, et R-581 tenue par construction.
- **`DEFN`** est écrit par Java depuis une definition acceptée aux étapes 1 à 3. Il contient :
  - la description DM-08 de chaque corps ;
  - les réglages de chaque joint (ADR-151 D3) et les points de grippage ;
  - la masse de l'assembly et l'autocollision ;
  - l'index de matériau de chaque part, résolu par `PhysicsMaterials` ;
  - l'appartenance et le filtre de collision, résolus en bits par `CollisionGroupRegistry` (ADR-132) ;
  - les parts déformables (R-623) ;
  - la liste des références à l'asset : catégorie et empreinte du nom (`name_hash` de DM-03).

  Le texte des noms ne passe pas : un refus rend le rang de la référence fautive, et Java en tire le
  chemin JSON et le nom pour son message `E-7001`.
- **Le natif** :
  - résout chaque référence contre l'asset et applique les marques à ses colliders ;
  - juge R-190 sur les nombres compilés (`E-3050`) ;
  - juge R-931 : une racine de corps sous un node animé est refusée (`E-7002`). Le cas où la racine est
    elle-même animée reste un avertissement, la physique l'emporte (R-930) ;
  - garde le résultat dans le registre de la session.
- **Ce que la `CompiledDefinition` contient en M4** : ce que la simulation consomme aujourd'hui, et
  rien d'autre.
  - les corps, leurs nodes racines et les joints ;
  - `PHYS` marqué, `NODE` et `ANIM` (pour R-1430) ;
  - le jugement de R-1430, fait une fois pour toutes : l'assembly a-t-elle une animation serveur.
- **Ce qui part de Java** : la résolution de `AssemblyBodies`, et l'application de `RefitMarking`,
  `MaterialMarking` et `CollisionFilter`. Leurs tests passent en Rust, avec leurs mutations.

### D3. L'asset de la compilation : un handle d'IF-06 (Q3)

- La compilation prend un handle d'asset chargé par `axion_asset_load`.
- Le masque de `axion_asset_load` accepte `PHYS` en plus, et les sections d'animation. Le serveur
  charge ainsi chaque asset qu'une definition désigne, sans ses sections de rendu.
- La `CompiledDefinition` garde ce qu'elle lit de l'asset. Le handle peut être rendu ensuite sans
  l'invalider.
- **Le moment** :
  - à chaque construction de la registry Java (rechargement de données côté serveur, réception de
    `S2C_Registry` côté client), pour chaque definition dont l'asset est compilé ;
  - pour les autres, à la fin de la compilation de leur asset, jamais sur le thread autoritaire
    (R-521).

  Une assembly qui apparaît avant sa definition compilée attend, comme elle attend aujourd'hui son
  asset.

### D4. La frontière : ABI 12 (Q2)

- **`axion_definition_compile(ctx, definition: u64, asset: Handle, out_size)`** :
  - lit `DEFN` dans `ASSET_IN` ;
  - en cas de succès, inscrit le résultat sous l'empreinte, en remplaçant le précédent, puis dépose un
    résumé dans `ASSET_OUT` : le nombre de corps et le node racine de chacun, le nombre de joints, et
    l'animation serveur ou non. Java s'en sert pour la persistance (`restoredOf`) et pour le rendu
    (`rigOf`) ;
  - en cas d'échec, rend `E-7001`, `E-3050` ou `E-7002`, et dépose dans `ASSET_OUT` le rang de la
    référence fautive et les lignes du motif (format `NEEDS_FILES`, ADR-139).
- **`axion_definition_remove(ctx, definition: u64)`** : retire une definition que le rechargement a
  fait disparaître.
- **`axion_asset_warnings(ctx, handle, out_size)`** : rend, dans `ASSET_OUT`, les lignes d'un asset
  chargé (une table `LODM` ou `ANIM` refusée et son motif). Java les journalise en nommant l'asset.
- **`CREATE_ASSEMBLY`** (IF-03) :
  - porte, dans son en-tête, l'empreinte de la definition (DM-09) ;
  - ne garde, après l'en-tête, que l'état restauré (ADR-153 D3) ;
  - perd les corps, les joints, les points de grippage et les sections `NODE`, `ANIM` et `PHYS`.

  Une empreinte inconnue du registre fait refuser la création. L'assembly reste inerte et intacte
  (R-704).
- **Une assembly vivante garde la `CompiledDefinition` de sa création.** Un rechargement ne la change
  pas sous ses pieds ; une nouvelle apparition prend la nouvelle. C'est la règle que `DefinitionRegistry`
  suit déjà en Java.

### D5. Le registre : un par session ; le client compile contre ses propres assets

- Le registre vit dans la session native, comme les assets. En solo, la session est partagée (ADR-155,
  étape 3c) : le serveur intégré compile, le client lit le même registre.
- Un client distant compile contre ses propres assets, qui viennent de ses resource packs (R-1640) :
  - un asset absent donne l'asset de secours et un avertissement ;
  - une definition qui ne se compile pas côté client est journalisée, et l'assembly se rend sans rig,
    comme aujourd'hui sans `NODE` ;
  - jamais de déconnexion.
- Un refus à l'étape 4 retire la definition de la registry Java et l'ajoute à `refusals()`. Il ne change
  ni les textes de `S2C_Registry` ni `definitions_hash` (ADR-150 D5) : chaque côté juge contre ses
  propres assets.

### D6. Le renvoi de l'étape 14 côté serveur : en M5, avec C-48 et C-53 (Q4)

- ADR-155 a écrit que l'étape 14 côté serveur « attend les sockets ». R-1430 ne la déclenche que si un
  socket, un collider, une région ou une attache dépend d'un node animé.
  - Les colliders : faits (ADR-155, tranche 3b), sans graphe vivant.
  - Les régions : M6.
  - Les sockets et les attaches : premiers consommateurs serveur en M5 (C-48 attaches, C-53 sièges).
- **Proposé** : la ligne C-30 de la DoD de M4 passe en M5, avec C-48 et C-53. Un graphe propagé côté
  serveur sans rien qui lise ses positions serait du travail sans effet (R-001 ; ADR-146, Conséquences).

### D7. Les tests

- Le CDC ne nomme aucun test pour les étapes 4 et 5 (T-280..T-284 couvrent les étapes 1 à 3, ADR-141).
  Les tests se nomment donc par leur règle : R-580 (un nom d'asset introuvable refuse la definition
  seule), R-190, R-930, R-931, R-704 (empreinte inconnue), R-1640 (asset absent côté client).
- Ceux d'`AssemblyBodies`, `RefitMarking`, `MaterialMarking` et `CollisionFilter` passent en Rust.
- Chaque règle s'accompagne de sa mutation rouge.
- Les cinq definitions d'exemple se compilent (T-630..T-634).
- Les GameTests existants restent verts : création, persistance (T-713*), joints, réseau.

## Mise en œuvre proposée

1. `DEFN` et sa lecture native, avec la résolution, les marques et les refus ; tests Rust.
2. Le registre de session, `axion_definition_compile` et `axion_definition_remove`, le masque d'IF-06 ;
   ABI 12.
3. Java écrit `DEFN`, compile au rechargement et à la fin de la compilation des assets, et tient les
   refus d'étape 4.
4. `CREATE_ASSEMBLY` par empreinte. Java retire la lecture de `NODE`, `PHYS` et `ANIM` côté serveur ; le
   rendu prend son node racine du résumé.
5. `axion_asset_warnings` et son journal ; la documentation : `PHYSICS.md`, qui dit aujourd'hui les
   nodes résolus « à l'apparition », le rustdoc de l'ABI, le CHANGELOG.

## Alternatives évaluées

- **Java compile tout, le natif ne valide que des index** :
  - avantage : le code de résolution et de marquage existe et il est testé ;
  - écarté : contraire à ADR-146 §5. Java continuerait de lire trois formats d'asset, et il lui faudrait
    décoder `ANIM` pour juger R-931.
- **Le natif lit le JSON** :
  - avantage : un seul encodage ;
  - écarté : la validation du schéma serait dupliquée, une dépendance structurante serait ajoutée, et
    la surface de R-581 s'élargirait.
- **Le conteneur de l'asset passé à la compilation, sans handle** :
  - avantage : une seule fonction ;
  - écarté : une seconde voie de décodage de l'asset, à côté d'IF-06.
- **`CREATE_ASSEMBLY` garde son contenu actuel et gagne l'empreinte** :
  - avantage : une transition plus douce ;
  - écarté : deux sources pour les mêmes données, et `PHYS` renvoyé à chaque apparition.

## Questions à trancher

- **Q1 — La compilation (D2).**
  - Proposé : natif, sur un encodage `DEFN` écrit par Java (les noms d'asset en empreintes).
  - Ou : Java compile, le natif valide des index.
  - Ou : le natif lit le JSON.
- **Q2 — La frontière (D4).**
  - Proposé : ABI 12 ; `CREATE_ASSEMBLY` ne porte plus que l'empreinte et l'état restauré ;
    `axion_definition_compile`, `axion_definition_remove`, `axion_asset_warnings`.
  - Ou : `CREATE_ASSEMBLY` garde son contenu et gagne l'empreinte.
- **Q3 — L'asset de la compilation (D3).**
  - Proposé : un handle d'IF-06, `PHYS` et les sections d'animation ajoutées à son masque.
  - Ou : le conteneur passé à la compilation.
- **Q4 — L'étape 14 côté serveur (D6).**
  - Proposé : renvoyée en M5 avec C-48 et C-53.
  - Ou : faite en M4, propagée pour toute assembly animée côté serveur.

## Preuve attendue

- Les tests de D7 verts, chaque règle accompagnée de sa mutation rouge.
- Les cinq definitions d'exemple compilées, et les GameTests de création, de persistance, de joints et
  de réseau verts.
- `CREATE_ASSEMBLY` sans `NODE`, `ANIM` ni `PHYS` ; Java ne lit plus ces sections côté serveur.
- Les bancs de rendu vanilla et natif verts.
- La CI verte.
